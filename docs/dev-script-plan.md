# dev.ps1 设计方案

> **状态**:**已落地**(2026-09-20)｜ 讨论来源:2026-09-20 五轮对齐
> **定位**:设计依据 + 实测记录。脚本本体在 `tools/dev.ps1`(自述 `dev.ps1 help`),入口路由见 `AGENTS.md`。
> 本文不再是「待办方案」,而是「为什么这么设计」的集中记录 —— **改脚本前值得读一遍**。

---

## 一、要解决什么

**痛点**（用户原话）：「踩坑返工、维护的文档太多、给我回复的内容太多」。

**真因**：每次会话都是一个**全新的 Agent**，上次怎么解决那个坑的它不知道 → 每次都要**重新发现 → 重新试 → 重新修**。成本不在「做」，在「每次重新推导」。

**为什么文档治不了**：文档只能**指路**，不能**拦人** —— 不照做没有任何后果。
证据（2026-09-20 实测）：`REGRESSION.md` 引用的「第六节」与《改动影响面与回归规程》**都不存在**，没人发现；`.gitignore` 里 `docs/PROGRESS.md` 这条规则**从未生效过**。

**解法**：把「每次都靠现场推导的动作」固化成脚本，让**不照做跑不通**，让**做没做到看得见**。

## 二、设计原则（五条）

| # | 原则 | 为什么 |
|---|---|---|
| 1 | **脚本是主体，Agent 无关** | 一个 `dev.ps1` 谁都能跑；skill / 提示词只是薄壳，换个 Agent 就作废 |
| 2 | **脚本只存「动作」，不存「知识」** | 动作（补变量 / 编译 / 跑测试）**不会过期**；知识（哪些文件敏感 / 检查点几条）**会过期** → 一律从权威源读 |
| 3 | **取消判断，而不是自动化判断** | 见下方专条 —— 这是最重要的一条 |
| 4 | **第一版只做纯动作** | 越复杂越容易失真（用户自己看穿的点） |
| 5 | **幂等 + `-h` 自描述** | 跑两遍结果一样；改脚本必须改自述，这是防腐烂的钩子 |

### 原则 3 展开：为什么不自动化判断

原设计想让 `ready` 自己比对 diff 决定跑快层还是慢层。**这个设计已否决。**

算账：快层秒级 + 慢层约 13 秒（2026-09-17 实测 12.9 秒，之后条数有增加）＝ **全量十几秒**。

- 省这十几秒 → 要引入一份「哪些文件敏感」的清单 → **清单会过期**（新增模块就不认识了）→ 某天静默漏跑
- 不省 → 脚本里**一个会过期的字都没有**

**十几秒换「永不失真」，划算。判断取消掉，AI 也不用记「什么时候该跑哪个」。**

## 三、子命令清单

| 子命令 | 做什么 | 什么时候跑 | 谁判断 |
|---|---|---|---|
| `build` | 编译 Debug，**自带 4 个环境变量补丁** | 改完代码 | 无条件 |
| `test` | 快层（纯逻辑，秒级） | 改完代码 | 无条件 |
| `ready` | 编译 + **跑全量检查点** + 引用检查，按固定格式打印结果 | 交付前 | 无条件 |
| `push` | 推 **main** 到双远程（origin=Gitee + github）；推送前提示工作区未提交改动与本地待推送提交数 | 合并后 | 无条件 |
| `recover` | git 索引异常恢复（**先备份未跟踪文件，再 restore**） | 出问题时 | 场景触发 |
| `env` | 环境自检（SDK / 环境变量 / 双远程可达性） | 疑难时 | 场景触发 |
| `check-docs` | 扫描全部「见 XXX 第 N 节」类引用，报告失效 | 定期 / 改动文档后 | 场景触发 |

**规律**：7 条里只有 3 条需要 AI「判断该不该用」，而且都是「出问题才用」。其余 4 条**无脑跑** —— 判断负担基本消灭。

### `ready` 的固定输出（这就是「摄像头」）

```
[编译] 0 警告 0 错误
[快层] 31 / 31 通过        退出码 0
[慢层] 278 / 278 通过      退出码 0
[文档] 12 处交叉引用全部有效
```

**用户的验收动作只有一条：让它贴这段。贴不出＝交付未完成。** 不需要懂代码，只要看有没有这几行。

## 四、错误处理：三类分叉（用户建议 + 补充分叉）

| 类型 | 例子 | 处理 | 上升到 AI？ |
|---|---|---|---|
| **A. 暂时性 / 环境性** | 网络 502、文件被占用、临时锁 | **脚本自己指数退避重试**；重试上限后仍失败才往外抛 | 否 |
| **B. 脚本自己坏了** | 路径写错、参数不对、逻辑错 | **AI 介入**：先绕过 → 后报告 → 问改不改 | 是 |
| **C. 前置条件不满足** | 不在 git 仓库、SDK 没装、分支不对 | 脚本**拒绝执行 + 说清怎么办** → AI 转告用户 | 转告即可 |

**原则：能让脚本自己修好的，绝不上升到 AI。**

理由：上升到 AI 要花 token、花一轮对话，而且 AI 未必修得对。脚本自己退避重试最便宜。
**范本**：项目里已有的 `Services/SafeClipboard` —— 指数退避 25/50ms、只对暂时性异常重试、**永不抛异常**。

## 五、退出码约定（整个机制的地基）

**「检查点红了」和「脚本自己坏了」是完全不同的两件事**，混在一起 AI 就会乱。用退出码分开：

| 退出码 | 含义 | AI 该做什么 |
|---|---|---|
| `0` | 成功 | 继续 |
| `1` | **任务失败**（编译有错、检查点红了） | 这是**正常结果** → 看输出去**改代码**，不是改脚本 |
| `2` | **脚本自身故障** | 走第六节的报告流程 |

**AI 只看退出码就知道该不该介入，不用读一堆堆栈。**

## 六、脚本异常报告机制（用户提出）

**流程**：脚本报错 → **先绕过去把任务做完** → 交付时**必须**附报告 → 等用户拍板。

**报告格式**（复用用户 SOUL.md 三-8 现成的《Skill 执行后汇报机制》，只换主语）：

> **脚本异常报告：[脚本名]**
> 1. **什么错** —— 哪一步、期望什么、实际什么
> 2. **怎么绕的** —— **用的是什么命令**
> 3. **建议** —— 改脚本 / 改环境 / 只是偶发不用改
> 4. **等用户拍板**

**第 2 条最值钱**：AI 绕过时用的手段，本身就是「脚本该长什么样」的线索。**每次绕过都是一次免费的改进提案。**

### 怎么保证 AI 真的会回头报告 —— 这是 L0 陷阱

光在方案里写「要报告」就是靠自觉，会被跳过。**必须变成交付标准**：

> 落地时在 `AGENTS.md` 红线区加一条：
> **脚本报错 → 先绕过做完任务 → 交付时必须附「脚本异常报告」；没报告的，视为交付未完成。**

这样它就不是善意提醒，而是**用户能验收的东西**。

## 七、防失真机制（回应「脚本会失真吗」）

### 脚本的烂法和文档不同

| | 文档 | 脚本 |
|---|---|---|
| 失真后 | **静默腐烂** —— 不对了但没人知道，照样被引用 | **跑不过就报错** —— 当场失败，不假装工作 |
| 举例 | 「第六节」不存在，半年后才被抓到 | 构建参数一改，检查没过 → 立刻红 |
| 发现成本 | 得有人读、去比对 | 跑一次就知道 |

**「跑不过」是好事，不是坏事。** 但脚本有两种失真，第二种要防：

| 类型 | 表现 | 危险度 |
|---|---|---|
| 硬失真 | 跑不起来，直接报错 | 安全（自曝） |
| **软失真** | **照样跑得好好的，但判断已经错了** | **真风险** |

**软失真的根因只有一条：把「会变的知识」写进了脚本。** → 回归原则 2：一律从权威源读，或干脆取消判断。

### 三条自动报警

1. **`ready` 打印实际条数** —— 和文档里写的对不上就报警（抓「加了检查点忘了改文档」）
2. **`check-docs` 扫失效引用** —— 今天手工抓的 3 处，以后自动抓
3. **`check-docs` 必须单独搜 `.workbuddy/`** —— ripgrep **默认跳过隐藏目录**，常规搜索搜不到（今天的实测盲点）

### 收敛效果

真正会烂的东西，从「8 份互相引用的文档」收敛到「**1 处**」（`REGRESSION.md` 的触发表），而那一处有维护纪律兜着。

## 八、落地范围（2026-09-20 实际落地 10 个）

**只做纯动作，不含任何会过期的判断。**

| 批次 | 子命令 |
|---|---|
| 第一批 | `build` / `test` / `ready` / `push` / `recover` |
| 第二批 | `snap` / `status` / `start` / `merge` / `commit` |
| 未做 | `pack`（发版打包，低频、边际价值小）；`env` 与 `check-docs` 的常用能力已分别并入 `status` 和 `ready` |

**实测状态**：`build` / `test` / `ready` / `snap` / `status` / `recover` / `help` 七个**已实跑验证通过**；
`start` / `merge` / `push` 会改变仓库或远程状态，**留给真实使用时验证**。

跑一两个月确认好用，再考虑加东西。

## 十、明确不做的事

| 不做 | 为什么 |
|---|---|
| 自动判断该跑哪层 | 会引入会过期的清单 → 软失真（原则 3） |
| 把检查点条数写死在脚本里 | 会过期 → 改为数实际输出 |
| 把「哪些文件敏感」写进脚本 | 会过期 → 跑全量即可 |
| 脚本里做 Lint / 代码规范检查 | 项目已定「不部署 CI/CD」，且非当前痛点 |
| 用脚本替代人工验收 | UI / 交互类机器测不了（REGRESSION 既有定论） |

## 附二：实测记录（2026-09-20 落地时真踩到的坑）

写脚本容易，**跑通不容易**。以下 5 个坑全部是实跑时暴露的，记下来免得下次重踩：

| # | 现象 | 根因 | 解法 |
|---|---|---|---|
| 1 | 脚本输出的中文全乱码（`status 鐜扮姸涓€灞?`） | 脚本里设了 `[Console]::OutputEncoding = UTF-8`，但它是被父进程调用的，父进程按系统代码页（本机 GBK）解码 | **不要改** `OutputEncoding`，保持系统默认 |
| 2 | git 读出的 commit message 乱码（`鏂板 dev.ps1`） | 仓库内容在磁盘上是 UTF-8 字节，按 GBK 解就错 | 只在**调用 git 那一段**临时切 UTF-8 解码，调完立刻还原（`Get-Git`） |
| 3 | 检查点 31 项全过、退出码本是 0，脚本却报失败，且「退出码」字段塞满整段输出文本 | `& prog` 的输出流进了函数返回值流，和退出码混成一个数组 | 外部程序输出必须**先捕获、恢复编码后再输出**（`Invoke-External`） |
| 4 | 检查点中文用例名乱码，且调用后被 `pause` 卡住 | .NET 系工具按 UTF-8 输出；`run-tests.bat` 末尾有 `pause` | 调用期间临时切 UTF-8 解码；用 `'' \| & $bat` 喂一个空行 |
| 5 | `snap` 报「一张图都没生成」，但几分钟后目录里躺着 25 张图 | `FocusCapture.exe` 是 **GUI 子系统程序**：用 `& exe` 调用时 PowerShell **不会等它跑完**，也不给退出码 | 用 `Start-Process -Wait -PassThru`；并且**看产物**（有没有 PNG），不看退出码 |

**第 5 条是本次最有价值的一课**：能用**产物**证明的，就不要信「声明的退出码」。
它同时让 `snap` 的实现比原方案更稳 —— 原方案写的是「检查退出码」，而实际上那个退出码根本拿不到。
