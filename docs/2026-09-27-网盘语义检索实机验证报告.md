# 网盘语义检索 —— 实机验证报告

> 日期：2026-09-27
> 分支：`experiment/netdisk-semantic-eval`（**主项目代码零改动；用户数据只读、零写入**）
> 配套：`docs/2026-09-27-网盘语义检索可行性评估.md`（评估）、`tools/baidu-unisearch/`（只读探针）
> **一句话结论：接口调得通、`dir` 守得住、但「语义」没有兑现 —— 沙箱内文件只有文件名进了索引，内容/向量召回零实证。**

---

## 一、验证方法

- **探针**：`tools/baidu-unisearch`（新建，独立 csproj，引用主项目复用凭据读取）
- **调用**：`POST https://pan.baidu.com/xpan/unisearch`，`scene=mcpserver`
- **总调用次数：4 次**（全部 `error_no=0`）。刻意不做压测 → 配额上限仍未探明
- **只读边界**：不下载 / 不上传 / 不删除 / 不建目录 / 不写任何文件 / **不刷新令牌**（`refresh_token` 一次性，刷新会改变用户授权状态）
- **脱敏**：绝不打印令牌；沙箱内路径只保留到**目录层级**，沙箱外一律记作 `(沙箱外)`

## 三、四个未知数的结论

### U1 应用 token + `scene=mcpserver` 能否调通 → ✅ **成立**

4 次调用全部 `HTTP 200 / error_no=0`。**我们现在的授权（`scope=basic,netdisk`）可以直接调这个接口**，不需要走官方 MCP 的独立授权体系。

### U2 沙箱文件是否被「特征预处理」→ ❌ **不成立（决定性）**

| 观察 | 数据 |
|---|---|
| 文件名关键词能命中沙箱内文件 | ✅ S1 命中 1 条（`files/`）、S4 命中 1 条（`attachments/2026-09/`） |
| `source` 出现向量来源（7 文档 / 8 视频 / 9 音频） | ❌ **一次都没有** |
| `source` 出现文档文本来源（11） | ❌ **一次都没有** |
| `content`（召回文本段落）非空 | ❌ **4 次全为 0** |
| 语义模式（`search_type=1`）命中沙箱内文件 | ❌ S2 = 0 条（返回的 10 条全在沙箱外，且 `source` 仍是 4） |

**判定**：对我们关心的沙箱内文件，**只有文件名进了搜索索引，内容（文本 / 向量）没有**。所谓「语义搜索」在本次全部实测中**退化为文件名关键词匹配**（`source` 恒为 4）。

> 严格来说：`content` 字段官方定义为「召回的文本段落，对应来源 7、8、9」，所以 `content=0` 只直接证明**没有向量召回**；但 4 次调用中 `source` **从未出现 11（文档文本）**，两条证据合起来指向同一结论：**内容级索引没有建立**。

### U3 配额 / 频控 → ⚠️ **仍未探明（未主动压测）**

4 次连续调用**未触发** `31034`（频控）或 `20012`（超限）。真实上限未知。按官方 FAQ「搜索接口每人每日 2000 次」的口径，余量充足；但**不能据此认定可高频调用** —— 未压测就不下结论。

### U4 `dir` 是否生效 → ✅ **严格生效**

S2 vs S3 是一次**干净对照**（同 query、同 `search_type`，唯一变量是加了 `dir`）：

| | `dir` | 条目 |
|---|---|---|
| S2 | 未传（默认 `"/"`） | **10**（全在沙箱外） |
| S3 | `/apps/FocusCapture` | **0** |

`dir` 参数用 JSON 数组字面量 + URL 编码（`dir=["/apps/FocusCapture"]`）**被服务端接受且严格生效**。

## 四、⚠️ 附带发现：隐私边界问题已被实证

**不传 `dir` 时，能搜到用户整个网盘的文件**：

- S2 返回 **10 条沙箱外**文件（含 category 1 视频 / 4 文档 / 6 其他）
- S4 返回 **3 条沙箱外**文件

这**实证了评估文档 §3.3 的担心**：`dir` 默认 `["/"]`，而这个 token 确实有全盘搜索能力。若照默认实现，应用内的 Agent 将能读到用户网盘里**所有**文件的名称、类型、大小、时间 —— 与「只访问自己沙箱」的既有边界**正面冲突**。

**结论**：凡实施（若实施），必须**显式传 `dir=["/apps/FocusCapture"]`**，不给默认值留任何口子。

---

## 五、最终判定：语义条路收益不成立，建议**不做**

评估文档 §3.1 给出的两分支判定，实测落到了**不成立**那一支：

| 评估时的假设 | 实测 |
|---|---|
| 沙箱文件被预处理 → 语义召回有效 → 值得做 | ❌ **未预处理** → 只能文件名 |
| 沙箱文件不预处理 → 退化成文件名搜索 → 价值有限，应转做「本地文件内容检索」 | ✅ **落在这一支** |

**所以：**
1. `unisearch` 对我们的**增量价值 = 云端实时文件名搜索**（对照现有 `find_cloud_files` 的「本地元数据离线子串匹配」）。
   - 但本地元数据本来就有 `FileStoreSync` 同步，「云端实时」这点增量，**不足以**支撑新增一条联网链路 + 占配额 + 撑开隐私边界的代价。
2. 现有 `listall` + 「与云端核对」在**穷举性**上更强（一次拉全，不是模糊匹配）——`unisearch` 无法替代它。
3. **建议：不实施「网盘语义检索」。** 若要追求「语义找文件」，真正的方向是**本地文件内容检索**（自己做 embedding + 向量存储），那是另一条独立的线。

### 已知缺口（诚实交代）

- **未进一步验证「沙箱外文件是否有内容索引」** —— 因此无法区分「是 `/apps/` 沙箱不被预处理」还是「该账号整体未启用预处理」。配额考虑已停止调用。这个区别对**未来**是否值得再评估有影响，但**不影响当前结论**（无论哪种，对我们都不可用）。
- 「文件特征预处理」如何触发（用户手动？特定入口？需申请？）官方文档未说明，**仍是未知数**。

## 六、数据安全（本次实测的硬约束，逐条核对）
