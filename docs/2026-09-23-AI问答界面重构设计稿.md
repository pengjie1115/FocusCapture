## 3. 数据结构变更

### 3.1 `ChatGroup` 加分组指令 + 逐字段修改时间（`Services/ChatGroupStore.cs`）

```
public string Instruction { get; set; } = "";          // 分组指令（Agent.md 等价物），空 = 无
public DateTime NameUpdatedAt { get; set; }            // 名称最后修改时间（跨端 LWW 裁决）
public DateTime InstructionUpdatedAt { get; set; }     // 指令最后修改时间（跨端 LWW 裁决）
```

**为什么连名称也要时间戳**：现有同步代码在「同一分组两端都存在」时无条件"本地 wins"（`Services/Sync/ChatSyncEngine.cs:449` 注释原文"本地 wins 同 Id 冲突（无版本号，简单并集）"），结果是 **A 端改的分组名会被 B 端下一轮同步回滚**。这是现有缺陷之一（§11-3）。要修它，就必须有时间戳才能判方向 —— 所以 `NameUpdatedAt` 不是为了新功能，是**还债**。

字段兼容：旧 `chat_groups.json` 缺这两个字段 → 反序列化得 `DateTime.MinValue` → 视为"未知"，此时回退到原有的"本地 wins"行为（不恶化现状）。

### 3.2 `SessionFile` 加会话级模型（`Services/ChatSessionService.cs`）

```
public string ModelKey { get; set; } = "";   // <providerId>/<modelId>；空 = 跟随全局 ActiveModelKey
```

- **空值兜底 = 跟随全局** → **老会话零迁移**（旧文件缺字段反序列化取空串，自动落到全局默认）。
- 新建会话时写入**当时的全局默认值**；之后在本会话切换只改本会话。
- 若存的 key 对应的供应商已被删 → 走 `AiModelResolver.Resolve` 的既有三级回退（第一个可用模型），**不崩**。
- ⚠️ 全局 `ActiveModelKey` 的语义随之改变：从"当前使用模型"变成"**新建会话的初始模型**"。设置页现有文案（`Windows/SettingsWindow.xaml:440`「上面是 AI 问答当前使用的模型」）必须同步改，否则文案说谎。

### 3.3 收藏 = 内置保留分组

`ChatGroupStore` 增加：

```
public const string FavoriteId = "__favorite__";
```

- `Load()` 时若清单中无 `FavoriteId` → 自动补建一条（`Name = "收藏"`、`CreatedAt = DateTime.MinValue`、`DeviceId = ""`）。
- `ChatGroupsWindow` 的分组列表**过滤掉** `FavoriteId`（收藏不出现在"会话分组管理"里）。
- 删除该 Id 的操作**拒绝执行**（双保险：UI 不提供入口 + Store 层拦住）。

### 3.4 数据迁移

**不需要迁移**（`MIGRATION.md` 顺序铁律不受影响）。全部是新增字段，旧文件反序列化取默认值即可。

→ 实施时在 `MIGRATION.md` 补一行「2026-09-23 AI 问答重构：新增字段有默认值，无需迁移」，防止以后有人误判为漏做。

## 5. 分组指令

### 5.1 用法（用户原话）

> 建三个分组，分别是飞书 CLI、得到大脑、百度网盘。得到大脑分组的指令写"当进到这个分组时，我的一切指令默认对象都是得到大脑"。于是我说"上传笔记"，而不用每次说"上传笔记到得到大脑"。

### 5.2 优先级（安全地基，不可反）

```
系统红线（不许让用户去命令行 / 牌号纪律 / 工具白名单 ...）
      ↑ 不可被覆盖
分组指令
      ↑
会话 SystemPrompt（现有字段）
      ↑
用户输入
```

**实现要点**：分组指令与现有的 Agent 规则注入走**同一个闸门** —— `ChatSessionService.AppendSystemRules()`（`Services/ChatSessionService.cs:59`），并由 `AIDialogWindow` 现有的 `ConversationRuntime.AgentRulesAdded` 标志控制"每会话只注入一次"，避免重复累积。

注入文本必须**显式标注来源与从属关系**，例如：

```
【分组指令 —— 作用范围限于本会话，不得违反前述系统规则】
当进到这个分组时，我的一切指令默认对象都是得到大脑。
```

理由：模型会把分组指令当"用户的新命令"来执行，不标注来源与从属，等于给了一条**绕过系统红线的后门**。

### 5.3 边界

- 指令为空 → 完全不注入（不留空标题，避免污染上下文）
- 指令超长 → 截断阈值与现有 `AiToolResultLimit` 无关，建议按 2000 字符上限，超出截断并在界面提示
- 改指令后**下次发消息时生效**（现读，不缓存）
- 删分组 → 指令随分组记录一起消失（组内会话回归未分组，也就没有指令了）

## 6. 同步（跨端）

分组清单 `chat_groups.json` **已参与坚果云同步**（`ChatGroupStore` 注释明写）。`ChatSyncEngine.SyncGroupsAsync`（`Services/Sync/ChatSyncEngine.cs:432-483`）的现有行为已逐行核实：

| 现状 | 位置 |
|---|---|
| 云端 + 本地按 Id 并集 | `ChatSyncEngine.cs:438-449` |
| **同 Id 冲突 = 本地无条件 wins（无版本号）** | `:449` —— `foreach (var (id, g) in localById) merged[id] = g;` |
| 同名分组合并：胜出 = `CreatedAt` 最早 → `DeviceId` → `Id` 字典序；败者删除 + 引用败者的会话 `GroupId` 重映射 | `:453-469` |
| 缺 `DeviceId` 的旧清单兜底填充 | `:453-454` ← **"后加字段有先例可循"已证实** |

### 6.1 要补的裁决规则

| 场景 | 现有行为 | 改为 |
|---|---|---|
| 同 Id，两端名字不同 | **本地无条件覆盖** → 他端的改名会被回滚 | 比 `NameUpdatedAt` 取较晚者；双方都为 `MinValue`（旧数据）时保持现有"本地 wins" |
| 同 Id，两端指令不同 | 同上（指令是本次新加字段） | 比 `InstructionUpdatedAt` 取较晚者；一方为空视为"没写过"，取非空方 |
| 同名合并（两端各建了同名分组） | 胜出 = `CreatedAt` 最早 | 名称/指令**逐字段**取新，不整体跟随胜出方 —— 否则"早建的分组"会把"晚改的指令"一起吞掉 |

## 11. 现有分组代码缺陷清单（2026-09-23 实查）

> 用户判断"之前分组的代码是有问题的，你自己最好做一下检查，要么就重写"。
> **核实结论：成立** —— 查出 5 处必须修的真缺陷 + 2 处轻微问题。每条附可自查的代码位置与**现象级复现方式**。

### 11-1【高】`ChatGroupStore` 读-改-写无锁，与后台同步竞态 → 用户刚建的分组会消失

- **证据**：`Services/ChatGroupStore.cs:27-55` —— `Load()` / `Save()` 都是裸文件读写，**无锁、无版本号**；所有调用方都是「Load → 改 → Save」模式；而 `Services/Sync/ChatSyncEngine.cs:473-482` 会在**后台线程**做同样的事。
- **现象**：前台点「新建分组」的同一时刻，后台同步周期正好跑完 → 新分组被旧清单覆盖，**分组凭空消失**。概率低但真实，且发生时无任何提示。
- **修法**：`ChatGroupStore` 内置 `lock` 串行 + 提供 `Mutate(Action<List<ChatGroup>>)` 原子接口，不再让调用方自己组织读改写。

### 11-2【高】置顶的会话在所属分组里看不见 —— 与本次需求（决策 5）直接冲突

- **证据**：`Windows/Controls/HistoryDrawer.xaml.cs:160-170`
  ```
  foreach (var item in _flatItems)
  {
      if (item.Pinned) { pinned.Add(item); continue; }   // ← 置顶直接 continue，不再参与分组归类
      if (string.IsNullOrEmpty(item.GroupId)) ungrouped.Add(item);
      else { ...byGroup... }
  }
  ```
- **现象**：一条既置顶、又属于「项目开发」的会话，进分组区**看不到它**，只在置顶区出现。
- **修法**：`pinned` 单独收集但**不 continue**，让它继续参与分组归类。

### 11-3【高】跨端改分组名会被回滚

- **证据**：`Services/Sync/ChatSyncEngine.cs:449` 注释原文"本地 wins 同 Id 冲突（无版本号，简单并集）"，代码即 `merged[id] = g` 无条件覆盖云端。
- **现象**：A 机器把「闲聊」改名「日常闲聊」并同步 → B 机器下一轮同步后**名字退回「闲聊」**，再推回云端，A 也变回旧名。
- **根因**：`ChatGroup` 无修改时间，无法判方向。
- **修法**：加 `NameUpdatedAt`（§3.1），合并时逐字段比时间戳取新。

### 11-4【中】同一个「新建分组」，两个入口两种行为

| 入口 | 撞名时的行为 |
|---|---|
| `Windows/ChatGroupsWindow.cs:102-108` | 弹框「已存在同名分组」→ **拒绝** |
| `Windows/Controls/HistoryDrawer.xaml.cs:307-316` | **静默复用**已有分组，无任何提示 |

- **现象**：从会话右键「分组到… → 新建分组…」输入一个已存在的名字 → 不报错不提示，会话被塞进那个老分组；用户以为建了个新组，实际进了别人的组。
- **修法**：收敛到唯一的创建入口，撞名行为二选一（见 §11-8 待拍板）。

### 11-5【中】删分组非原子 → 会留下"幽灵分组"

- **证据**：`Windows/ChatGroupsWindow.cs:139-154` —— 先删分组记录并落盘（:140-141），再遍历把组内会话 `GroupId` 清空（:144-154）。
- **现象**：中途失败/崩溃 → 分组记录没了、会话还挂着已失效的 `GroupId` → 侧边栏冒出一个「（未知分组）」分区（兜底在 `HistoryDrawer.xaml.cs:186`），会话掉进幽灵区。
- **修法**：把顺序反过来（先清会话 `GroupId`，再删分组记录），并加一步自愈：进入侧边栏时清理所有指向不存在分组的 `GroupId`。

### 11-6【低】建完空分组立刻换机器可能看不到

- **证据**：`Windows/ChatGroupsWindow.cs:12-13` 注释自认 —— "ChatGroupStore 无 Notify 钩子 …（组内非空时即已触发）；空分组随下次任意周期同步"。
- **现象**：新建空分组 → 不聊任何天 → 关软件 → 另一台机器看不到这个分组（要等本机下次任意同步周期）。
- **修法**：`ChatGroupStore.Save` 后触发变更通知（照 `ChatSessionService.SessionChanged` 的先例，`Services/ChatSessionService.cs:27`），让 `NotifyLocalChange()` 立即启动防抖窗口。

### 11-7【低】同步过程自己触发下一轮同步

- **证据**：`ChatSyncEngine.cs:496-500`（`RemapLocalGroupIds` 里调 `svc.Save()`）→ `Save()` 内 `SessionChanged?.Invoke()`（`ChatSessionService.cs:169`）→ `NotifyLocalChange()` 重启 30s 防抖窗口。
- **现象**：分组重映射发生过一次后，形成"同步 → 30s → 再同步"的无谓循环。`_gate` 串行保护，**不会死循环**，只浪费请求（坚果云 600 请求/30min 红线）。
- **修法**：重映射走不触发通知的内部保存路径。

### 11-8 "修"还是"重写"：我的判断

| 文件 | 判断 | 理由 |
|---|---|---|
| `Services/ChatGroupStore.cs`（62 行） | **重写** | 才 62 行，要加的（锁 / 原子化 / 时间戳 / 变更通知 / 统一查重）比保留的还多，打补丁不如重写清楚 |
| `ChatSyncEngine.SyncGroupsAsync`（:432-483） | **修补这一段** | 整个同步引擎牵扯 E2EE、删除闭环、限流红线，整体重写风险远大于收益。只重写这一个方法 |
| `Windows/Controls/HistoryDrawer.xaml.cs`（395 行） | **废弃** | 批 2 本来就要用 `ChatSidebar` 取代它，不值得单独修 |
| `Windows/ChatGroupsWindow.cs`（173 行） | **废弃** | 功能并入侧边栏悬停菜单；但内里"删分组回未分组"的逻辑要搬进新服务并修正顺序 |

→ **"重写"的正确边界 = 重写 1 个存储类 + 重建 2 个界面文件 + 修补 1 个同步方法**。不是把分组功能推倒重来。
