> 状态：**设计已收口，待你过目后实施**
> 日期：2026-09-15（v2：完成全篇自检，补 14 处遗漏）
> 前置阅读：《百度网盘接入调研报告.md》（接入可行性、沙箱限制、限速证据）

## 一、一句话定位

**本地当工作区，网盘当仓库，坚果云当路牌。**

检索、筛选、分析全部在本地完成（零成本、瞬时）；文件本体按需从网盘取回。

---

## 二、架构

### 2.1 三条通道

```
┌─ 本机 · 工作区 ──────────────────────────────┐
│                                              │
│   [ 本地文件区 ]            [ 元数据 JSON ]   │
│    见 2.2 目录结构           客观事实，极小     │
│    可淘汰 / 有容量上限       随笔记同行        │
│                                              │
│   [ 本机缓存账本 ] ← 只存本机，绝不上云        │
│    有没有副本 / 最后用於何时 / 上传进度        │
└──────────────────────────────────────────────┘
         │                            │
    文件本体 · 大                元数据 · 极小
         ▼                            ▼
   [ 百度网盘 ]                  [ 坚果云 ]
   纯仓库 · 受限速                随笔记待办同步
   永久保留资产
```

**核心设计：两条通道分离。** 大文件走网盘（慢、受限），小元数据走坚果云（快、现成）。

### 2.2 文件放在哪（目录结构）

**⚠️ 相对上一版修正一处**：对话附件**不挪窝**，留在现有位置。新增的只有 `files/`。

```
数据根/（%AppData%\FocusCapture，可自定义，见 2.4）
 ├── chat_history/           现有，不动
 │   ├── *.json              对话记录
 │   └── attachments/        ← 对话附件（现有位置，零迁移风险）
 ├── files/                  ← 新增：正式文件
 │                            AI 产出 + 你主动上传的 → 云端永久保留
 └── …（其余现有数据）
```

**为什么不把附件挪到文件区下面**：能不动就不动。挪一次就多一次迁移风险，收益却是零。

**"文件区"概念上是一个东西，物理上落在两处**：

| 内容 | 物理位置 | 云端策略 |
|---|---|---|
| 对话附件 | `chat_history/attachments/`（沿用现有） | 默认保留 30 天 |
| 正式文件 | `files/`（新增） | 永久保留 |

两者归**同一套元数据**管理，在文件列表里按类型区分。好处：你在资源管理器里打开 `files/`，只会看到正式文件，不会被 AI 截图淹没。

### 2.3 ⚠️ 文件区里的文件被淘汰，你在别处的原件不受影响

- 你把桌面上的 Word "上传上去" = **复制一份进入文件区**，桌面那份**原封不动**
- 文件区里那份被淘汰，**只是删掉这份副本**，桌面原件、云端仓库都还在
- 所以"淘汰"永远不会造成数据丢失——**云端才是权威副本**

### 2.4 数据根位置可自定义（独立改动，建议与网盘方案拆开做）

**默认**：`%AppData%\FocusCapture`（维持现状，一个字节都不搬）
**设置项**：用户可改成任意合法路径，**文件区跟着一起走**（不做独立路径，避免两套路径管理）

**三条必须的防护**：

| 防护 | 做法 |
|---|---|
| **迁移** | 改路径时自动搬移现有数据：**先自动备份 → 复制 → 校验 → 切换 → 失败自动回滚**。**旧目录绝不自动删除**，等你确认后自己清 |
| **校验** | 拒绝系统目录 / 无写权限 / 网络路径；**写入测试失败即回滚**，绝不半途生效 |
| **重启生效** | **不做热切换**。改完提示重启（运行中一半旧路径一半新路径，是最容易出诡异 bug 的形态） |

**⚠️ 工程建议：与网盘方案拆开做。**

- 数据根自定义 = **全局风险改动**（最坏后果：丢笔记）
- 网盘接入 = **新增功能**（最坏后果：功能不可用）
- 混在同一批改，出事分不清是谁的锅。**同一版本内分两步走，先做路径自定义、确认稳了再上网盘**——工作量不变，定位成本差一倍。

**技术代价（诚实）**：现有 `FocusCapturePaths.RootOverride` 是测试用的改道开关，升级为用户设置后**测试隔离仍需保留这条通道**，两套不能打架。

## 三、决策清单（全部已拍板）

| # | 决策 | 理由 |
|---|---|---|
| 1 | 本地角色 = **缓存**，网盘 = **全量权威仓库** | 本地删除/淘汰不影响网盘 |
| 2 | **按需下载**：登录只同步元数据，文件要用时才下 | 全量拉回与容量上限互斥；按需后"淘汰复活/首登雪崩/黑名单"三问题同时消失 |
| 3 | **不做全量自动拉** → 不需要云端"不要名单" | 不自动拉，就没有东西需要拦 |
| 4 | 云端只保留**一个标记：彻底删除** | 走现有回收站 + 墓碑机制防复活 |
| 5 | **淘汰 = 设备级事件，只在本机记账，绝不写云端** | 若写云端，自动过期会变成"永久删除" |
| 6 | 淘汰**双条件**：时间 + 容量，设置面板可调 | 你选的 |
| 7 | 文件实体区**复用现有 AI 附件文件夹** | 不另起炉灶；顺带修好"B 设备看不到附件" |
| 8 | 附件上网盘的**开关默认关** | 保持现有"只存本机"行为 |
| 9 | 开关开启后，附件**自动上传**，不用逐个点存档 | 你选的 |
| 10 | 云端清理**只作用于对话附件**，默认 30 天可调 | 一刀切会毁掉"全量仓库"的根基 |
| 11 | AI 产出 + 你主动上传的文件：**云端永久保留** | 这是资产 |
| 12 | 网盘里**已有的老文件不纳入** | 受 `/apps` 沙箱限制，需手动搬运，先不做 |
| 13 | **上传触发有两条路径，防重复靠"来源标记 + MD5 查重"两防线**（见 5.2） | 堵死同步盘最常见的"回环重复"事故 |
| 14 | **元数据只记客观事实，会变的状态全部放本机账本** | 元数据变成近似只增不改 → 多设备合并从难题降为"按 id 求并集" |
| 15 | 附件开关只管**自动**，不管**手动** | 开关关着时你说"把这张图存上去"，照样该传（显式意图优先） |
| 16 | **数据根可自定义**，文件区跟着走（不做独立路径） | 你只需管"数据放哪"一个概念，规则统一 |
| 17 | 路径迁移：**自动搬 + 备份 + 失败回滚 + 旧目录不自动删** | 最坏后果是丢笔记，必须双保险 |
| 18 | 本地容量上限默认 **5 GB** | 你定的 |
| 19 | 多设备**不做并发冲突检测**，后写覆盖 | 自用够；做了反而复杂 |
| 20 | 文件区位置 = **数据根下**，默认不搬任何东西 | 现有附件零迁移风险 |

## 四、数据模型

### 4.1 元数据（同步到坚果云，跨设备共享）

**设计原则：只记客观事实，不记任何设备状态。** 这样它近乎只增不改，合并极简。

| 字段 | 说明 |
|---|---|
| `id` | 稳定唯一 ID（建议 SHA256(内容)，天然去重） |
| `name` | 原始文件名（网盘侧保留原名，便于你人工辨认） |
| `netPath` | 网盘沙箱内路径，形如 `/apps/{应用名}/…` |
| `size` / `md5` | 校验 + **MD5 查重防重复上传** + 触发百度"秒传" |
| `type` | `artifact`（AI 产出）/ `upload`（主动上传）/ `attachment`（对话附件） |
| `tags` | 标签，供本地检索 |
| `createdAt` | 创建时间 |
| `updatedAt` | 最近修改（仅重命名/改标签时更新） |
| `expireAt` | **仅 `attachment` 有值**，到期清云端 |

> **注意**：`uploadState`（待上传/上传中/失败）**不在元数据里** —— 它是本机状态，见 4.2。这是第 14 条决策的落地。

### 4.2 本机缓存账本（**只存在本机，绝不上云**）

| 字段 | 说明 |
|---|---|
| `id` | 对应元数据的 id |
| `localPath` | 本地文件路径 |
| `cachedAt` | 何时到本机 |
| `lastAccess` | 最后使用时间 ← **淘汰排序依据** |
| `origin` | `downloaded`（从网盘取回，**不触发上传**）/ `local`（本地新增，需上传） |
| `uploadState` | 待上传 / 上传中 / 已上传 / 失败 |
| `uploadRetry` | 重试次数，用于失败后界面提示 |

> `origin` 字段就是**防线①**的载体：取回的文件标记为 `downloaded`，永远不触发上传。

### 4.3 多设备合并规则（设计阶段已定，不留到实施）

因为元数据近似只增不改：

| 情况 | 处理 |
|---|---|
| 两台设备各加了新记录 | **按 id 求并集**，无冲突 |
| 同一 id 两边都有 | 取 `updatedAt` 较新者（重命名/改标签的场景） |
| 一边删了、一边改了 | 以**删除墓碑**为准（走云端"彻底删除"标记） |

**关键收益**：只要"会变的东西"不进元数据，合并规则就这么简单。

## 五、关键流程

### 5.1 写入（文件进仓库）

```
文件产生（AI 产出 / 你拖入文件区 / 对话附件）
   → 算 id + md5
   → 写元数据（云端共享）
   → 立即落本地文件区
   → 标记 origin=local → 进后台上传队列
   → 成功后清空本机上传状态
```

要点：**先本地后云端，绝不阻塞你**。失败自动重试（官方 precreate 支持 uploadid 断点续传）。

### 5.2 上传触发与防重复（本次补强）

**上传有两条入口**：

| 入口 | 说明 |
|---|---|
| 显式动作 | AI 说"把这个存到网盘" / 你点上传 / 显式说"把这张图存上去" |
| 放进文件区 | 你把文件丢进 `files/`，自动排队上传（你要的"先存本地、后台异步上传"） |

**防线①：来源标记。** 从网盘取回的文件标记 `origin=downloaded`，**永不触发上传** → 堵死"取回→自动上传→重复"的回环。

**防线②：MD5 查重。** 上传前先查元数据，已有同 `md5` 记录 → 网盘里已经有了 → **只登记本地副本，不发上传**。

> **两道都要，缺一不可。** 防线①挡住常规回环；防线②兜住"你把取回的文件又拖到别处再丢回文件区"这类操作。
>
> **别指望百度的"秒传"兜底**：秒传省的是流量，**不防重复条目**——同内容不同路径，网盘里照样出现两个条目。

### 5.3 读取（"绕限流"真正发生的地方）

```
本地查元数据定位
   → 缓存账本里有 → 直接打开（零成本，不联网）
   → 没有          → 按需下载 → 写账本(origin=downloaded) → 打开
```

**只有第二种情况吃限速**，且只吃你真正在用的那一个文件。

### 5.4 淘汰（本地空间回收）

```
触发（超时 或 超容量）
   → 按 lastAccess 从最旧开始清
   → 只删本地文件 + 删账本条
   → 元数据不动（云端仍是权威）
```

淘汰后**不会自动拉回**（本来就不自动拉）；你要用，手动点一下再下回来。

### 5.5 删除（两个动作必须分开）

| 动作 | 本地 | 云端 | 元数据 |
|---|---|---|---|
| **清本地**（＝淘汰） | 删 | 留 | 留 |
| **彻底删除** | 删 | **删**（先入回收站） | 打墓碑 |

### 5.6 附件到期清理（本次补强）

```
到达 expireAt
   → 云端删（仅 attachment 类）
   → 本地那份：标记为「优先淘汰」，随下次淘汰清掉
```

**为什么不立刻删本地**：你可能正在用。标记后交给淘汰器统一处理，避免两套删除逻辑打架。

### 5.7 新设备登录

```
拉元数据（几 MB，秒级）→ 完整列表立刻可见 → 一个字节都不下载
```

边界情况：**元数据尚未拉完时**，界面显示"同步中"，不做任何"文件不存在"的判断（避免误报）。

## 六、AI 对话存取文件（本次基座）

**定位**：本地文件夹与自动同步是**后台存储**；**AI 对话框能存文件、能取文件才是用户碰得到的触点**。没有这一层，整个网盘接入就退化成一个需要手动操作的同步盘。

### 6.1 五条链路

| # | 链路 | 用户怎么说话 | 工程量 |
|---|---|---|---|
| A | AI 生成的内容 → 存网盘 | "把这份报告存到网盘" | **小**：内容在内存里，1 个工具即可 |
| B | 对话框里已附的附件 → 存网盘 | "把这张图存上去" | 中：工具需拿到当前对话的附件 |
| C | 本机任意文件 → 存网盘 | "把桌面那个 Word 传上去" | 中：**依赖「选择文件」入口** |
| D | AI 从网盘找到文件 → 交给用户 | "把我上周存的那份文档找出来" | 中：查本地元数据（零成本）+ 交付动作 |
| E | AI 从网盘取回 → 读内容自己用 | "把网盘里那份报告读一下总结" | 大：**本次先只支持文本类**（MD/TXT/代码）；PDF 解析本项目未做 |

**A 最轻**（不需要本地文件路径）；**C 和 D 才是"基座"的核心体验**。

### 6.2 ⚠️ 必须守住的安全红线：路径绝不能由 AI 填

如果做成 `upload_file(path)`，参数由模型生成 —— 模型就能编造**任意路径**，等于把整台电脑的文件系统向 AI 敞开。这与 `LocalTools.cs`「只作用于笔记库」的沙箱红线**直接冲突**。

**正确做法：用户选择 → 产生句柄 → AI 只能引用，无法凭空构造。**

```
你点「选择文件」 → 系统发一个牌号（file:20260915-1）
   → 界面显示成卡片（复用现有附件卡片的交互）
   → AI 只能说"把 file:20260915-1 存到网盘"
```

**结果：AI 的可达范围 = 你亲手点过的文件。** 边界在你手里，不在模型手里。

### 6.3 查找机制（本次补强，链路 D 的入口）

新增一个**本地搜索工具**，纯离线查元数据，支持：

| 维度 | 示例 |
|---|---|
| 文件名（模糊匹配） | "AI大模型" |
| 类型 | 图片 / 文档 / AI产出 / 附件 |
| 时间范围 | "上周"、"9月"、"最近7天" |
| 标签 | 你在元数据里打过的标签 |

**不联网、不消耗网盘额度**——这正是"检索在本地"的价值。

### 6.4 交付动作（链路 D 的出口）

**形态：文件以卡片形式落进当前对话**，卡片上再给三个动作。

| 动作 | 你会看到 |
|---|---|
| 双击卡片 | 用系统默认程序打开 |
| "在文件夹中定位" | 弹出资源管理器，文件已选中，随便拖随便复制 |
| "保存到…" | 弹保存框，你选存哪 |

> **为什么"打开/定位"几乎零成本**：按需下载已经在本地缓存了文件，这两个动作只是把硬盘上已有的东西呈现出来。
>
> **连带效果**：插进对话的附件按附件规则走——受那个**默认关**的开关管。不想让它上网盘，不开开关即可。

## 七、和现有系统的关系

| 类别 | 内容 |
|---|---|
| **可直接复用** | `Dpapi`（存 AppKey / SecretKey / token）、`RecycleBinService`（彻底删除的回收站）、`ChatAttachmentService` 的存储能力（文件实体区） |

| **新增** | 百度网盘客户端封装（设备码授权 + 上传/下载/列举）、元数据服务、本机缓存账本、淘汰器、附件到期清理器、本地搜索工具、设置面板项（开关 / 天数 / 容量上限 / 文件区位置）、Agent 工具（存 / 取 / 搜 / 交付） |
| **需要改动** | `ChatAttachmentService`（加元数据登记与上传钩子）、`AIDialogWindow`（附件开关入口、「选择文件」入口、文件卡片交付动作） |

### 8.1 原 4 项待定 —— 已全部关闭

| # | 结论 |

| 4 | 多设备并发：**不做冲突检测**，后写覆盖 |

### 8.2 待实测确认（3 项）

| # | 待验证 | 怎么验 |
|---|---|---|
| 1 | **真实下载速度** | 你建好应用后，手工走一次 dlink 下个 100MB 文件 |
| 2 | 个人使用应用的**频控数字** | 官方未写死，需实测 |
| 3 | 沙箱目录内**能否建子目录** | 文档未明确禁止，需实测 |

### 8.3 已知边界（不用验，认了就行）

- **单文件上限随账号等级**：普通 4 GB / 会员 10 GB / 超会 20 GB。超限要给出明确提示，别静默失败
- **Token 刷新失败**（refresh_token 一次性）：失败时引导你重新授权，不能卡死
- **云端附件到期后**：老对话里的附件变死链，这是清理策略的必然结果

## 九、代价与风险（丑话）

1. **取回受限速**。方案不消除限速，只是让它少遇到。首次取用某个文件要等下载。
2. **非会员体验打折**。官方 FAQ 承认速度与会员身份挂钩。**建议先实测再决定开工。**
3. **附件出本机是隐私让步**。默认关着，你自己开。
4. **桌面端必须内置 SecretKey**（百度 OAuth 无 PKCE）。自用无妨，公开分发等于公开应用身份。
5. **个人应用限 10 个用户**。自用够，做产品要先走"公开发布"审核。
6. **⚠️ 最卡人的是自己这侧**：`LocalTools.cs` 全部工具只作用于笔记库，**Agent 拿不到本地文件路径** —— 这正是第六章要解决的核心，也是本次更新的基座。它比百度那侧的任何问题都更决定工期。

## 十、实施顺序建议（分三阶段，尽早撞上致命风险）

关键原则：**先把「限速到底多难受」问明白，再决定投多少工作量。**

| 阶段 | 内容 | 目的 |
|---|---|---|
| **阶段一 · 最小闭环** | 设备码授权 + 上传 + 取回 + 链路 A/D 两个 Agent 工具 | **尽早实测限速**，验证功能值不值得做 |
| **阶段二 · 基础设施** | 本地文件区、元数据服务、按需下载、缓存账本、防重复两防线 | 让"绕限速"真正生效 |
| **阶段三 · 体验与治理** | 「选择文件」入口、淘汰策略、附件开关、设置面板、附件到期清理 | 可用性收口 |

**为什么阶段一就要做 Agent 工具**：基座链路一旦跑通，你当天就能体验"让 AI 存一份、过两天从另一台设备取回来"，限速的真实体感立刻到手。这比先花大力气搭本地缓存、最后才发现限速不可接受，要划算得多。
