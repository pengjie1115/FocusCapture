# Agent 工具盘点与新增建议

> 盘点时间：2026-09-17
> 盘点范围：`Services/Agent/`（LocalTools + FileTools + 框架）、`Services/Destinations/`（GetNote）
> 用途：供决策「下一批加哪些工具」，**本文件只是建议清单，未改动任何代码**

---

## 〇、结论先行（三句话）

1. **现有 15 个工具，覆盖「笔记增删改查 + 待办状态流转 + 网盘存/找/取/读文本」三块**，装配点是 `AIDialogWindow.EnsureAgentRegistry()` 一个方法，加工具的成本本身很低。
2. **真正的缺口有两类**：① 应用里**已经有代码、只是没注册成工具**的能力（改笔记内容、恢复删除、按日期查、导出、改文件名/标签、手动同步）——有些接近零成本；② **文件格式解析**（你点名的表格 / PDF / 网盘里的 Word 与图片）——这是唯一需要引入新依赖、且需要单独验证可行性的部分。
3. **红线不能破**：新增工具一律不得出现「本机路径」参数（现有安全模型就靠这条：模型编不出 `handle` 与 `file_id`），破坏性动作（彻底删除 / 清空）继续不给 AI。

## 二、缺口诊断：用户说得出口、但 AI 现在做不到的话

| 用户会说 | 现状 | 卡点 |
|---|---|---|
| "把那条待办的内容改成 XXX" | ✗ | `UpdateTodo` 支持 `newContent` / `dueTime` / `clearDue`，**但只暴露了 status** |
| "刚才删的那条，恢复一下" | ✗ | `RecycleBinService.List/Restore/RestoreBatch` 都有，没暴露 |
| "给我看看上周都记了啥 / 这个月记了多少条" | ✗ | `LoadNotesRange` / `LoadNoteCounts` 有，没暴露 |
| "把今天的笔记导出一份" | ✗ | `NoteExportService.BuildExport` 有，没暴露 |
| "网盘那个文件改个名 / 加个标签" | ✗ | `FileRepository.UpdateMetadata` 有，没暴露 |
| "现在同步一下" | ✗ | `SyncEngine` 有，没暴露 |
| "读一下网盘里那个 Excel / PDF / 那张图" | ✗ | `read_cloud_file` 只认文本白名单 |
| "读一下我贴的那个 docx 文档" | △ | 对话附件路径能抽 Word 文本；**网盘路径不能** |
| "帮我把这段内容做成表格存起来" | ✗ | 只能存 md/csv 纯文本，不能生成 xlsx |

## 三、建议新增（按「成本 ÷ 价值」分四类）

### 【类别 1】应用已有能力，暴露即可 —— 成本最低，建议优先

> 特点：**不需要新依赖、不需要新算法**，多数是「写一个 AgentTool 子类调一下已有方法」。全部遵守现有红线（ref_time / file_id 定位，无路径参数）。

| 建议工具名 | 做什么 | 依赖的已有代码 | 成本 | 风险点 |
|---|---|---|---|---|
| `update_note` | 改笔记/待办正文 | `NoteService.UpdateTodo(newContent)` / `AppendEdit` | 低 | 改待办与改笔记是两条路径，需先摸清 `AppendEdit` 语义再定签名 |
| `update_todo_due` | 改/清提醒时间 | `UpdateTodo(dueTime / clearDue)` | 低 | 与 `update_note` 可合并成一个工具 |
| `list_recycle_bin` | 看回收站里有什么 | `RecycleBinService.List()` | 低 | 只读，无风险 |
| `restore_deleted` | 恢复被删条目 | `RecycleBinService.Restore/RestoreBatch` | 低 | 属写操作，需过确认闸 |
| `list_notes_by_date` | 查某天/某区间的笔记 | `LoadNotes(date)` / `LoadNotesRange` | 低 | 注意：待办按 `TodoDisplayTime` 过滤的既有约定 |
| `note_stats` | 统计条数/活跃度（"这个月记了多少"） | `LoadNoteCounts` | 低 | 无 |
| `export_notes` | 导出 md/txt/docx 到文件区并给卡片 | `NoteExportService` + `FileDeliveryHub` | 中 | 导出产物应走文件仓库（而不是写桌面），否则破坏"数据全本地可控" |
| `update_file_meta` | 改文件名 / 改标签 | `FileRepository.UpdateMetadata` | 低 | 改名会不会影响网盘侧同名文件，需确认 |
| `sync_now` | 手动触发一次云同步 | `SyncEngine` | 中 | 并发问题：用户手动同步与后台定时同步要互斥 |

**小计建议**：这一类别共 9 个，我推荐其中 5 个进第一批（`update_note`、`list_notes_by_date`、`note_stats`、`list_recycle_bin` + `restore_deleted`）；
`export_notes`、`update_file_meta` 放第二批，`sync_now` 放待验证批。**全局分批以第六节总表为准。**

### 【类别 2】你点名的格式解析类 —— 价值最高，但需要分档决策

> 这一类的共同前提：**解析能力要能被两条路径共用**（网盘 `file_id` + 对话附件 `handle`），否则会出现"同一个文件，贴进对话能读、从网盘调读不了"的割裂。

#### 2.1 表格（xlsx / csv）—— 推荐做，可零依赖

| 项 | 内容 |
|---|---|
| 形态 | `read_spreadsheet(file_id 或 handle, sheet, 行范围)` → 返回「表头 + 前 N 行」的结构化文本，让模型算数/总结/找异常 |
| 现状 | `csv` 已在文本白名单里能读，但**给模型的是原始文本，没有行列语义**；`xlsx` 完全读不了 |
| 实现路径 | xlsx = zip + XML，**可纯 C# 手写**（`System.IO.Compression` + `XmlReader`），与现有 `ExtractDocx` / `.docx` 导出同一思路，**不引第三方包** |
| 已知坑 | ① 共享字符串表 `sharedStrings.xml` ② 内联字符串 ③ **日期是序列号**（1900 基准，需转换）④ 合并单元格 ⑤ 多 sheet |
| 成本 | **中**（不是随手写写；日期序列号和多 sheet 是必须处理的，否则数字全错） |
| 风险 | 大表格（几万行）要截断，否则撑爆上下文 —— 需定「先给表头 + 行数 + 前 50 行」的策略 |
| csv 附注 | 中文 CSV 常见 GBK 编码，现有读取器**明确拒绝非 UTF-8**。要不要顺带支持编码嗅探，是个独立决定（我倾向：给明确提示 + 让用户另存 UTF-8，别做嗅探，避免猜错编码） |

#### 2.2 PDF —— 唯一必须引第三方库的部分，建议单独评估

| 项 | 内容 |
|---|---|
| 现状 | `ChatAttachmentService.CreateFromFileAsync` 里明确写了 `.pdf` 直接拒绝（第 117-118 行）；`FileRepository.ReadTextAsync` 注释写明「PDF 解析本项目从未实现」 |
| 为什么不能手写 | PDF 是二进制容器：交叉引用表 + 压缩流（FlateDecode）+ 字体编码（CID / ToUnicode CMap）。**手写基本不现实**，与 docx/xlsx 的"zip+XML"根本不是一个量级 |
| 可选库 | **PdfPig**（UglyToad.PdfPig，Apache-2.0，纯托管 C#，专为文本提取设计）— 我的首选；iText7 是 AGPL **不要碰**（授权风险）；PDFium 系绑定要分发原生 dll |
| 网络实测（本次） | ✅ `api.nuget.org` 302 可达 / ✅ `globalcdn.nuget.org` 包下载 HTTP 200 —— **拉包这条路现在是通的**（9-14 记的"无外网无法验证"已过时） |
| 关键澄清 | NuGet 只在**我方开发期**拉包，DLL 随 exe 分发；**用户侧不需要网络**，不破坏"本地优先、离线可用"的定位 |
| ⚠️ 能力边界（必须提前说清） | ① **扫描件/图片版 PDF 提取不出文字**，那是 OCR 范畴，需要另一套（本地 OCR 或视觉模型），本期强烈建议不做 ② 中文 PDF 的抽取成功率依赖是否内嵌 ToUnicode 表，**需拿真实样例实测** ③ 排版顺序可能乱 |
| 成本 | **中高**：引库 + 实测抽取质量 + 处理"抽不出文字"的诚实提示 |
| 建议 | 先做一个**离线验证**：拿你的真实 PDF 跑一次 PdfPig，看中文抽取可读率。**验证通过再动手，不通过就不做** |

#### 2.3 网盘里的 Word（docx）—— 建议做，成本极低

| 项 | 内容 |
|---|---|
| 现状 | `ChatAttachmentService.ExtractDocx` 已经写好（解 zip 读 `word/document.xml`），但**只在对话附件路径生效**，网盘 `read_cloud_file` 读不了 |
| 做法 | 把抽取逻辑抽成公共方法，`read_cloud_file` 支持 `.docx`；顺手也让 `read_cloud_file` 支持 `.xlsx` |
| 成本 | **低** |
| 价值 | 填掉「同一文件两条路径能力不一致」的坑，是体验一致性问题，比新增功能更值 |

#### 2.4 网盘里的图片 —— 可以做，但有前提

| 项 | 内容 |
|---|---|
| 现状 | 图片压缩链路完整（`ChatAttachmentService.CompressImageFile`），且上行走 `image_url` 多模态部件；但 Agent 侧没有"读网盘图片"的工具 |
| 做法 | 新增 `read_cloud_file` 的图片分支：取回 → 压缩 → 以图片部件发给模型 |
| ⚠️ 前提 | **需要模型有视觉能力**。当前配置的是 OpenAI 兼容端点，不同模型的图片支持情况不同 —— 不支持的模型会报错或忽略。需要先确认你实际用哪个模型 |
| 成本 | 中（涉及请求构造改动：`OpenAICompatibleProvider.BuildMessagesArray` 是唯一序列化入口，改动要谨慎） |

### 【类别 3】其他通用 Agent 标配 —— 建议克制，逐个掂量

| 候选 | 价值判断 | 我的建议 |
|---|---|---|
| **时间解析** `parse_time`（"下周三下午三点是几号"） | `TimeParser` 已有完整实现，成本极低 | ✅ 可以加，但**模型自己算日期已经八九不离十**，价值中等。注意它一直被用在待办识别的关键路径上，别改坏 |
| **读剪贴板** `read_clipboard` | `Win32.GetClipboardText` 已有 | ⚠️ 谨慎。剪贴板自动捕获本来就是核心功能，"AI 主动读剪贴板"更可能带来隐私惊扰。**建议不做** |
| **截图** `screenshot` | 能实现（WinForms/WPF 都有） | ⚠️ 中价值，噪音大（截全屏给模型看，信息密度低）。除非有明确场景（"看一下我这个报错"），否则不做 |
| **联网搜索 / 抓网页** | 需要 API Key + 联网 + 内容外流 | ❌ **建议不做**：与应用"数据全本地、离线可用"的定位正面冲突，且引入 key 管理成本 |
| **代码执行 / 命令行** | — | ❌ **绝对不做**：安全事故面巨大，且与"零基础用户"的定位不匹配 |
| **任意路径读写文件** | — | ❌ **红线**：现有安全模型完全建立在"模型编不出路径"之上。一旦开这个口，整个防护归零 |
| **彻底删除文件 / 清空回收站** | — | ❌ **红线**：破坏性动作不给 AI（已写进项目纪律）。回收站"恢复"可以给，"彻底删"不给 |
| **系统信息**（磁盘/时间/进程） | 价值低 | ❌ 不做，凑数 |

## 四、如果只能选三个（我的推荐）

按「立刻能感受到差别 × 成本可控」排序：

1. **`update_note`（含改提醒时间）** — 现在用户说"改一下那条"，AI 只能说做不到。这是最刺眼的功能空洞，且成本最低。
2. **`read_spreadsheet`（xlsx + csv 表格化）** — 你点名的需求，零依赖可实现，覆盖"帮我看看这个表"的高频场景。
3. **`read_cloud_file` 支持 docx/xlsx（复用已有抽取器）** — 消除两条路径的能力割裂，成本极低。

**PDF 单独立项**：先做一次离线抽取验证（拿真实 PDF 跑 PdfPig 看中文可读率），**验证报告出来再决定做不做**，不要先写代码。

## 五、真要动手时的纪律（写在这里，免得忘）

1. **注册位置唯一**：`AIDialogWindow.EnsureAgentRegistry()`，新增一行；框架层（`Services/Agent/`）**不得引用 Destinations 命名空间**。
2. **无路径参数**：一律走 `handle`（用户点"选择文件"产生的牌号）或 `file_id`（本地元数据编号）。
3. **工具描述要写清使用前提**：现有工具的 `Description` 里塞了大量"不许说已上传成功"这类纪律，是因为模型会过度承诺 —— 新工具照抄这个习惯。
4. **同步更新 `REGRESSION.md`**：新增工具要加慢层检查点（`tests/sync/`），尤其是"编造牌号/传路径必须解析失败"这类红线断言。
5. **确认闸**：所有写操作 `IsReadOnly = false`，并把 `DescribeAction` 写成人话。
6. **别一次性加太多**：每加一个工具，都会增加模型的工具选择负担与误调用率。**宁可分三批加，也不要一口气加到 30 个。**

## 六、新增工具总表（21 条候选，按序号）

> 说明：本表把三、四两节的所有候选拉平到一张表，供逐条圈选。
> **「能力边界」= 能做 + 明确不能做 + 前提**，边界写不清的工具一律先别做（模型会自己脑补能力范围）。
> 建议程度：★★★ 第一批（我推荐先做）／★★ 第二批／★ 可选或待验证／✗ 不做。

| # | 工具名 | 工具能力边界 | 建议程度 |
|---|---|---|---|
| 1 | `update_note` | 改一条**已存在**笔记或待办的正文；用 `ref_time`(+`content_hint`) 定位，定位不唯一时必须报错让模型澄清。**不能**：改条目类型（笔记↔待办不可互转）、批量改、改提醒时间（见 #2） | ★★★ |
| 2 | `update_todo_due` | 只改/清一条待办的提醒时间（`dueTime` / `clearDue`），同样 `ref_time` 定位。**只对待办有效**，对普通笔记无意义；**建议与 #1 合并成一个工具**，少一个工具就少一份误调用 | ★★★ |
| 3 | `list_recycle_bin` | 只读列出回收站条目（内容摘要 + 删除时间），给 #4 提供定位依据。**不返回**原始文件路径，**不能**在回收站里改内容 | ★★★ |
| 4 | `restore_deleted` | 把回收站里一条或多条恢复回笔记库，属写操作需过确认闸。**不能**恢复超出保留期（30 天）已被清掉的条目；同指纹去重，重复恢复不产生副本 | ★★★ |
| 5 | `list_notes_by_date` | 按某天或某日期区间列出笔记与待办。**须遵守既有约定**：待办按 `TodoDisplayTime` 过滤（与主界面一致）；区间过大要截断，不能把整库倒给模型 | ★★★ |
| 6 | `note_stats` | 统计条数、活跃度、月度分布（"这个月记了多少条""哪天记得最多"）。**只统计本机已落盘数据**；不做图表渲染、不评价内容质量 | ★★★ |
| 7 | `export_notes` | 导出 md / txt / docx / json 到**设置里的导出文件夹**（按用户拍板：本机留一份、**不上云**）。三种取数路径，优先级从上到下：① `ref_times` **精选指定条目**（支持 `{"time","hint"}` 消歧）② `query` 关键词筛选 ③ `date` / 区间**全量**。**不支持**任意路径（红线）；同名自动加序号不覆盖。⚠️ 条目时间戳**只有分钟精度**，同一分钟多条必须带 hint | ★★★（已实现） |
| 8 | `update_file_meta` | 改网盘文件的**显示名 / 标签**（`UpdateMetadata`）。**不改文件内容**；⚠️ 需先确认「改名要不要连网盘侧那份一起改」——只改本机元数据会造成两端名字不一致 | ★★ |
| 9 | `sync_now` | 手动触发一次云同步（拉 + 推）。**必须与后台定时同步互斥**（同一把锁）；失败要如实报错，**绝不谎报"已同步"** | ★ |
| 10 | `read_spreadsheet` | 读 xlsx / csv，返回「表头 + 总行数 + 前 N 行」的结构化文本，供算数、总结、找异常。**不做**公式计算引擎、图表、透视表；**必须处理**日期序列号（否则数字全错）与多 sheet；超大表强制截断 | ★★★ |

## 七、补充发现：模型不知道「今天几号」（P0 上下文缺失，不是工具）

> 起因：用户提问「模型不知道今天多少号，是不是和第 14 条（`parse_time`）相关？」
> **结论：不相关。** 这是两件事：
> - **#14 `parse_time`** = 把**用户说的**时间表达翻成日期（"下周三" → 2026-09-23）。是**加一个工具**。
> - **模型不知道今天几号** = 请求里**根本没告诉它当前日期**。是**补上下文**，一个工具都不需要加。

### 证据（全链路四处，均无当前日期）

| # | 位置 | 内容 | 关键行 |
|---|---|---|---|
| 1 | `ChatSessionService.BuildSystemPrompt` | 只有角色描述 + 可选笔记内容，**无任何日期** | `ChatSessionService.cs:338-354` |
| 2 | `AIDialogWindow.AppendAgentRulesOnce` | 4 条工具纪律（工具结果是唯一事实来源等），**无日期** | `AIDialogWindow.xaml.cs:1905-1915` |
| 3 | `ExtraSystemContext` | 每轮注入的附加上下文，**只传文件牌号** | `AIDialogWindow.xaml.cs:1506-1510` |
| 4 | `PromptBuilder.BuildTimeParseMessages` | 时间解析兜底提示词，**也没给今天日期** | `PromptBuilder.cs:29-37` |
| — | 补充核实 | `Services/AI/` 与 `Services/Agent/` 全域 **grep 无任何 `DateTime.Now` / `DateTime.Today`** | — |

### 为什么这条比 #14 严重得多

模型不知道今天几号，会**整片地错**，而不是偶尔错：用户说"今天记了什么""上周那份文档""明天提醒我"——**凡是带相对时间的话，它都在猜基准点**。而 #14 只是让时间解析更准一点。**严重程度不在一个量级。**

### 正确修法（推荐 A）

| 方案 | 做法 | 评价 |
|---|---|---|
| **A. 走 `ExtraSystemContext`（推荐）** | 在里面追加一行「当前时间：yyyy-MM-dd HH:mm 星期X」 | ✅ 每轮**实时求值**、**不落会话历史**（`AgentRunService.BuildTurnMessages` 每轮调用），改动约 3 行。**符合项目既有纪律**：「每轮变化的短期状态走 `ExtraSystemContext` 注入，不写进会话历史」 |
| B. 写进系统提示词 | 在 `BuildSystemPrompt` 里加日期 | ❌ **会持久化进会话文件**（`ChatSessionService.cs:155` `SystemPrompt = _systemPrompt`）。跨天之后，那个会话里的日期就是**错的**，比不告诉它更糟 |
| C. 顺手修 #4 | `BuildTimeParseMessages` 也补上今天日期 | ✅ 独立小 bug：没基准点，"明天中午 12 点"只能靠猜。修它不影响工具清单 |

### 现象级验收（做完怎么看对不对）

1. 问"今天几号" → 答出的日期与系统日期一致
2. 早上问一句、**隔天再在同一会话里问** → 日期**跟着变**（证明没被写死进历史）
3. 问"上周我记了啥" → 时间范围与真实上周对得上

### 对 #14 的影响

上下文里有了当前时间后，模型自己算"下周三"基本够用 → **#14 的价值进一步下降**，可以从"可选"降到"暂不做"。真正需要确定性时间解析的场景（自动建待办的 `due_time`），已经有本地 `TimeParser` 兜底，不依赖模型。
