# 技能外部依赖 · 授权闭环设计稿

> 2026-09-21。范围：飞书授权跨端失效的根治 + 依赖机制可扩展性 + Agent 通道 + 运行时按需分发。
> 本文只记**结论与依据**，不记探索过程。被推翻的结论单列一节，避免后人重踩。

---

## 一、问题溯源

### 1.1 现象

用户在第二台电脑上，飞书授权永远停在"正在生成二维码…"；界面上另有红字报错。
本机（已配置过的）撤销授权后重新授权，能正常出码。

### 1.2 根因（两层，均已核实）

**第一层：应用只做了"两步中的第二步"。** lark-cli 要能用，需要先有**应用凭据**（appId + appSecret），再授权**用户身份**。

| 段 | 命令 | 产物 | 现状 |
|---|---|---|---|
| ① 应用凭据 | `lark-cli config init` | `%USERPROFILE%\.lark-cli\config.json` + 系统密钥库 | ❌ **应用里没有这一步** |
| ② 用户授权 | `lark-cli auth login` | 用户 token | ✅ 已实现（`SkillAuthWindow` 三步：申请码 → 出码 → 领 token） |

凭据缺失时 `auth login --no-wait --json` 直接返回
`{"type":"config","subtype":"not_configured"}`（退出码 3），**连 device_code 都拿不到**，二维码不可能出来。
这不是"卡住"，是第一步就死了。

**第二层：`config.json` 不含密钥本体，拷文件等于搬了钥匙串标签。** 实测文件内容：

```json
{"apps":[{"appId":"cli_aa93eb****",
          "appSecret":{"source":"keychain","id":"appsecret:cli_aa93eb****"},
          "brand":"feishu","lang":"zh_cn","users":[]}]}
```

真实密钥在**本机密钥库**（不在该文件、也不在 `cmdkey` 可见条目里）。
只拷 `config.json` 的后果：`not_configured` 消失，但请求缺客户端凭据 → 飞书返回
`device_authorization 400: The request is missing a required parameter`。

### 1.3 已被推翻的结论（**不要重踩**）

| 曾经的结论 | 状态 | 正确结论 |
|---|---|---|
| "把本机 `config.json` 拷到另一台就能用" | ❌ **错** | 密钥不随文件走，跨机必然失败 |
| "预置一个自研 Skill 教 AI 怎么用飞书" | ❌ **废弃** | lark-cli 二进制内嵌 28 个官方 Skill，业务知识不该由我们维护 |
| "修好后扫一次码就能用" | ⚠️ **不准** | 内部是两次兑换（应用凭据 + 用户授权）；用户感知如何取决于 4.1 选哪个方案 |
| "没有 Skill 时也能让 AI 操作飞书" | ❌ **不成立** | Agent 只有 `load_skill` / `run_skill_script`，两者都要求 Skill 存在 |

### 1.4 关键反转：官方自带技能体系

`lark-cli skills list` 实测返回 **28 个 skill**，内容 embed 在二进制里、随 CLI 版本同步：

- 业务：`lark-base`（多维表格）、`lark-sheets`、`lark-doc`、`lark-wiki`、`lark-slides`、`lark-markdown`、`lark-whiteboard`、`lark-im`、`lark-mail`、`lark-calendar`、`lark-task`、`lark-okr`、`lark-approval`、`lark-contact`、`lark-meeting`、`lark-drive`、`lark-apps`
- **配置/授权**：`lark-shared`（auth、身份、`--domain`、缺 scope 怎么办）
- **元能力**：`lark-openapi-explorer`（挖未被 CLI 封装的原生 API）、**`lark-skill-maker`（教 AI 把飞书操作封装成可复用 Skill）**
- 读取方式：`lark-cli skills read <name>`（markdown）、`skills list <name>`（像 ls）
- 官方 README 的 AI Agent 快速开始，**明确把 `config init --new` 作为标准路径**：
  > Run this command in the background. It will output an authorization URL — extract it and send it to the user. The command exits automatically after the user completes the setup in the browser.
- 每个命令自带风险分级：`read` / `write` / `high-risk-write`（后者必须 `--yes`）

**推论：我们要做的不是"写飞书知识"，而是"造一条从 Agent 到 lark-cli 的通路"。**

## 二、实测事实（作为设计依据）

### 2.1 体积构成

| 组成 | 大小 |
|---|---|
| 编译输出总计 | 96.1 MB |
| `runtime\lark-cli` | 47.1 MB |
| `runtime\python`（便携） | 20.2 MB |
| 去掉 `runtime` 之后 | ≈ 29 MB |

`runtime\` 全目录已在 `.gitignore`（`/runtime/`），靠 `tools\fetch-*.ps1` 拉取，构建时复制进输出。

### 2.2 下载源（均已在脚本里验证可用）

| 依赖 | 源顺序 |
|---|---|
| lark-cli | npmmirror 二进制镜像 → GitHub releases |
| Python | 华为云镜像 → npmmirror → python.org |

### 2.3 本机环境测得的能力/限制

- lark-cli 版本 `1.0.96`；`auth login --no-wait --json` 在本机返回 device_code（可用作对照基准）
- lark-cli 的 JSON 输出走 **stderr**（PowerShell 直读 stdout 会吞掉，必须合并流）
- 二进制内含文案：`config init requires a terminal for interactive mode. Run with --new to create a new app`
- 二进制内含文案：`access denied: app %s has not applied for the required scope(s)` / `ask the tenant admin to re-enable the app in the Lark admin console`
  → **新建应用可能缺 scope 或需管理员介入**
- 沙箱限制（影响验证手段，**已部分推翻**）：沙箱内脚本/cmdl 的 `Start-Job` / `Process.Start` 被拦，但**独立编译 exe 起子进程正常**（2026-09-21 用 `tools/depdiag/` 探针跑通了 `config init --new`，见 §2.4）；`$env:USERPROFILE` 隔离复现不了跨机现象（密钥库不随用户目录走）

### 2.4 `config init --new` 真实输出（2026-09-21 独立探针实测）

在隔离 USERPROFILE + 清 HERMES_HOME/OPENCLAW_HOME/LARK_CHANNEL/PYTHONPATH 下跑 `lark-cli config init --new`，90s 超时 kill 保留已读：

- **全走 stderr，stdout 空**（0 行）；**不是 JSON，是纯文本 + ASCII 块二维码 + URL**
- 结构：`[ASCII 码] / 打开以下链接配置应用: / <空> / https://open.feishu.cn/page/cli?user_code=XXXX-XXXX&lpv=<cli版本>&ocv=<版本>&from=cli / <空> / 等待配置应用...`
- **流式、启动约 1 秒吐完**，然后阻塞等浏览器完成
- **超时 kill 保留全部已读**（stderr 29 行 + URL）—— R1 验证通过
- 命令自带 `Risk: write`（非 high-risk-write，不需 `--yes`）；help 原文坐实 R1 阻塞语义：`use --new to create a new app. The command blocks until the user completes setup in the browser. Run it in the background and retrieve the verification URL from its output.`
- lark-cli 区分独立 CLI 模式 vs Agent 宿主模式（OPENCLAW_HOME/HERMES_HOME 存在时 `--new` 默认拒绝→要用 `config bind`），**印证清宿主变量的正确性**
- 实现推论（已纳入 §4.1/§5/§8）：解析 = 从 stderr 纯文本正则提 URL（非 JSON）；流式读到 URL 即提取显示，**但命令不能 kill**，要持续运行到用户浏览器完成才自然退出（user_code 设备码流，kill 掉没主体接收、配置写不进）；第一步产物是浏览器链接（非扫码），二维码在第二步 auth login

## 三、目标与非目标

**目标**

1. 任何一台电脑第一次用，用户不需要接触命令行、不需要理解"应用凭据"这个概念
2. 外部依赖机制**留出扩展位**：接第二个 CLI 时不需要改基类
3. AI 能在没有第三方 Skill 的情况下操作飞书（走应用自带通道）
4. 分发包默认体积从 96 MB 降到 ~29 MB

**非目标**

- 不做"给外部用户使用"的多租户方案（本项目只服务本人多设备，见 4.1 说明）
- 不做插件市场 / 可视化依赖编辑器
- 不把飞书业务知识写进代码或文档（官方维护）

## 四、方案设计

### 4.1 应用凭据从哪来 —— 两个可行方案（丙已否决）

> **两条硬约束**（用户 2026-09-21 明确）：
> ① 应用凭据是**私人信息，绝不写进代码 / 仓库 / 分发包 / 日志**；
> ② **不在设备之间共享**。

| | **乙：`config init --new`（默认）** | 甲：粘贴凭据（兜底入口） |
|---|---|---|
| 用户动作 | 点授权 → 浏览器创建应用 → 回应用扫码 | 从飞书开放平台复制 appId+secret，粘贴一次 |
| 飞书里的应用数 | **每台电脑 +1**（清理要回开放平台手动做） | 1 |
| 凭据落在哪 | 全程 CLI 自己完成，**应用连 secret 都不接触** | 只进 lark-cli 自己的 keychain，**应用不留副本** |
| 技术未知点 | ⚠ **`--new` 输出格式未验证**（见 §7 第 0 步）+ 新建应用权限未知 | 无（`config init --app-id X --app-secret-stdin` 非交互，已验证） |
| 定位 | 默认路径：不必去开放平台翻凭据 | 兜底：不想建新应用 / 想复用已有应用 |

**决策（用户 2026-09-21 拍板）：乙为默认，甲为兜底。** 两者在同一个授权窗口内并列 —— 乙是主按钮，甲是次要入口。

#### 乙的完整用户旅程（UI 文案必须照这个写）

```
点"授权" → 应用后台申请创建应用 → 拉起浏览器（用户跟着点一下，创建完成）
        → 回应用里出二维码 → 扫码 → 完成
```

**这是两步（浏览器创建 + 扫码），不是"扫一次码就完事"。**
界面文案不能写"扫码即可"，要如实写"第一次需要创建一个飞书应用，会打开浏览器，跟着点一下就行"。
（"点授权 → 出码 → 扫码"的一步式体验，只在**凭据已就绪**的机器上成立，即第二次以后。）

#### 甲的实现路径（兜底入口）

1. 授权窗口内的次要入口：输入框粘贴 appId + appSecret（从飞书开放平台复制）
2. 应用调 `config init --app-id <id> --brand feishu --app-secret-stdin`
   —— secret 走 **stdin**，不进命令行、不进日志、不进任何持久化副本
3. 凭据落进 lark-cli 自己的 keychain，**应用不持有**
4. 接着扫码，完成用户身份授权

#### 一条硬事实（决定了为什么必须有"第一次"这一步）

**没有应用凭据时，"扫码授权"根本无法开始**：`auth login` 直接返回
`not_configured`（退出码 3）或 `400 missing a required parameter`
→ **拿不到 device_code → 没有 verification_url → 二维码画不出来**。
这是飞书设备码流的机制，不是实现缺陷。

所以每台从没配过的机器，第一次必然多一个"把凭据搞进来"的动作（建 or 粘），无法绕过 ——
除非把凭据写进代码 / 分发包（用户已否决），或跨设备共享（技术不可行 + 用户已否决）。

#### 已否决：丙（跨设备共享凭据）

原设想：第一台填一次 → 加密存应用数据目录 → 其余机器自动复用。**否决，两条独立理由**：

1. **技术不成立**（本轮查证）：项目现有凭据加密一律走 **DPAPI(CurrentUser)**
   —— 见 `Services/Sync/Dpapi.cs` 与 `BaiduCredentialStore.cs:41` 注释：
   > 加密一律走 DPAPI（CurrentUser）：**换机器解不开是期望行为**，提示重新授权即可，不崩。

   即：照项目既有加密方式落盘，**第二台机器根本解不开**，"随数据迁移"做不到。
   要跨机可解就得改成"用户口令派生密钥"那一套（类似 SyncEngine 的 DEK），为这个场景引入口令管理，不值。
2. **用户明确不共享**：凭据是私人信息，不在设备之间共享。

→ 所以"第一台填一次、其余机器只扫码"这个卖点**不存在**。
现实只有两条路：**每台机器各填一次（甲）** 或 **每台机器各建一个应用（乙）**。

### 4.2 依赖机制抽象（留余地）

现状问题（代码核实）：

| 环节 | 位置 | 问题 |
|---|---|---|
| 依赖表 | `SkillDependencies.All()` | 硬编码一行，加依赖必改代码 |
| 探测解析 | `SkillDependency.ParseStatus()` | 认的是 lark 的 `identities.user.available` 字段，**半通用** |
| 授权协议 | `StartAuthAsync` / `MakeQrPngAsync` / `CompleteAuthAsync` / `LogoutAsync` | ⚠️ 基类"默认实现"里**写死了 lark 命令**；抽象形状是照着一个实现刻的 |
| 前置配置 | 无 | ❌ 本次事故的真缺口，抽象里没有位置 |

改法（最小抽取，不改调用点）：

1. 新增 `IDepAuthFlow`：把**授权协议**（申请码 / 出码 / 领 token / 登出）与**登录态解析**从基类搬进实现类
2. `SkillDependency` 基类只保留：Id / Name / Locate / Matches / `ProbeAsync`（起进程后交给 flow 解析）/ 展示信息
3. 新增 `PrepareAsync(ct)`：**前置配置**（默认空实现），飞书实现为"确保应用凭据就绪"
4. `SkillDependencies` 从"硬编码数组"改为注册式（`Register(...)` / `All()`），未来加依赖 = 加一个类 + 一行注册

> **诚实标注**：若三个月内不接第二个 CLI，这一层属于**为未到需求预留**。做它的理由是"现在抽成本低、事后抽要动存量"，而不是"现在必须做"。

### 4.3 Agent 通道（桥接，取代"自研 Skill"）

```
builtin-skills\lark-cli\
  SKILL.md           ← 只讲三件事：① 先 skills list 看官方技能 ② 再 skills read 读需要的
                        ③ 纪律：写/高危操作必须先问用户、不要给用户命令行
  scripts\lark.py    ← 透传：args 原样交给 lark-cli，回传退出码 + stdout + stderr
```

- 业务知识**全程来自官方**，我们只维护胶水
- 首次运行由应用落地到 `%AppData%\FocusCapture\Skills\`（策略：**目标不存在才复制**，不覆盖用户改过的版本）
- 与用户自建 Skill（如 `feishu-kb-manager`）并存，互不影响

**考虑过但否决的替代**：把 28 个官方 skill 全量导出成 28 个应用内 Skill —— 否决理由：系统提示的 Skill 清单会暴涨（token 成本）、官方 skill 的 `references/`/`scripts/` 并不 embed（内容不完整）、且桥接方案已经能按需读到同样内容。

**安全代价（明确记录）**：透传 = AI 能跑 lark-cli 任意命令（发消息、读邮件、删云盘文件）。约束三层：现有"首次执行 Skill 弹确认" + 每次调用的操作确认 + SKILL.md 里的行为纪律。**兜底的真正边界是用户授权的 scope，不是我们的代码。**

### 4.4 运行时按需分发

用户已拍板：打包默认不带 `runtime` → 查找顺序"自带优先 → AppData 兜底" → **用户点击才下载**（带进度）→ lark-cli 与 Python 一起走这套。

设计要点：

1. **落地位置**：`%AppData%\FocusCapture\runtime\<id>\`（应用目录可能不可写）
2. **查找顺序**（所有消费方统一）：自带 `AppContext.BaseDirectory\runtime\<id>\` → 用户数据目录 → PATH
3. **触发点**：设置页依赖行显示"未安装 · 点这里下载"；授权流程开始前也检查一次
4. **下载器**：HttpClient + 多源兜底 + 进度回调 + 落临时文件 + 大小/可执行性自检（沿用脚本里"`--version` 跑一次"的思路）
5. **离线**：飞书本身要联网，lark-cli 按需不损什么；但 **Python 是所有脚本类 Skill 的公共前提**，它按需 = 首次用任何脚本类 Skill 都要联网一次。**这条用户已知情并接受。**
6. **包体策略**：默认产出精简包（~29 MB）；保留"完整包"开关（开发机/无网环境用）

## 五、关键技术风险（**本节含审查中新发现的两个真 bug**）

| # | 风险 | 说明 | 处置 |
|---|---|---|---|
| **R1** | 高危 **`config init --new` 会阻塞，而现有 `SkillProcess.RunAsync` 是"进程退出后才读输出"** | 语义是「输出 URL → 阻塞等用户在浏览器完成 → 退出」。照现有实现，**URL 要等到用户操作完才拿到** → 整个流程死锁式卡住。**这是本次审查新发现的，原方案没覆盖** | `SkillProcess` 需支持**流式读取**（按行/按标记读到 URL 即返回，或超时 kill 但**保留已读内容** —— 现有实现超时时直接丢弃输出，也要改） |
| **R2** | 高危 **`BundledPathPrefix()` 只把「自带目录」前置到 PATH** | 按需下载后 lark-cli 在 AppData，脚本里的 `shutil.which("lark-cli")` 找不到 → 桥接脚本失效。**新发现** | 改为：把所有候选目录（自带 + 数据目录）都前置 |
| R3 | 中危 `SkillRuntime` 的 Python 路径是固定拼接 | 按需下载后需回落到数据目录 | 与 R2 同一处理：统一"候选路径列表" |
| R4 | 中危 新建应用的权限未知 | lark-cli 自身文案显示存在"应用未申请 scope / 需管理员" | 授权后若 scope 不全，界面引导改走"用已有凭据"（甲） |
| R5 | ~~中危 `config init --new` 的输出格式未验证~~ ✅ **已验掉** | ~~本机跑不了（沙箱拦进程启动）~~ 独立探针跑通 | ✅ 已实测（§2.4）：stderr 纯文本+URL、非 JSON、流式 1 秒吐完、阻塞；解析改 URL 提取 |
| R6 | 低危 确认粒度 | 桥接后每次调用都弹确认，连续操作会烦 | v1 单命令（安全优先），批量留待后续；`run_skill_script` 的调用确认已是现成闸 |
| R7 | 低危 输出截断 | `SkillScriptRunner` 截 4000 字符，lark-cli 大 JSON 会被切 | SKILL.md 里教 AI 用 `--jq` 收敛输出（官方也推荐） |
| R8 | 低危 自带与 AppData 双份 | 先按需下载、后升级到完整包 → 两份共存 | 策略：自带优先，AppData 那份不动（删除类操作只给用户，界面只提示） |
| R9 | 低危 授权失败不写日志 | `StartAuthAsync` 失败无日志，报错还被截到 200 字符 | 本次一并补：失败写日志、完整报错落盘 |
| R10 | 低危 界面文案不同步 | `ShowFailure()` 不改 `QrPlaceholder.Text`，"正在生成二维码…"与红字并存 → 用户以为卡死 | 本次一并修 |

## 九、自我审查（我的失误与更优解）

### 9.1 我犯的错

1. **把"拷 `config.json`"当成解决方案给你** —— 依据是看到配置里有 `appSecret` 字段就下结论，**没有打开文件看它的结构**。结果是你在另一台电脑上白折腾一轮。这是"看着像就下结论"，违背了我自己该守的取证纪律。
2. **我提的"方案丙（跨设备共享凭据）"是错的，而且错在论据上** —— 我拿 `baidu\app_credential.dat` 当"加密存凭据的既有先例"，却**没读它是怎么加密的**：项目里明写走 DPAPI(CurrentUser)、"换机器解不开是**期望行为**"。拿它论证"可跨机迁移"，等于自打嘴巴。
   另外，推荐它之前我也没问一句"你接受凭据落盘 / 跨设备共享吗"。**和错误 1 是同一个毛病：看着像就下结论，不去看真东西。**
3. **第一版影响面评估漏了两个会导致功能直接不可用的技术点**（R1 阻塞读取、R2 PATH 前置），是这一轮自查才挖出来的。说明我上一轮"影响面评估"做得不够扎实 —— 只扫了接口层，没扫数据流。
4. **对"预置 Skill"的第一版设想是错的** —— 我准备自己写领域知识，而官方早就内嵌了 28 个。如果我当时直接开工，会白写一套很快过时的东西。

### 9.2 我认为当前方案仍存在的短板（不掩饰）

- ✅ **`config init --new` 已实测（2026-09-21 独立探针 `tools/depdiag/`），当前最大未验证风险已消除。** 真值见 §2.4：**全走 stderr、纯文本 + ASCII 码 + URL、非 JSON**、启动约 1 秒流式吐完、然后阻塞等浏览器完成、超时 kill 保留已读（R1 验证通过）。对实现的修正：① 解析 = 从 stderr 纯文本正则提 URL（非 JSON，§8 检查点已同步）② 流式读到 URL 即提取显示，但**命令不能 kill**，要持续运行到用户浏览器完成才自然退出（user_code 设备码流，kill 掉没主体接收、配置写不进）③ 第一步产物是**浏览器链接**（非扫码），二维码在第二步 `auth login`。详见 `.workbuddy/memory/2026-09-21.md`。
- **按需下载会让"第一次用"多一步等待**，且给应用增加一条网络失败路径（下载失败的提示与重试必须做扎实，否则体验比自带更差）。
- **桥接透传的安全面确实变大了。** 我的三层约束里，真正有效的是"每次调用的确认"和"用户的 scope 授权"，行为纪律（写进 SKILL.md）属于软约束 —— **模型可能不遵守**。这一点我不粉饰。
- **L2 有过度设计嫌疑**（§4.2 已标注）。我倾向做，但如果你觉得不值，砍掉它不影响其它部分。
- **凭据纪律按用户要求收紧**（原丙方案的"加密落盘"设想已废除）：甲方案下 secret 只经 stdin 交给 lark-cli，**应用不落副本、不进日志、不进仓库、不进分发包**；乙方案下应用连 secret 都不接触（浏览器流程全程由 CLI 自己完成）。
