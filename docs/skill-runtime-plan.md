## 一、这一阶段做什么 / 不做什么

**做**：让 FocusCapture 具备"加载 WorkBuddy 格式 Skill 并执行其脚本"的最小闭环。

**不做**（明确划出去，避免范围蔓延）：

## 二、两个硬决策（先定这两个，其余都是推论）

### 决策 1：Skill 是"用户资产"，放数据根

```
%AppData%\FocusCapture\          ← FocusCapturePaths.Root（用户可自定义）
  Skills\                        ← 新增
    feishu-kb-manager\
      SKILL.md                   ← 原样放，不改造
      scripts\kb.py
      config\config.json
```

**理由**：Skill 是用户自己攒的东西，应该跟着数据走 —— 用户换自定义数据根时会一起搬，备份/同步也带上它。放进应用安装目录的话，应用一升级就没了。

**不改造格式**：直接吃 WorkBuddy 的目录结构。这是整个方案的价值来源 —— 能复用已有的 100+ 个 Skill，而不是让用户为 FocusCapture 重写一遍。

### 决策 2：运行时是"应用部件"，放应用目录

```
<应用目录>\runtime\python\        ← 便携版 Python（约 11MB）
```

**理由**：它是应用的一部分，不该跟着数据迁移被复制来复制去。

**⚠ 这里有三个必须处理的坑**（第 1 个是自查时才发现的，会让功能直接失效）：

| # | 坑 | 处理 |
|---|---|---|
| 1 | **官方 embeddable 包自带 `python313._pth`，会让 Python 进入 isolated 模式** —— 见 §三实测 | **部署时删掉该文件**（由 `fetch-python-runtime.ps1` 负责） |
| 2 | 应用可能装在 `C:\Program Files\`（无写权限），Python 会尝试写 `__pycache__` | 启动子进程固定注入 `PYTHONDONTWRITEBYTECODE=1` |
| 3 | Windows 上 Python 输出到管道时按 GBK 编码 → 中文乱码 | 固定注入 `PYTHONIOENCODING=utf-8` |

## 三、运行时的真实成本（已实测，不是估算）

| 项目 | 实测值 |
|---|---|
| 官方便携包 `python-3.13.12-embed-amd64.zip` | **10.9 MB**（华为云镜像下载 7.1 秒） |
| 解压后 | 20.23 MB / 34 个文件 |
| 能跑 `kb.py` 吗 | **能** —— 实测输出 `{"ok": false, "error": "缺少子命令"}` |
| 标准库覆盖 | 12 项全通过（含 `urllib.request` / `ssl` / `sqlite3` / `subprocess`） |
| 中文输出 | 正常 |
| `pip` / `venv` | **没有**（第三方库要靠预置，阶段一不做） |

### ⚠ `._pth` 隔离模式（自查新增，实测数据如下）

官方包里的 `python313._pth` 内容只有三行，但它让 Python 进入 **isolated 模式**：`sys.path` 完全由它决定，**脚本所在目录不自动加入、`PYTHONPATH` 被忽略、`site` 不执行**。

实测（同一份便携 Python，只改这一个文件）：

| | 保留 `._pth`（官方原样） | 删掉 `._pth` |
|---|---|---|
| 同目录模块 `import mod_a` | **FAIL `ModuleNotFoundError`** | **OK** |
| 标准库 `json`/`urllib`/`sqlite3` | OK | OK |
| `sys.path` | 仅 2 项（`python313.zip` + exe 目录） | 5 项（**含脚本目录**、含 `Lib`） |

**这条不处理会死得很具体**：`local-rag`（`import rag_core`）、`wechat-articles`、`tencentmap` 这类**把公共逻辑拆在同目录模块**的 Skill 会直接跑不起来；而且以后想把第三方包放进 `Lib\` 也永远不会被加载。

**处理方式**：`fetch-python-runtime.ps1` 下载解压后**删除 `python313._pth`**。

**连带影响（新增一条硬规则）**：删掉 `._pth` 后 `PYTHONPATH` 重新生效 —— 而宿主环境里可能已经设了 `PYTHONPATH`（实测本机 WorkBuddy 会话就注入了 `vendor\shim` 路径）。**执行器必须显式清空子进程的 `PYTHONPATH`**，否则用户的 Skill 会莫名其妙加载到别的东西。

**为什么这个 11MB 花得值**：它换掉的是"让用户自己去装 Python、配 PATH"—— 那是理解成本和执行成本的大头，而且新手极易装错。

### 依赖分级（决定每个 Skill 的支持程度，对用户如实标注）

| 级别 | 内容 | 对策 | 覆盖情况 |
|---|---|---|---|
| L0 | 纯 SKILL.md，无脚本 | 直接可用 | 本机 46 / 72 |
| L1 | 只用标准库的脚本 | 便携 Python 直接跑 | 多数（`urllib` 用了 17 次，`requests` 只有 4 次） |
| L2 | 需要第三方包 | **阶段一只标注"需要第三方包 X"，不自动装** | 少数（`sklearn` 5 / `docx` 3 / `numpy` 2） |
| L3 | 需要外部程序（`gh` / `ffmpeg` / `lark-cli`） | 逐个单独处理，**必须如实标注** | 个别 |

> `lark-cli` 属于 L3，但它恰好是"一个可执行文件 + 用户身份授权"，已在上一轮实测过可在非 WorkBuddy 环境跑通，**阶段一按 L3 处理**：不做自动安装，缺失时明确报错并给出指引。

## 四、三个核心部件

### 4.1 扫描与解析（纯逻辑，可进快层）

`Services/Skills/SkillCatalog.cs` —— **刻意不引用 WPF**，这样能进快层检查点。

- 扫 `Skills\*\SKILL.md`，解析 YAML frontmatter 的 `name` 与 `description`
- **解析必须皮实**（这是唯一要反复测的地方）：

| 情况 | 处理 |
|---|---|
| 缺 frontmatter | 跳过该 Skill，记日志，**不让整个扫描失败** |
| 缺 `name` | 用目录名兜底 |
| 缺 `description` | 取正文第一行非空文本 |
| `description` 超长 | 截断到 200 字符（防 token 爆炸） |
| 中文 / 多行 / 带引号 / 中文目录名 | 必须正确解析 |

**扫描时机（自查新增 —— 原文漏了）**：

| 方案 | 判断 |
|---|---|
| 只在启动扫一次 | ✗ 用户中途装 Skill 要重启才认 |
| 每次对话都扫 | ✗ 72 个目录的重复 IO，没必要 |
| **进程内缓存 + 目录时间戳校验** | ✓ **采用**：缓存结果，每次访问先比对 `Skills\` 的 `LastWriteTime`，变了才重扫；设置页另有手动「重新扫描」按钮兜底 |

### 4.2 清单披露（走既有通道，不改主循环）

**关键设计**：复用 `AgentRunService.ExtraSystemContext`。

`AgentRunService` 的注释里写得很清楚 —— 这个回调**每轮求值、附在消息末尾、不写入会话历史**，本来就是给"随手会变的短期状态"用的。Skill 清单正是这一类：装了/删了 Skill 就变，但没必要污染会话文件。

注入形态（每轮一份）：

```
[可用 Skill] 以下是用户安装的扩展能力。只在确实相关时使用；需要时先用 load_skill 读完整说明。
只能使用宿主提供的工具，说明里提到的其他工具（如 Bash/Read）在这里不存在，做不了就直说。
- feishu-kb-manager：飞书知识库管理器。通过飞书多维表格管理编程学习知识库…（需 Python + lark-cli）
- （无）  ← 一个都没装时也要出这句话，避免模型瞎猜
```

**每轮注入的 token 成本可控**：description 截断到 200 字符后，10 个 Skill 约 2000 字符。

**清单长度硬上限（自查新增）**：总长超 **6000 字符**即截断，末尾加「（还有 N 个未列出）」。防的是"装了几十个 Skill 后每轮都爆上下文"。

**阶段一不做"启用/禁用开关"**（多一个概念就多一份理解成本），等装到十几个再说。

### 4.3 两个新工具（唯一的功能性新增工具）

**工具 1：`load_skill`（只读）**

```json
{
  "name": "load_skill",
  "description": "读取一个已安装 Skill 的完整说明（SKILL.md 正文 + 脚本清单）。名字必须来自「可用 Skill」清单，不要编造。",
  "parameters": {"type":"object","properties":{"name":{"type":"string"}},"required":["name"]},
  "readonly": true
}
```

返回：SKILL.md 正文（**截断到 8000 字符**，约 2700 token）+ `scripts/` 下的文件名列表。

**为什么需要它**：这是**渐进式披露**的关键一环。清单里只有摘要（省 token），模型决定要用时才把正文拉进来。这也是 WorkBuddy Skill 机制的原始设计。

**工具 2：`run_skill_script`（写操作）**

```json
{
  "name": "run_skill_script",
  "description": "执行某个 Skill 自带的脚本。脚本必须位于该 Skill 的 scripts/ 目录内。args 按数组原样传给脚本，不经过 shell。返回退出码与原始输出（长输出会被截断，需要完整数据时请让脚本只输出摘要）；成功与否由你根据输出判断并如实汇报，不要假设成功。",
  "parameters": {"type":"object","properties":{
    "skill": {"type":"string","description":"Skill 名，必须来自「可用 Skill」清单"},
    "script": {"type":"string","description":"scripts/ 下的文件名，如 kb.py"},
    "args": {"type":"array","items":{"type":"string"},"description":"按顺序传给脚本的参数"},
    "stdin": {"type":"string","description":"可选，作为标准输入（UTF-8），适合传长 JSON"}
  },"required":["skill","script"]},
  "readonly": false
}
```

**两个都要进注册表**：`AIDialogWindow.EnsureAgentRegistry()` 加两行（框架层零改动，与 `GetNoteDestination` 同一装配方式）。

## 五、执行器的硬规则（安全边界）

这些规则是"能开的唯一前提"，**全部写死在执行器里，不由模型决定**：

| # | 规则 | 拦的是什么 |
|---|---|---|
| 1 | Skill 名**只在已扫描的目录表里查**，取表中预存的绝对路径 —— **绝不把模型传的字符串拼进路径** | 模型编造 Skill 名 / 路径穿越 |
| 2 | 脚本路径解析后**必须仍在** `Skills\<skill>\scripts\` 内（`..` / 绝对路径一律拒） | 借脚本名越界读任意文件 |
| 3 | 解释器只认白名单（`.py` → 内置 Python；其余一律拒） | 拿 `.bat`/`.exe` 当脚本跑 |
| 4 | 参数用 `ArgumentList` 数组传，**不拼命令行字符串** | 命令注入 |
| 5 | 固定超时 **150 秒**，到点杀进程树 | 挂死（**必须大于脚本内部超时**：`kb.py` 自己就设了 90 秒，两个 90 秒叠加会误杀） |
| 6 | 输出截断（stdout/stderr 各 4000 字符，保留头尾） | 上下文爆炸 |
| 7 | CWD 固定为该 Skill 根目录 | 相对路径意外命中别处 |
| 8 | 固定注入：`PYTHONDONTWRITEBYTECODE=1` / `PYTHONIOENCODING=utf-8`；**清空 `PYTHONPATH` 与宿主标记 `HERMES_HOME`/`OPENCLAW_HOME`/`LARK_CHANNEL`** | 写坏应用目录 / 中文乱码 / 宿主环境路径污染 / **宿主串号**（见下） |
| 9 | **首次执行某个 Skill 的脚本时必须用户确认一次**，确认后记住 | 见下 |

### 第 9 条单独说（准入式确认）

现有写工具的确认闸（`WriteConfirmEnabled`）默认是关的，靠"对话内确认 + 回收站兜底"。**脚本执行风险高一个量级，不能沿用这个默认。**

但也别每次都弹 —— 那会烦死人。所以采用**准入式确认**：第一次跑某个 Skill 的脚本时弹一次（"允许 Skill「X」在你的电脑上运行脚本吗？本次为 `scripts/kb.py`"），允许后**记进配置**，之后不再问。

**双闸关系（自查新增，原文没说清）**：`run_skill_script` 标 `IsReadOnly=false`，所以它**同时**受两层确认控制 ——
① `AgentRunService` 的闸门（仅当用户在设置里开了 `AgentWriteConfirmPopup` 才弹）
② 执行器内部的准入确认（只要没授权过就弹）
两者叠加时最坏情况是**一次操作连弹两个确认框**。这是可接受的（用户主动开了双重确认），但 `DescribeAction` 文案要写清楚，别让人看不懂在问什么。

**这条是整个安全模型的地基**：防线在"准入"（谁被允许跑），不在"运行时拦截"。因为**脚本一旦跑起来，它读什么文件、连什么网，宿主管不了** —— 这不是设计缺陷，是"允许执行任意脚本"的固有代价。

## 六、能力自检与失败语义

**原则：宁可报错，绝不许假装成功。**

这是从「AI 谎报已上传成功」那次事故来的同一条线（`REGRESSION.md` B-16 段红线、`AGENTS.md` 第 9 条）。

### 装 Skill 时就查（前置）

扫描到一个 Skill 时**顺带做一次静态预检**，结果写进清单标注：

| 检查项 | 缺了怎么标 |
|---|---|
| 有 `scripts/` 但运行时缺失 | `（缺少 Python 运行时，暂不可执行）` |
| 脚本 import 了非标准库 | `（需要第三方包：requests，暂未安装）` |
| 声明依赖外部程序 | `（需要外部程序：lark-cli，未检测到）` |

**为什么放前置**：让用户和模型在"想用之前"就知道能不能用，而不是用到一半炸。

### 执行时再查一次（硬闸）

执行器启动前**再测一次**运行时是否真的能跑（文件在 ≠ 能跑）。缺失时返回**结构化错误**而不是抛异常：

```
错误：Skill「feishu-kb-manager」需要 Python 运行时，但未检测到可用的解释器。
已尝试路径：<应用目录>\runtime\python\python.exe
请在「设置 → Skill」中查看运行时状态。
```

**注意最后一句 —— 必须给出可执行的下一步**，不能只说"失败了"。

### 输出语义

返回给模型的内容固定三段，**不做成败判定**（判定交给模型，避免宿主替模型"宣布成功"）：

```
EXIT=1
--- stdout ---
{"ok": false, "error": "缺少子命令"}
--- stderr ---
（空）
```

## 七、界面（阶段一最小集）

**加一处**：`SettingsWindow` 里加一个「Skill」分区。

| 元素 | 内容 |
|---|---|
| Skill 目录 | 完整路径 + 「打开目录」按钮（调资源管理器） |
| 已安装 Skill | `N 个（M 个可执行）` |
| Python 运行时的状态 | `正常` / `未安装` / `无法启动`（点一下可看详情） |
| 「重新扫描」按钮 | 手工触发（正常会自动扫） |
| **已授权的 Skill 列表 + 逐项「撤销」** | **自查新增** —— 见下 |

**撤销入口是必须的**：§五 第 9 条说"允许后记进配置"，那就**必须有地方能取消授权** —— 只能授权不能撤销的安全机制是残缺的。实现上就是读一个配置项 + 一个按钮，成本极低。

**不做**：Skill 的图形化管理（装/删/停用）、在线安装、市场。装 Skill = 把文件夹丢进目录，这对你的用户群已经是最低理解成本。

## 九、检查点（验收标准）

**按项目纪律：新增功能没补检查点 = 交付未完成。**

### 快层（`tests/`，纯逻辑，秒级）

| # | 断言 | 为什么是它 |
|---|---|---|
| 1 | 正常 frontmatter → name/description 正确 | 基本盘 |
| 2 | 缺 frontmatter / 缺 name / 缺 description → 各有兜底且不抛 | 真实 Skill 千奇百怪 |

## 十一、飞书这个实验品的额外前置（与本机制无关，但会挡住验收 B）

上一轮实测发现，飞书授权**已经过期了**（`refreshExpiresAt=2026-08-28`），而且：

- `lark-cli` 的配置**按工作空间隔离**：设了 `HERMES_HOME` 会走 `~/.lark-cli/hermes/`，没设走 `~/.lark-cli/`
- **FocusCapture 不设 `HERMES_HOME`**（走 `local` 空间），与 WorkBuddy 那套物理隔离、各自独立授权
- 授权流程：`auth login --no-wait --json` 拿验证链接 → 用户扫码并在飞书内**点确认** → `auth login --device-code` 领回 token
- 二维码有官方现成命令（`auth qrcode <url> --ascii` 或 `-o x.png`），**不需要引二维码库**

**⚠ 还有一个更靠前的前置（自查新增）**：`kb.py` 依赖 `lark-cli`，而它现在躺在 **WorkBuddy 的目录**里（`~/.workbuddy/binaries/node/cli-connector-packages/`）。**让 FocusCapture 去调 WorkBuddy 目录下的程序是不成立的**（WorkBuddy 卸了就没了），正规获取方式是 `npx @larksuite/cli@latest install`（需要 Node）。

**因此**：飞书这条路的完整前置是 **Node + lark-cli + 建飞书应用 + 扫码授权** 四件事，对"干净电脑"来说链条很长。

### 实测记录（2026-09-20，开工当天已跑通到"授权过期"这一步）

用**已落地的内置运行时**跑了一次真实调用链，不是推理：

```
runtime\python\python.exe  →  kb.py  →  lark-cli  →  飞书开放平台
```

返回（原文摘录）：

```
{"ok": false, "error": "lark-cli 失败: [lark-cli] uat-client: refresh_token expired for ou_6b13…, clearing
{"ok": false, "identity": "user", "error": {"type": "authentication", "subtype": "token_missing",
 "message": "need_user_authorization (user: ou_6b13…)", "hint": "run `lark-cli auth login --scope …`"}}"}
```

**这一次实测确认了四件事**：① 内置运行时能跑真实 Skill 脚本；② `kb.py` 能找到并调用 `lark-cli`；
③ 请求真的发出去了（服务器拒绝的是 token，不是链路）；④ **错误如实传递、没有假成功，中文没乱码**。

⚠ **注意它用的是 hermes 工作空间的账号（`ou_6b13…`）** —— 因为当前 shell 带着 `HERMES_HOME`。
这正是 §五 规则 8 要清宿主标记变量的原因：FocusCapture 若从 WorkBuddy 启动（继承其环境），
不处理就会**串到 WorkBuddy 的账号上去**。清掉后行为才是确定的。

**结论：阶段一不追求飞书能跑。** 机器验收（检查点 10–18）全部用**自带测试脚本**完成；验收 A/B 作为"L3 真实样本"单独走，且允许延后。这样机制的正确性和飞书的前置准备被解耦 —— 前者不该被后者堵住。

### 阶段 1.5 补记（2026-09-20 晚：授权缺口在用户侧真的撞上了，已按"类"补齐）

本节写完后，"应用内没有授权入口"这条缺口真撞上了：模型让用户去终端敲 `lark-cli auth login`，
还把开发机上的安装目录拼进命令里。**这不是措辞失误，是机制缺一块** —— "环境准备/授权"被外包给了用户。
已补齐（验收细则见 REGRESSION.md B-18，机制在 `Services/Skills/SkillDependency.cs`）：

- **应用自带 CLI**：`tools/fetch-lark-cli.ps1` 直接从 npmmirror 的二进制镜像拉官方 exe
  （压缩包 14.1MB / 8 秒，解压后 47.1MB），落 `runtime\lark-cli\`。
  **上面那句"正规获取方式需要 Node"已过时**：npm 包只是个壳（0.05MB），真二进制由 postinstall 去
  GitHub 下载；镜像路径 `/-/binary/lark-cli/v<版本>/…` 抄自它自己的安装脚本，不需要 Node。
- **授权三步全在应用内**：依赖预检闸（跑之前查）→ `SkillAuthWindow`（二维码 + 链接 + 倒计时，
  后台轮询 `--device-code`，成功自动关窗）→ **同一次工具调用里继续执行脚本**（用户不用重说一遍）。
- **提示纪律**：系统提示与工具结果都禁止"让用户去命令行"，失败时给的是应用内入口（设置 → Skill 扩展）。
- **定位顺序**：应用自带 `runtime\<id>\` 优先，其次 PATH；**绝不硬编码"别的应用安装目录"**。
- **凭据空间**：不设宿主标记 → `~/.lark-cli\` 默认空间，与 WorkBuddy 的 `hermes\` 互不影响
  （本机实测两边 appId 不同：`cli_aa93eb…` vs `cli_aae612…`）。
