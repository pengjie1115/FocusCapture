绿点 = **「上次测试通过」的记录，不是「现在能用」的保证**。

## 1. 现状 vs 目标

| 维度 | 现状（事实，含位置） | 目标 |
|---|---|---|
| 供应商 | 一个下拉框，作用**只是帮你填 BaseUrl**，本身不存任何状态（`Windows/SettingsWindow.xaml:416`） | 供应商列表卡片，各自独立存 Key / 地址 / 模型 |

### 5.1 供应商状态探测（绿点）

**触发时机（用户拍板）**：

- 进入「AI 模型」板块时，自动并发探测**全部**已配置供应商
- 编辑页保存后，立即探一次该供应商（刚配完立刻有反馈）

**明确不做**：应用启动探测、后台定时探测。

**为什么不做启动探测 / 定时探测**（写在这儿防以后有人"优化"回去）：

- 用户需要绿点准确的时刻，**就是他打开面板看的那一刻**。启动时测的那一次，等他几分钟后打开面板时可能已经变了 —— 花了钱买不到要的东西
- 启动探测 = 应用从「离线可用」变成「启动即发网络请求」，与红线 12 的本地优先精神冲突；6 个供应商就是 6 次真实 API 调用
- 后台定时 = 常驻活动 + 耗电，且**易被安全软件拦**（本项目已有被安全软件拦截的真实事故）

**实现要点**：

- 直接复用现成的 `OpenAICompatibleProvider.TestConnectionAsync`（最小请求 `max_tokens=1`，`OpenAICompatibleProvider.cs:208`）
- `Task.WhenAll` 并发，单个 5s 超时；整批总时长上限 8s
- 探测期间卡片显示「检测中」态，**不阻塞界面**
- **失败绝不弹模态框**（项目铁律：UI 事件里的外部资源操作自己 `try` 住，弹窗会吃掉后续点击）
- UI 更新必须经 `Services/UiThread.AskAsync`（探测跑在线程池线程上）
- 探测失败**不修改任何配置**，只改状态点

**失败分类（必须做）**：

不做分类的后果很具体：**断网时所有供应商一起变红 → 用户以为 Key 全坏了 → 去删配置**。这是本功能最大的坑，比代码本身重要。

| 类型 | 判定依据 | 悬停文案 |
|---|---|---|
| 本机网络不通 | 连接层异常（连不上 host） | 「本机网络不可用，与配置无关」 |
| Key 无效 | HTTP 401 / 403 | 「API Key 未通过验证」 |
| 供应商侧问题 | HTTP 429 / 5xx | 「供应商暂时不可用，稍后重试」 |

**状态语义（UX 铁律）**：状态点是「上次探测结果 + 时间」，**不是「可用」保证**。
悬停必须写「上次检测：通过（2026-09-23 19:40）」，**不得写「可用」**。

## 6. 上下文窗口生效设计

### 6.1 生效规则

**触发点**：三条请求路径（流式 / 带工具 / 非流式）在构造请求体之前的**公共上游**做一次裁剪，避免三处逻辑分叉（本项目已有教训：`BuildMessagesArray` 就是把两套逻辑合并成一处才修掉丢附件的 bug）。

**阈值**：

```
可用预算 = ContextWindow − MaxOutputTokens − 固定开销 − 安全余量
```

- `ContextWindow == 0`（留空）→ **直接跳过裁剪**，保持改造前行为（零回归风险）
- 固定开销 = 系统提示词 + tools 定义 JSON（见坑 C）
- 安全余量 = 20%（见坑 A）

### 6.2 原始两个坑及处理

**坑 A：估算必然不准。**

没有 tokenizer，只能按字符数粗估（中文约 1.5 字符/token，英文约 4）。误差可能 20%+。

→ 处理：**保守系数 + 20% 安全余量**，绝不顶格算。这是该功能天生带的误差，不是能修好的 bug —— 文档里说清楚，别假装精确。

**坑 B：不能把工具调用拆散。**

Agent 开启时会话里存在 `assistant(ToolCallsJson)` + `tool(ToolCallId)` 成对消息。裁剪时丢掉一半 → 接口直接 400。

→ 处理：**裁剪的最小单位是「完整的工具调用单元」**（一条 assistant+tools_calls 连同它后续所有对应 tool 结果，作为不可分割的一组整体丢弃）。这条踩了就是**随机性 400**，很难复现，所以必须有专门检查点。

### 6.3 本次调研新增的四个坑

**坑 C：tools 定义的固定开销不能丢。**

Agent 开启时每次请求都带 tools 定义 JSON（多个工具的 `parameters` schema），轻松几千 token，且**必须保留**。

→ 处理：把它算进「固定开销」从预算里先扣掉。不计入 = 以为还能塞，实际超窗口。

**坑 D：图片的 token 不按字符算。**

图片以 base64 塞进 `content`，字符串几万字符，但供应商按**图像分辨率**折算 token（一张 1568px 的图约 1000~2000 token）。

→ 处理：**字符估算法对图片彻底失效**，每张图给一个固定估算值（与现有「图片清晰度」档位挂钩：省流 768 / 标准 1568 / 高清 2048 三档各一个值）。这是实际必须处理的，因为本项目明确支持图片附件。

**坑 E：裁剪是隐形的，用户看不见。**

界面上历史消息一条不少，发给模型的却少了几条 → 表现是「AI 明明上面看到了怎么不记得」。**用户永远查不出原因**，只会认为 AI 变笨了。

→ 处理：裁剪真的发生时，界面上给轻提示：「已达上下文上限，最早的 N 条本轮不再发送」。属体验坑，但不处理会变成投诉。

**坑 F：单条消息本身就超窗口。**

用户塞进来一个巨大文档附件，裁剪历史完全无效。

→ 处理：识别这种情况，**拒绝发送 + 人话提示**（「这条内容太大了，超过模型能装下的上限」），不许让它去撞 400 英文报错。

### 6.4 tokenizer：能不能自己做？

**结论：能做，但不建议做。**

| 方案 | 可行性 | 判定 |
|---|---|---|
| 内置词表 + 实现 BPE | 技术上可行。C# 有 SharpToken / TiktokenSharp 这类库 | **不做** |
| 用 OpenAI 词表近似国内模型 | `cl100k_base` 约 1.7MB / `o200k_base` 约 3.5MB。可近似，但中文分词粒度与 DeepSeek / GLM / Qwen 自研 tokenizer 不一致 | 收益有限 |

三条否决理由：

1. **词表是「一模型一份」，不是「一套通吃」**。DeepSeek、GLM、Qwen 都是自研 tokenizer，不是标准 tiktoken 格式，得自己转 + 每个新模型补一份。
2. **我们的模型列表是用户自己填的模型 ID**，无法预知要带哪些词表 —— 永远追不上。
3. **收益不足以覆盖成本**：判断（非事实），中文场景下从 ±25% 降到 ±15%，对「要不要裁剪」这个决策帮助有限 —— 因为无论多准都还得留安全余量。

**推荐替代：自校准（比任何词表都准）。**

供应商每次响应都会返回真实 `usage.prompt_tokens`。拿到真实值后反算「本次字符数 → 实际 token」的比率，存起来给下次用。用的是供应商自己的真实数字，零依赖、零包体、跨供应商自适应。

**但自校准自己带风险（必须说清）**：

| 风险 | 说明 |
|---|---|
| 需要新增请求字段 | 流式要返回 usage 得带 `stream_options: {"include_usage": true}` |
| 兼容性未知 | **不是所有 OpenAI 兼容节点都支持**，有的会直接 400 |
| 降级要求 | 必须做成「带了失败就退回不带」，且失败不许影响正常问答 |
| **需实机验证** | 本机无法验证各供应商支不支持 —— 属于「自动化证明不了」的类别 |

→ **处理：自校准后置到第二期**，不跟主改造捆在一起。理由：主改造本身已经很大（数据结构 + 界面 + 迁移），再塞一个需要实机逐个供应商验证的东西，出问题无法归因。

### 6.5 本期范围（三层）

| 层 | 内容 | 本期 |
|---|---|---|
| **L1** | 保守估算 + 20% 余量 + 留空不裁剪 + 坑 B/C/D/E/F 全处理 | **做** |
| **L2** | 自校准（`stream_options` 反算真实比率） | 第二期，独立提交 |
| **L3** | 内置词表 | 不做 |

**理由**：L1 已经让「上下文窗口」**真生效**（满足用户「做了就要生效」的要求），且零外部依赖；L2 是精度优化，且必须先实机摸清供应商兼容性。

## 7. 老配置迁移（最高风险项）

用户现有配置：`AiBaseUrl` + `AiApiKey` + `AiModel` + `AiMaxTokens` 四个扁平字段。
**升级后必须自动可用，不许丢 Key。**

**迁移规则**：

1. `AiModelProviders` 为空 **且** 旧字段有内容 → 生成一条供应商
   - `Name` = `AiProviders.MatchByUrl(AiBaseUrl)?.Name ?? "自定义"`
   - `BaseUrl` / `ApiKey` 直搬
   - `Models` = 旧 `AiModel` 非空则建一条（`Id` = 原名，`DisplayName` = 原名，`MaxOutputTokens` = 旧 `AiMaxTokens`）
   - `ActiveModelKey` 指向它
2. **幂等**：已有 `AiModelProviders` 就完全不动（防重复迁移）
3. 旧字段**保留在 JSON 里不删**（回退旧版本仍可用），新代码不再读
4. **保命回退**：迁移过程 `try` 住，异常时回退到「直接读旧字段」路径，保证 AI 不至于因迁移失败而不可用

## 12. 供应商 /models 端点调研结论（2026-09-23，子 Agent 并行完成）

> 完整报告：`docs/2026-09-23-供应商models端点调研.md`（311 行，逐家标注来源分级）。
> 这次调研是**并行派发**的：它零文件冲突、且是后续实现的真前置，符合「能并行的才并行」原则。

### 12.1 对原设计的 3 处修正

**修正 1：自动回填「上下文窗口」不是主路径 —— 原 §6.4 的期待过于乐观**

| 供应商 | 能否从 `/models` 拿到窗口 |
|---|---|
| Kimi | ✅ `context_length`（官方文档明确保证） |
| DeepSeek | ❌ |
| 智谱 GLM | ❌（元素只有 `id` + `object`） |
| 通义千问 | ❌（推测） |
| 腾讯混元（旧域名） | ❌ |
| 腾讯 TokenHub | ❌ |
| Agnes | ⚠️ 无官方证据（**却是本项目主力供应商**） |

→ **7 家里只有 1 家拿得到。** 窗口仍以用户手填为主，「获取可用模型」时能拿就拿 —— 是顺带收益，**不是承诺**。
这一条反过来印证了当初的决策是对的：「不预填猜测值、留空即不限制」。若当初把「自动回填」当必要条件，这功能就是个坑。

**修正 2：失败分类从 3 类扩到 4 类 —— 「账户/余额」必须单列**

调研挖出的实测事实（专坑用户的那种）：

- **智谱把「欠费」放在 HTTP 429 里**（错误码 `1113`）
- DeepSeek 余额不足用 **`402`**

按原设计「429/5xx = 供应商暂时不可用，稍后重试」，用户会对着「欠费」反复重试 —— **永远重试不好，而且我们还在骗他「稍后重试」**。

新增第 4 类（§5.1 那张表补一行）：

| 类型 | 判定 | 文案 |
|---|---|---|
| 账户/余额 | HTTP `402`；或 429 且错误码 ∈ {1113, 1302, 1305, 1308, 1309, 1311, 1313} | 「账户余额不足或套餐到期，请到供应商后台充值/续订」 |

**修正 3：腾讯拆成两个预置项 + 显示名可自动回填**

- 腾讯正在把模型服务迁到 **TokenHub**。旧域名 `api.hunyuan.cloud.tencent.com` 仍可用，但**两套响应结构不同**
  → 预置表拆两行（旧域名 / TokenHub），避免用户填了 TokenHub 地址却按旧结构解析
- TokenHub 返回 **`name`** 字段（展示名）+ `status`（`online` / `pre-offline`）
  → **显示名可以自动回填**，用户不必手填。这是本次调研的意外收获。

### 12.2 解析侧宽容策略（`AiProviderFetcher` 的实现依据）

各字段的异构情况：`id`（必有）/ `object` / `created` / `owned_by` / `name`（TokenHub）/ `status`（TokenHub）/ `context_length`（Kimi）/ `supports_*`（Kimi）

实现约定：

1. **顶层容器**：依次尝试 `data` → `models`，取第一个是数组的
2. **模型 id**：依次尝试 `id` → `name` → `model`
3. **显示名**：优先 `name`（TokenHub 有），否则用 id
4. **窗口**：依次尝试 `context_length` → `context_window` → `max_context_length` → `max_input_tokens`，取第一个能转成正整数的；**全都拿不到就留空**（不猜，与决策 #6 一致）
5. **下线模型**：有 `status` 且不是 `online` 的（如 `pre-offline`）默认**不勾选**，但**不隐藏** —— 用户可能仍要用
6. **错误体解析必须宽容**：**可能是纯文本**（DeepSeek），也可能是 JSON。解析不出结构时**直接截断展示原文**，绝不因为解析失败就把错误吞掉（吞掉 = 用户只看到「失败」两个字，无从下手）
7. **无分页**：6 家都不需要翻页，不做分页逻辑

### 12.3 检查点分层（原 §9.2 未指明层，此处按实际落地补上）

分两层放，判据是项目既有惯例「**能不能零项目依赖**」：

| 层 | 放什么 | 实际条数 |
|---|---|---|
| **快层** `tests/`（128 条，秒级，每次改动都跑） | `TokenCountParser`（`384K`/`1M` 解析）—— 刻意零项目依赖，够格进快层 | **+15 条**（组 `[13]`） |
| **慢层** `tests/sync/`（458 条） | 迁移、三级解析、源生成 JSON、`max_tokens` 规则 —— 都要碰 `AppSettings` / `AppLog` / `FocusPaths` | **+24 条**（组「AI 模型配置」） |

**为什么这两类必须分层**（有实证）：

- 慢层工程用 `ProjectReference` 引主项目，能直接断言 `AppSettings` / `AiModelResolver` / `OpenAICompatibleProvider`
- 快层工程**刻意不引主项目**（只链接零依赖源文件，保秒级编译），其 csproj 注释明写「**被测类不得依赖项目内其他类，否则编译报错**」。本次新增的配置类三个都依赖 `AppLog` / `AppSettings` / `FocusPaths` → **不具备进快层的条件**
- 所以 **`AppSettings` 变更不影响快层**（它没链接 `AppSettings`）；但 `TokenCountParser` 是纯字符串处理 → **应该进快层**（理由同 `SkillCatalog`：解析是最需要反复测的部分）

> 原 §9.2 把 8~11 条全部当作一层，实际落地按依赖拆成 15 + 24 = 39 条。
> 条数比原计划多，因为写的时候发现「三级解析回退」的每一级都值得单独立条（断哪一级的表现都是静默的）。
