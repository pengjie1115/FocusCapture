# 云端核对方案实施清单（2026-09-27）

> 分支：`experiment/baidu-listall-verify`
> 状态：**已实施完成**（2026-09-27）。接口实机验证结论见 `docs/2026-09-27-云端核对验证报告.md`；
> 本文 §5.2 的判定规则已按那次实测**修正并落地**（见该节注记）。
> 已落地：`CloudVerify`（纯函数）+ `CloudVerifyService`（编排）+ `CloudStates.Missing` +
> `BaiduNetdiskClient.ListAllAsync` + 设置页「与云端核对」入口 + `CloudVerifyWindow`（报告与清理出口）。
> 一句话目标：**让本地元数据尽量贴近云端真相** —— 堵住「Agent 说文件还在、其实用户在网盘里已经删了」这条失真。

---

## 0. 边界（用户已拍板，不可越界）

| # | 边界 | 理由 |
|---|---|---|
| 1 | **只做状态修正，绝不做条目新增** | 多设备靠既有元数据同步（`FileStoreSync.Merge` 按 id 求并集）自行收敛；反向核对再塞新条目会和同步来的那条撞 id / 重复 |
| 2 | **全程不下载、不上传、不修改任何文件本体** | 核对只读云端目录清单，对文件零操作 |
| 3 | **不自动、不后台定时跑** | 见 §9 限流；由用户在设置页手动触发，带冷却期 |
| 4 | **核对结论只能是「疑似缺失」，不能是「已删除」** | 匹配键（路径）本身不保证可靠，见 §5 |

## 1. 现状（已核实，2026-09-27）

| 事实 | 位置 |
|---|---|
| 元数据**只增不减**：删除只打墓碑 `Deleted=true`，记录保留 | `Services/Files/FileRepository.cs:660-671` |
| 多设备合并 = 按 id 求并集，不存在冲突 | `Services/Sync/FileStoreSync.cs:98-135` |
| `find_cloud_files` **纯离线**，只读本地元数据 | `Services/Agent/FileTools.cs:262-312` |
| 每行末尾的状态来自**本机账本** `CacheEntry.UploadState`，含义是"我们这边传成功过没有"，**不是"云端此刻还在不在"** | `Services/Files/FileModels.cs:140-161` |
| **全项目没有任何一处把云端实际文件与本地元数据做过比对** | 已穷搜确认 |
| 唯一边缘接触点：取回失败时返回一句提示，**不更新任何状态** | `Services/Files/FileRepository.cs:440` |

**结论**：用户手动在网盘删除文件后，本机完全不知情，`find_cloud_files` 仍可能标着「云端已就绪」→ Agent 据此说错话。本方案就是补这一环。

## 2. 核心接口：`listall`（递归获取文件列表）

```
GET https://pan.baidu.com/rest/2.0/xpan/multimedia?method=listall
      &path=/apps/FocusCapture
      &recursion=1        ← 关键：递归，子目录一起返回
      &start=0&limit=1000
```

| 项 | 官方口径（2026-09-02 版文档） |
|---|---|
| 目录限制 | **仅支持 `/apps/{appname}`** —— 正好是沙箱，够用 |
| 返回字段 | `list[].path`（**完整路径**）、`server_filename`、`size`、`isdir`、`md5`、`server_mtime` |
| 递归 | `recursion=1` 覆盖所有子目录 → **按月分目录不再是负担** |
| 分页 | `has_more=1` 时用响应里的 `cursor` 作下次 `start`（**不要自行累加固定步长**） |
| 限流 | 错误码 **31034**；官方原文"listall 接口请求频率建议不超过每分钟 8–10 次" |
| md5 | ⚠️ 官方两处均注明"**云端哈希值，非文件真实 MD5**" → **不可用于内容比对** |

**调用次数对比**（这是本方案相对"逐目录列"的核心优势）：

| 方案 | 攒 12 个月附件时 | 结论 |
|---|---|---|
| 普通 `list` 逐目录 | 14 次（files 1 + attachments 1 + 逐月 12） | 易撞限流 |
| **`listall` + `recursion=1`** | **1 次**（≤1000 文件），超出每千条 +1 | 可接受 |

基座已具备：`BaiduNetdiskClient` 已定义 `XpanMultimediaUrl` 常量（现用于下载直链 `filemetas`），加本接口只是同 URL 上加一个方法。

## 3. 数据流

```
[设置页] 「与云端核对」按钮
        ↓ 前置检查：已授权 + 元数据首轮同步完成 + 过冷却期
[服务]  CloudVerifyService.RunAsync()
        ↓ ① 拉云端：ListAllAsync(NetRoot, recursion=1) → List<CloudEntry>
        ↓ ② 取本地：FileRepository.AllMetadata(includeDeleted:true) + 逐条 FindCache 里账本
        ↓ ③ 比对：CloudVerify.Compare(...)  ← 纯函数，检查点直接覆盖
        ↓ ④ 报告：差异清单（脱敏）→ 报告窗口
[用户]  确认「应用标注」
        ↓ ⑤ 写回：FileRepository.MarkCloudMissing(id) / MarkCloudOk(id)（只改 CloudState）
        ↓ ⑥ 记录核对时刻（AppSettings.CloudVerifyAt）
```

## 5. 比对算法（纯函数，`CloudVerify.Compare`）

### 5.1 匹配键
以 **`NetPath` 规范化后字符串相等**为准：两侧 `TrimEnd('/')`，**大小写敏感**（百度路径大小写敏感）。

> ⚠️ 不用 md5：官方明说它不是文件真实 MD5。md5 只在报告里作"可能同内容"的弱提示，**绝不参与判定**。

### 5.2 本地侧逐条判定

| 条件 | 判定 |
|---|---|
| `Deleted == true`（墓碑） | **跳过** —— 用户已彻底删除，我们已主动删过云端 |
| `CloudState == Expired` | **跳过** —— 如期清理，云端本就该没有 |
| `CloudState == CleanupPending` | **跳过** —— 正在补删，交给清理器 |
| 路径在云端清单里命中 | → `Ok`（若原为 `Missing`，则**撤销标注**） |
| 路径未命中 + 本机账本 `UploadState == Uploaded` | → **`Missing`**（曾验证传成功、现在云端没了）|
| 路径未命中 + 本机账本 `UploadState ∈ {Pending, Uploading, Failed}` | **不标注** —— 还没传上去，云端本该没有 |
| 路径未命中 + 本机**无账本条目** + 记录创建时间**早于安全窗口**（建议 1 小时） | → **`Missing`**（本机登记过、云端没有，且不是同步中间态）|
| 路径未命中 + 本机**无账本条目** + 记录**很新**（在安全窗口内） | **不标注** —— 可能是"他端刚上传、元数据先到、云端还在传" |

> ⚠️ **上面这两行是 2026-09-27 实机验证后修正的**（证据见 `docs/2026-09-27-云端核对验证报告.md` §四）。
>
> 原规则是「**无账本条目 → 一律不标注**」，理由是"记录应是别端同步来的"。**实测推翻了这条假设**：
> 本机账本只有 10 条、元数据却有 29 条，差额里的 17 条是**本机历史上登记过、但账本条目已被本地缓存淘汰逻辑
> （`FileRepository.DropLocal` 会连带 `_ledger.Remove`）一并移除**的记录 —— 它们既不在上传队列、云端也不存在，
> 恰恰是失真的主体（占活跃记录 61%）。按原规则，这批永久得不到标注，等于白做。
>
> 修正思路：用**时间窗口**而非**账本证据**来防误报 —— 既堵住失真，又不误伤"刚发生的同步中间态"。

### 5.3 云端侧

云端清单里有、本地元数据按路径**找不到任何记录**（含墓碑）→ 归入**「云端多出」报告**。

**只报告，绝不入账**（边界 1）。报告话术要说明：可能是另一台设备刚上传、元数据还在同步路上；也可能是你手动放进网盘的。

## 6. 状态与字段

- **新增状态**：`CloudStates.Missing = "missing"`，`Label` → 「云端已不存在」。
- **不新增字段**：复用现有 `CloudState`（它是 string，旧版本客户端会原样保留，不崩 —— 符合"只增不改"）。
- **最后核对时间**：`AppSettings.CloudVerifyAt`，本机事实，**不进元数据、不参与同步**。
- **撤销时机**：① 下次核对命中云端；② 该文件重传成功（改动 8）。
- **UI 落点**：「设置 → 文件与网盘」，与既有「重试云端清理」「测试连接」并列；核对结果用只读报告窗口，用户点「应用标注」才写回。

## 7. 检查点设计（不联网，红线：自动化检查点不得联网）

`CloudVerify.Compare` 是纯函数，用**内存构造的假云清单**覆盖以下场景：

| 场景 | 期望 |
|---|---|
| 本地有 + 云端有 | 不标注（或撤销 `Missing`） |
| 本地有 + 云端无 + 账本 `Uploaded` | → `Missing` |
| 本地有 + 云端无 + 账本 `Pending` | 不标注 |
| 本地有 + 云端无 + 无账本条目（他端记录） | 不标注 |
| 墓碑记录 | 跳过 |
| `CloudState == Expired` | 跳过 |
| `CloudState == CleanupPending` | 跳过 |
| 云端有 + 本地无 | 计入「云端多出」报告，**元数据不变** |
| 路径尾部 `/` 差异 | 规范化后视为命中 |
| 路径大小写不同 | 视为**不**命中（大小写敏感） |
| 本机记录重传成功后再核对 | `Missing` 被撤销 |

另需覆盖：`FileToolSupport.Describe` 在 `Missing` 时输出"云端已不存在"（防 Agent 说错话的回归闸）。

## 9. 限流与风险对策

| 风险 | 对策 |
|---|---|
| 官方两个口径矛盾：配额页「未审核应用 10 次/每小时」 vs listall 文档「每分钟 8–10 次」 | 本方案一轮只花 **1 次**调用，**无论按哪个口径都撞不到**；实现时仍接 31034 退避 |
| 用户连点核对 | 冷却期（建议 ≥10 分钟）+ 运行中禁点 |
| 核对与上传/清理并发 | 共享同一把闸，避免基于中间态误判 |
| 元数据首轮同步未完成时核对 | 复用 `FileStoreSync.InitialPullCompleted` 判断，未完成不许核对（否则把"还没同步"误报成"云端多出"） |
| 结论过期 | 报告与状态区展示「最后核对于 X」，让用户和 Agent 都知道新鲜度 |
