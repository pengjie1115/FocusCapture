## 三、逐项验证结果（V1~V6）

### V1 `listall` 能否用现有令牌调通 —— ✅ 通过

```
[INFO] AppKey=ZDrM****  令牌到期=2026-10-23 10:42  有效=True
[INFO] 沙箱根=/apps/FocusCapture
[结果] 条目=23  调用次数=1  耗时=737ms  errno=0
```

`errno=0`，一次调用返回全部 23 个条目。**接口可用、权限正常。**

### V2 `path` 与本地 `NetPath` 口径是否一致 —— ✅ 通过（这是最关键的一项）

`compare` 结果中 **命中（本地有·云端有）= 11 条**。

路径匹配是**严格字符串相等**（仅 `TrimEnd('/')`，大小写敏感）。能命中 11 条，说明云端返回的：

```
/apps/FocusCapture/files/***.pdf
/apps/FocusCapture/attachments/2026-09/***.jpg
```

与本地 `FileRepository.BuildNetPath` 产出的 `NetPath` **口径完全一致**（含中文字符、URL 未额外编码）。**整套比对算法的地基成立。**

```
--- 字段可用性清点 ---
    path=23/23  server_filename=23/23  md5=20/23  server_mtime=23/23
```

`path` 字段 **23/23 全部返回**，无一缺失。

### V3 `recursion=1` 是否覆盖 `attachments/YYYY-MM` —— ✅ 通过

```
--- 按相对路径分组 ---
    分组 files                  共  11 项（文件 10）
    分组 attachments/2026-09    共  10 项（文件 9）
    分组 attachments            共   2 项（文件 1）
```

月份子目录 `attachments/2026-09` 的 10 个条目**被递归一次性带出**，且路径带完整月份前缀。

**结论：按月分目录的机制完全不需要改动**，它在递归清单里只是一个普通路径层级。

### V4 耗时与限流 —— ✅ 通过

| 轮次 | 调用次数 | 耗时 | 结果 |
|---|---|---|---|
| listall #1 | 1 | 831ms | errno=0 |
| listall #2 | 1 | 737ms | errno=0 |
| compare（含 listall） | 1 | 1062ms | errno=0 |

全程 **无 31034、无 20012**。总计 3 次调用（低于任一限流口径）。对比"逐目录列"方案（files 1 + attachments 1 + 逐月 N），**单轮调用数从十几次压到 1 次**。

### V5 云端 `md5` 与本地内容 MD5 是否相等 —— ❌ 不相等（重要）

```
--- V5：云端 md5 与本地内容 MD5 实测 ---
    可比对 11 条，相等 0 条  →  实测不一致
```

**11 条样本全部不等**。本地 `FileMetadata.Md5` 是真实文件内容 MD5（`MD5.HashData`），云端返回的是另一种哈希。

**判定：`md5` 绝不能用作内容比对键**，实施清单 §5.1「以 `NetPath` 为唯一匹配键」的判断**得到实证支持**。

### V6 `has_more` / `cursor` 翻页 —— ⚠️ 未触发（数据量不足）

当前仅 23 个条目（< 1000），一轮即取完，翻页分支**未被真实数据覆盖**。翻页逻辑按官方"用响应 `cursor` 作下次 `start`"实现，但**缺少实机证据**，属未验证项（见 §六）。

## 四、意外发现：本地元数据**已经**与云端明显脱节

`compare` 的完整结果：

```
[云端] 条目=23  其中文件=20
[本地] 元数据记录=29（含墓碑）

    命中（本地有·云端有）                : 11
    ▶ 疑似缺失（本地有·云端无·账本已上传） : 0
    跳过·墓碑                            : 1
    跳过·云端已到期清理                   : 0
    跳过·云端待清理                       : 0
    跳过·还没传上去                       : 0
    跳过·他端记录（本机无账本证据）         : 17   ← 问题在这里
    ▶ 云端多出（只报告、不入账）           : 9
```

### 4.1 关键事实

| 观察 | 数据 |
|---|---|
| 本地元数据活跃记录 | 28 条（另 1 条墓碑） |
| 其中**云端实际存在** | 11 条（39%） |
| 其中**云端不存在、但本机账本也查不到记录** | **17 条（61%）** |
| 云端存在、**本地元数据完全无记录** | 9 条 |

**这 17 条正是你最初担心的失真**：`find_cloud_files` 会把这些记录返回给 Agent，而它们**在网盘上并不存在**。Agent 若据此回答"这个文件在网盘上、可以取回"，就是在说假话 —— 用户实际取回时会失败。

**而且这 17 条恰好落在清单 §5.2 的盲区**：

> 原规则：「路径未命中 + 本机**无账本条目** → 不标注 —— 记录是从他端同步来的，本机没有"传成功过"的证据，不足以定论」

实测表明："无账本条目"**并不等于**"他端同步来的"。本机账本只有 10 条，而元数据有 29 条 —— 差额 19 条里，绝大多数是**本机历史上登记过、但账本条目已消失**的记录（本机账本 `files_ledger.json` 曾被本地缓存淘汰逻辑清理：`FileRepository.DropLocal` 会连同账本条目一起移除）。

按原规则，这 17 条**永远得不到标注**，失真正好完整保留。**规则必须修正。**

### 4.2 另一个发现：`NetPath` 是**不稳定键**

`FileRepository.BuildNetPath` 的后缀由 `ShortId` 生成，而 `ShortId` 内含 `Guid.NewGuid()`：

```csharp
var hash = SHA256.HashData(Encoding.UTF8.GetBytes(seed + "|" + Guid.NewGuid().ToString("N")[..4]));
return Convert.ToHexString(hash)[..8].ToLowerInvariant();
```

**同一文件名每次登记都会得到不同的路径后缀。** 这解释了"云端多出 9 条"的成因之一：云端存在历史路径版本的文件，而本地记录已被替换/清空，两边按路径对不上。

> 注意：`Guid.NewGuid()` 也意味着**"同内容同 id → 同路径"这条注释与实现不符** —— 内容 id 相同（MD5 查重会拦住常规路径），但 `ShortId(displayName)` 每次不同。这是既有实现的既有行为，**本次不主张改动**（它不影响核对方案的可行性，路径匹配对"登记后未变的记录"依然稳定），但值得记为已知风险。

## 五、对实施清单的修正

### 修正 1（必需）：§5.2 的"无账本证据 → 不标注"改为分级处理

原规则过于保守，会把失真主体漏掉。建议改为：

| 条件 | 判定 |
|---|---|
| 路径未命中 + 账本 `Uploaded` | → `Missing`（不变） |
| 路径未命中 + 账本 ∈ {Pending, Uploading, Failed} | 不标注（不变，确实还没传上去） |
| 路径未命中 + **无账本条目 + 记录创建时间早于安全窗口（如 1 小时前）** | → **`Missing`**（新增：本机登记过、云端没有、且不是刚发生的同步中间态） |
| 路径未命中 + 无账本条目 + 记录**很新** | 不标注（防"他端刚上传、元数据先到、云端还在传"的误报） |

**理由**：核对的目的就是"本地记录 vs 云端真相"，云端没有就是没有。用"时间窗口"替代"账本证据"来防误报，既堵住失真，又不误伤同步中间态。

### 修正 2（建议）：`CloudState` 增加区分

建议 `Missing` 之外再列一个**内部子类**（或报告里单列）用于"无账本证据的缺失"，便于用户区分：
- 「云端已不存在（曾上传成功）」
- 「云端从未存在（登记后未上传成功）」

两者对用户的意义不同（前者是"被删了"，后者是"根本没传上去"）。

### 修正 3（建议）：报告里单列「云端多出」

9 条"云端多出"目前无法自动归因（他端 / 手动放入 / 历史路径遗留）。报告窗口应**原样列出并标注不确定**，且明确"不会自动入账"。

## 六、剩余风险与未验证项

| # | 未验证 / 风险 | 影响 |
|---|---|---|
| 1 | **翻页未实测**（V6） | 文件数 >1000 时的 `cursor` 行为无实机证据；上线前应构造 >1000 文件或复用官方示例验证 |
| 2 | **应用是否已过上线审核未知** | 官方两个限流口径矛盾（"10 次/每小时" vs "每分钟 8–10 次"）。本方案一轮仅 1 次调用，按任何口径都安全，但**建议向用户确认应用状态** |
| 3 | **他端记录无法甄别** | 多设备场景下，本机无法知道"某条元数据记录是本来就没传成功，还是云端被删了"—— 修正 1 的时间窗口只能降低误报，不能根除 |
| 4 | **核对结论会过期** | 标注只反映"核对那一刻"；`AppSettings.CloudVerifyAt` 只解决"新鲜度可见"，不解决正确性 |
| 5 | **`ShortId` 带 Guid** | 路径不稳定，长期看会累积"云端多出"。不在本方案范围内，但应记入已知问题 |
| 6 | **未做并发闸验证** | 与上传队列/清理器的互斥尚未实测 |
