## 4.2 P1–P8 互相冲突吗？（用户提问，2026-09-25 17:15）

**结论：8 项里 3 处真冲突、2 处顺序依赖、1 处收益重叠，其余无关。真冲突全是「新方案 vs 现有红线」，不是方案之间打架。**

### 真冲突一：P7 ↔ AGENTS.md 红线 6「红不许瞒」

| | |
|---|---|
| 红线 6 | 检查点红了宁可挂着，**不许 AI 自行判定**「这算需求变更」 |
| P7 | 确认为环境 / 时序问题 → **打标隔离出关键路径** |
| 为什么冲突 | 两者都是「红了之后怎么办」的规则，而 P7 给了 AI 一个**自我豁免的口子**。Google 敢自动隔离是因为量大且有人专职看；单人项目自动隔离 = 门禁可以自己给自己开绿灯 |

**修法（三选一）**：① 不做 P7；② 隔离**必须用户确认 + 留痕 + 设 TTL**（到期自动回到关键路径，逼着处理）；③ 仅在「这条在本次改动前后都红、且与改动文件无交集」时才自动隔离，且隔离记录写进 REGRESSION。**推荐 ②。**

### 真冲突二：P8 ↔ AGENTS.md 红线 5「新增功能没补检查点 = 交付未完成」

P8 的 L0 / L1 定义就是「某些改动可以不补检查点」→ 与红线 5 正面冲突。**不显式改红线 5，P8 就只是给 AI 放水的口子**（跟冲突一同一个病）。

### 顺序依赖一：P5 是 P1 的规格来源（不冲突，但不能只做 P1）

- P1 是「把违规的搬走」（一次性动作）；P5 是「以后不许再违规」（机制）。

## 7. 附录

### 7.1 关于「早发现 vs 晚发现」的账（回答问题 2）

**结论：按触发条件分层，不会牺牲发现时机。** 推理链：

1. 早发现的收益 = **后续步骤与该 bug 的耦合程度**。
2. 改 UI / 文案时，慢层里的同步、加密、删除检查点**在原理上不可能红** → 跑它抓到的 bug 数是零，它不是「更早发现」，只是让**同一批验证重复做了 N 次**。
3. 真正会出现「带着 bug 继续改」的场景，是后面的改动**依赖**前面引入的 bug（改数据结构、改同步协议）。而这**本来就命中触发表** → 慢层会被跑 → 不漏。
4. 修复成本对比：当场修（代码还在脑子里）vs 合并时修（要重建上下文），我判断 3-5 倍差距。但**合并前那次全量是必须跑的，不会取消** —— 合并不是「第一次发现点」，它是最后一道闸。
5. **用户担心的那个风险是真的，但缺口不在跑不跑，在触发表本身**：它现在是手写关键词列表，会腐化。洞要用 P6 补。
