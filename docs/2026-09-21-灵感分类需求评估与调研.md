## 0. 一句话结论

需求可行，但提出的三个方案里**两个方向选偏了**；而真正可行的那条路，**代码里已经铺好一半**。

1. **「创建时前置分类」解决错了问题** —— 你想要的「一步上传今天做过的事」，代码已支持"不勾选 = 传当前筛选结果"，**只差一个「今天」筛选档**。加前置分类等于为一个已能解决的问题，给灵感捕获加上永久摩擦。**【事实】**
2. **「AI 自动分类」在现有数据上会漂移** —— 一条灵感只有「时间戳 + 一句话 + 来源窗口」，语义信号极弱；不确定标签集就必然漂移。**规则必须由用户定，不能由模型定**（行业共识，见 §5.3）。**【判断】+【外部共识】**
3. **「行级标签」是唯一低成本路线，而且通道已经存在** —— `SyncNote.Tags` 是现成的、加密同步的、**不参与行 ID** 的元数据字段。**【事实】**

## 1. 需求拆解：这其实是两件事

| | 需求 A：批量操作 | 需求 B：长期管理 |
|---|---|---|
| 原话 | 「分类好以后，今天做的事一步上传」 | 「方便我进行其他操作，也方便管理」 |
| 真实瓶颈 | 挑不出「今天做过的事」 | 内容没有结构，事后找不到 |
| 正确解法 | **筛选维度**（时间 / 类型 / 来源） | **分类体系**（组 / 标签） |
| 代价 | 极低，一个筛选档 | 中高，要定粒度 + 长期维护 |
| 需要分类吗 | **不需要** | 需要 |

**关键点**：A 的收益被错挂在了 B 的解法上。实际因果是「先筛选 → 就能一步上传」，不是「先分类 → 才能一步上传」。
分类只是筛选的**其中一种维度**，而时间 / 类型 / 来源这三个维度是**零成本自动获得**的。

## 3. 三个硬约束

### 3.1 分类信息不能写进正文行内 【事实 + 判断】

- 行 ID = `SHA256(完整行文本)` 前 16 字节，**相对路径不参与**：`Models/SyncNote.cs:64-68`
- `Services/NoteService.cs:366-372` 注释原文：「原地替换 = 旧文本消失，而行身份是 SHA256(行文本)，改行等于『删旧行 + 加新行』」

**【判断】** 把标签写进正文 → 每次改分类 = 一次删 + 加。后果：进回收站、云端发墓碑、跨端可能短时双条。
不是不能用，是**成本被低估了** —— 改分类的心理成本应该是"改个字段"，不是"删掉重记一遍"。

### 3.2 `Tags` 目前是文件名的投影，不是独立来源 【事实，本轮最关键】

- 上传方向：`Tags ← entry.Tag ← 文件名`（`SyncEngine.cs:567`）
- 拉取方向：`文件名 ← Tags[0]`（`SyncEngine.cs:891-892`）

→ 双向都是「文件名 ↔ `Tags[0]`」的镜像。

**【判断】** 只把 `Tags` 改成多元素是不够的 —— **下一次 push 会被文件名覆盖回单值**。
要支持多标签，必须给 `Tags` 一个**独立持久化来源**（sidecar 索引 / 独立字段文件 / 行内标记三选一），否则"支持多标签"是假功能。

### 3.3 上传去重指纹不含分类 【事实】

`GetNoteSyncState.Fingerprint` = `MD5(时间戳到分 | 类型 | 内容后4位)`。
→ 改分类后再点上传**会被跳过**。
**【判断】** 若希望"改了分类就更新云端那条"，需二选一：把分类纳入指纹（引入新的重复风险），或提供「强制重推」入口。

### 3.4 待验证项（不拍脑袋）

| # | 待验证 | 为什么重要 | 怎么验 |
|---|---|---|---|
| V1 | 跨文件移动一条行（行文本不变）**会不会误发墓碑** | 若会 → 方案 B / 3.2 的 Tags 独立化都有坑 | `dev.ps1 test -Slow` 的「行身份」组 + 手工双设备模拟 |
| V2 | 改 `Tags` 后云端 PUT 是覆盖同 ID 还是新增 | 决定"改分类"是否真的零抖动 | 同上 |
| V3 | `Tags[0]` 为空的存量行落到哪个文件 | 影响多标签时的兜底 | `SyncEngine.cs:891` 附近分支实测 |

**【判断】V1 / V2 至少先跑通一个，再动 §6 的方案 B / C。**

## 4. 想法逐条体检

| 你的想法 | 判断 | 原因 |
|---|---|---|
| 输入框加「前置分类选项」 | ❌ 第一期不建议 | ① 灵感捕获的全部价值是**零摩擦**，每次记之前先做一次分类决策，长期必然退化成"随便选一个"或"不选" ② 它要解决的问题用筛选就能解决 ③ "成本前置、收益后置"是最不该选的组合 |
| 面板里手动创建分组归类 | ✅ 可行，但**先定粒度** | "分组"互斥（一条一个组），"标签"多值（一条多个）。**这个选择让实现代价差一个量级**，不是措辞问题 |
| 借助大模型自动分组 | ⚠️ 需改造后才可行 | ① 不定标签集 → 必然漂移 ② 你的数据只有「时间戳+一句话+来源窗口」，语义信号极弱 ③ 更可靠的是**确定性规则**（时间/来源/关键词），AI 只做"建议"不做"决定" |
| 「分类好以后一步上传」 | ⚠️ 因果链反了 | 见 §1：批量上传靠**筛选**，分类只是维度之一，且是成本最高的那一种 |
| 「也方便管理」 | ❓ 未定义，无法评估 | 管理 = 找得到？能批量操作？能定期回顾？三者方案完全不同 → 见 §8 |

## 5. 竞品怎么解（跨品类）

### 5.1 成熟产品的共同分工

| 机制 | 回答的问题 | 互斥 | 代表 |
|---|---|---|---|
| **文件夹 / 项目** | 它属于哪 | 是（1 个） | 几乎所有产品 |
| **标签 / 上下文** | 它是什么属性 | 否（多个） | Gmail、Todoist、Obsidian、Bear |
| **保存的筛选 / 智能文件夹** | 我此刻想看什么组合 | 不适用 | Todoist Filters、Apple Notes 智能文件夹 |

- **Todoist** 的三层分工最直白：**Project 回答"归属"、Label 回答"类型/上下文"、Filter 回答"我现在要看的组合"**。
  来源：todoist.com 官方 GTD 指南（`/productivity-methods/getting-things-done`）+ `/inspiration/how-to-use-todoist-effectively`
- **Obsidian** 的口径：**标签管分类、链接管关系、文件夹管项目**；并给出硬数字：**每条笔记 2-4 个标签、全局标签总数 ≤ 50 个**，超过 50 说明该合并或简化。
  来源：luoluo.help/docs/obsidian/tagging（该页自标查证日期 2026-09-14）

### 5.2 值得具体借鉴的五个设计

| 产品 | 机制 | 能借什么 |
|---|---|---|
| **Todoist** | 输入时打 `@tag` 自动补全，`@` 从正文剥离 | **打标签摩擦近零**：在输入流里顺带完成，不打断输入 —— 与"输入框加前置选项"是相反的做法 |
| **Apple Notes** | 智能文件夹 = 规则聚合，笔记**不用搬家** | "不改数据、只改视图" —— 批量操作的正确姿势 |
| **Bear** | 嵌套标签 `#books/xxx` + **批量重命名标签** | 标签体系必然会长歪，**必须有改名/合并出口**，否则三个月后就是一坨 |
| **Gmail / Outlook** | 筛选器（规则）驱动，可回溯、支持负向条件 | **规则比 AI 可靠**：行首关键词 / 来源 / 时间三条够用；负向条件防误分类 |
| **flomo** | 标签替代文件夹，无分类也能记 | 验证「标签优先」在碎片灵感场景成立；但它**不解决批量导出** —— 恰好说明「分类 ≠ 批量操作」 |

### 5.3 AI 自动分类的行业共识（直接对应你的第三个想法）

来源：newprompt.net（分类一致性指南）、cobbai.com（意图打标最佳实践）、llmcms.org（AI 打标治理）

三条共识，几乎逐字回答你的疑问：

1. **必须先有"固定封闭标签集"**。让模型自由打标签 → 每批都自己发明 → 同一条今天叫 `pricing`、明天叫 `cost` → **所有基于标签的统计都成了"移动靶"**。
   → 你担心的"规则怎么定"，答案是：**规则不能不定，且必须由你定，不能让模型定。**
2. **要留"兜底车道"**（`Other` / 收件箱）。不适合分类的先别硬塞，否则会产生静默的错误标签。
3. **低置信度交人确认**，人工修正回流；顶层类别 **8-10 个封顶**（来源：zeroindaily.com）。

**【判断】** 对 FocusCapture：每天几十条碎片文本，**上模型的收益远小于"确定性规则 + 事后批量整理"**。等真实痛点明确再说。

## 6. 三个方案

### 方案 A：筛选驱动（零分类负担）—— 推荐第一期

**做法**
1. 灵感速览筛选行加**时间档**：今天 / 近 7 天 / 全部
2. 上传按钮复用"无勾选 = 传当前筛选全部"（已有）
3. 条目加**「已上传」视觉标记**（数据层 `GetNoteSyncState` 已有；`QuickViewWindow.xaml` 的列表模板中**未找到**该标记 —— 属"未找到"，不等同于确认不存在）
4. 可选：加一个「未上传」筛选档

**成本**：小。**不碰行格式、不碰同步、不新增字段。**
**收益**：覆盖核心场景 —— 点「今天」→ 点「存」，两步。
**边界**：不能做跨时间的主题聚合（"所有关于银发经济的灵感"）。若这是你要的，必须走 B / C。

### 方案 B：分组 = 文件名（复用已有 Tag 机制）—— 推荐第二期

**做法**
1. 把「分组」正式定义为**文件名**（沿用 `{标签}.md` 规则）；面板暴露：分组列表 + 分组筛选 + 改分组
2. 改分组 = 跨文件移动行（行文本不变 → 行 ID 不变）
3. 输入框可加分组选择，但**默认"不选"= 落 Inbox**，不强制

**成本**：中。**先决条件：V1 / V2 待验证项先跑通。**
**边界**：一条只能在一个组（互斥）；**路径不进 `SyncNote`**（【事实】`SyncNote` 无 path 字段）
→ **分组是本地组织方式，不跨端同步。** 这一点必须确认是否可接受。

### 方案 C：行级多标签（`Tags` 独立化）—— 暂缓

**做法**：给 `Tags` 找独立来源（sidecar / 独立索引文件），面板支持多标签 + 标签筛选 + 批量改标签。

**成本**：大。要动 `SyncEngine` 的上传/拉取两条路径，并为 sidecar 失效加兜底。
**风险**：不解决 §3.2 的"投影"问题就做多标签 = **造一个下次同步就被抹掉的假功能**。
**建议**：等 A / B 用出真实缺口再做。到那时你才知道**标签集到底是什么** —— 而这正是 AI 自动分类的前置条件。

### 对比

| | A 筛选驱动 | B 分组=文件名 | C 行级多标签 |
|---|---|---|---|
| 碰行格式 / 同步 | 不碰 | 不碰行 ID | 碰 |
| 分类跨端同步 | 无需同步 | ❌ 不同步 | ✅ 同步 |
| 一条多个分类 | — | ❌ 互斥 | ✅ |
| 创建时摩擦 | 0 | 低（可选） | 低（可选） |
| 工作量 | 小 | 中 | 大 |
| 前置依赖 | 无 | V1/V2 验证 | B + Tags 独立化 |
| **推荐** | ✅ 先做 | 第二期 | 暂缓 |
