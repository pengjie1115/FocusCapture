# 悬浮球拖放保存方案

> 状态：**设计已冻结，待实施**
> 日期：2026-09-16
> 前置调研：拖放探针 `Diagnostics/DragProbe.cs`（`FocusCapture.exe --dragprobe`），四轮真机实测
> 数据来源：用户亲手拖放约 40 次，覆盖资源管理器 / WPS / 微信 / 浏览器 / WorkBuddy 五类来源

---

## 0. 一句话

把文字或文件直接拖到悬浮球上，触发「存笔记 / 存网盘 / 问 AI」三个动作。

---

## 1. 需求原文（用户最初描述，保留备查）

> 把文字或者文件直接拖动到悬浮球上面触发储存。如果是一段文字，可以把它分成两种：
> 第一种是把文字拖到悬浮球上面，就立即保存为一条新的笔记。第二种是，如果把文字拖到悬浮球上面停留，
> 比如一秒钟，就触发外部储存，可以选择把这段文字上传到得到大脑。
> 如果是文件拖动到悬浮球上面，就自动触发外部储存选项，就可以弹一个菜单出来，
> 看到底是上传到得到大脑，还是百度网盘，亦或者是后面咱更新的一些外部储存路径。

**注意：上面这段原文里有两处设想在后续讨论中被推翻**（"停留一秒触发"和"拖上去自动弹菜单"），
见第 3 节。实施时以第 4 节为准，**不要按需求原文实现**。

---

## 2. 最终形态一览

| 拖入内容 | 自动动作 | 用户可点的动作 |
|---|---|---|
| **文字** | 立即存为本地笔记 + 球闪绿 | 竖向小条：「AI 问答」「得到大脑」 |
| **文件** | **什么都不做** + 球闪绿 | 紧凑卡片：「用 AI 问答打开」「存到网盘」「发到得到大脑（仅文本类）」「更多渠道，敬请期待」 |

两者都必须先打开设置里的**总开关**（默认关闭）。

---

## 3. ⚠️ 已废弃的中间结论（禁止按这些实现）

> **本节是全文最重要的一节。** 讨论过程中有 6 处结论被推翻。
> 后来人如果只看聊天记录或某一版中间线框图，极易按错误版本实现。逐条列明「错在哪、为什么废、正确是什么」。

| # | 中间结论（**错的，已废弃**） | 为什么废弃 | 正确版本 |
|---|---|---|---|
| 1 | 文字在球上**悬停 1 秒**触发上传得到大脑 | **不可撤回的动作不能由时间阈值触发**。误触发代价不对等：误存笔记是本地脏数据（能删），误上传是内容已经发出去（收不回） | 上传必须**显式点击** |
| 2 | 文件拖上去**自动弹出菜单**选目标 | **拖拽期间鼠标左键被 OLE 拖放循环独占，目标窗口上任何按钮、菜单都点不动。**松手前弹出=点不了；松手后弹出=这趟拖动已结束 | **松手之后**再弹卡片 |
| 3 | 「透明区也能接收拖放」（探针首轮日志里的判断） | 探针判定半径**没算椭圆那 1px 描边**，把贴着边界的落点误判成圆外，造出假信号 | 透明区**穿透**。只有圆形可见区能接收拖放，**所有浮层必须是独立窗口** |
| 4 | 「吸附态收不到拖放」（用户反馈"没反应"） | 探针在吸附态下**不闪绿**（代码里一行 early return），反馈缺失被读成功能失效 —— 日志里其实收到了 11 次 | 吸附态**能**接收；但必须给视觉反馈 |
| 5 | 「需新增暂存区：拖入先复制保命 → 点存网盘才入仓+上传」 | 把用户说的"在卡片上选一下"错误理解成了"入库和上传分两次点" | **拖入什么都不做**；点「存到网盘」→ 复制入仓 + 自动异步上传（现有链路原样不动） |
| 6 | 「浏览器拖网页图片支持」（虚拟文件流） | 实测取流失败 `COMException: DV_E_FORMATETC`。`FileGroupDescriptorW` 能读到（596 字节），但 `FileContents` 读不了 —— **WPF 的取值接口只会按内存块方式请求，虚拟文件要求 IStream 方式** | **本次不做**。要做得绕过 WPF 下到 COM 层自研拖放接收器，风险收益不成正比 |

### 另有 4 处是**视觉/交互**被用户直接否掉的，同样不要按旧版实现

| 旧版 | 改版 |
|---|---|
| 小条按钮**横向**排列 | **竖向**排列 |
| 小条带「已存为笔记」提示文字 | **去掉**，只靠悬浮球闪绿 |
| 卡片每个选项带图标（我随手画的方块/圆圈占位符） | **去掉图标**，改用**整行悬停高亮** |
| 卡片副行「1.2 MB · 已复制到本机」 | 改成「1.2 MB · **来自微信**」（新逻辑下拖入不复制了） |
| 卡片末项「以后新增的渠道」 | 改成「**更多渠道，敬请期待**」（灰色不可点） |

## 4. 交互设计

### 4.1 总开关

新增设置项 `DragToSaveEnabled`，**默认关闭**。

| 状态 | 行为 |
|---|---|
| 关闭 | 悬浮球 `AllowDrop = false`。拖放**完全无反应**，连光标都不变，与改造前一致 |
| 打开 | 拖放生效 |

### 4.2 文字拖入

```
DragEnter  → 判定为文字
             ├ 球自动展开（复用 FloatBall.ExpandBall()）——吸附态只有 8×36，不展开根本瞄不准
             └ e.Effects = Copy（让光标显示"可以放"，而不是禁止符号）

Drop       → ① 取文字（**只认 UnicodeText**，见 §6 铁律）
             ② NoteService.SaveNote(text, sourceWindow)  → 存本地笔记
             ③ FloatBall.FlashGreen()                    → 闪绿
             ④ 球旁浮出竖向小条
             ⑤ e.Handled = true
```

**小条的两个出口**：

| 按钮 | 行为 | 复用情况 |
|---|---|---|
| AI 问答 | `AIDialogHelper.Open(ExplainMode.Ask, null, text)` | ✅ **签名现成**，`selectedText` 参数就是干这个的 |
| 得到大脑 | 直接调 `GetNoteDestination.ExecuteAsync("getnote_save_note", json, ct)` | ✅ 适配器现成；**注意这是绕过 AI 直接调**（用户已拍板） |

- 停留 `DropActionStripSeconds` 秒（默认 3，可调 2~10）
- **不点则自动消失**，笔记已经稳稳存在本地了
- 「得到大脑」的标题策略（**推定，未与用户确认**）：取正文首行前 30 字；无换行则取前 30 字
- 未配置得到大脑凭证 → 该项置灰并提示去设置

**来源标注**：`SaveNote` 的 `sourceWindow` 参数填**识别出的来源程序名**（如「微信」「浏览器」）。
实测拖放期间 `GetForegroundWindow()` 能稳定拿到源程序（`Weixin.exe` / `Tabbit Browser.exe` / `360FileBrowser64.exe` / `wps.exe`）。
识别不出时填「拖动」。

### 4.3 文件拖入

```
DragEnter  → 判定为文件
             ├ 球自动展开
             └ e.Effects = Copy

Drop       → ① 取路径列表
             ② **什么都不做**（不复制、不入仓、不上传）
             ③ FloatBall.FlashGreen()
             ④ 弹紧凑卡片
             ⑤ e.Handled = true
```

**卡片的四行出口**：

| 选项 | 行为 | 复用情况 |
|---|---|---|
| 用 AI 问答打开 | `ChatAttachmentService.CreateFromFileAsync(path)` → 打开对话并预置附件 | 造附件现成；**`Open` 需要扩展附件参数**（见 §10） |
| 存到网盘 | `FileRepository.RegisterLocalFile(path, FileTypes.Upload, name, false, null)` + `UploadQueue.Kick()` | ✅ **现有链路原样** |
| 发到得到大脑 | 仅**文本类文件**显示（`.md/.txt/.csv/.json/代码`）；读出文本走 `getnote_save_note` | 适配器现成；「只对文本类显示」是用户拍板 |
| 更多渠道，敬请期待 | 灰色不可点 | 占位，给后续渠道留位 |

**卡片头部信息**：

| 字段 | 规则 |
|---|---|
| 标题（文件名） | 正常来源用真实文件名；**微信图片拿不到原名**（实测 `FileNameW`/`FileName`/`FileDrop` 三者返回同一个哈希路径），自动生成 `微信图片_yyyyMMdd_HHmmss.jpg` |
| 副行 | `{大小} · 来自{来源程序}` |
| 多文件（**推定，未确认**） | 标题显示「N 个文件」，副行显示总大小，所有动作作用于全部 |

**不点任何选项** → 卡片消失，**无任何副作用**（网盘没多文件、笔记没多条目、源文件原地不动）。

## 5. 视觉规范（数值即线框，实施按此写）

### 5.1 竖向小条

| 项 | 值 |
|---|---|
| 位置 | 紧贴球旁：球在屏幕左半 → 小条弹在球右侧；球在右半 → 弹在球左侧 |
| 尺寸 | 宽 96px，内边距 4px，圆角 6 |
| 背景 / 边框 | `#2A2A2A` / 1px `#3A3A3A` |
| 按钮 | 文字 12px `#999999`，居中，行高 28px，圆角 4，**无图标** |
| 悬停 | 背景 `#3A3A3A`，文字 `#E0E0E0` |
| 标题 | **无**（存成功靠球闪绿告知） |
| 透明度 | 由 `DropActionOpacity` 驱动（`Window.Opacity`，与悬浮球同套做法） |

设计意图（用户原话）：**"让人不仔细看都不注意到它的存在都行"** —— 所以整体压到低对比，只有鼠标悬停才亮起来。

### 5.2 紧凑卡片

| 项 | 值 |
|---|---|
| 尺寸 | 宽 **276px 上限，贴合内容**（旧版卡片右侧留白过多，已否） |
| 内边距 / 圆角 | 10px 12px / 8 |
| 背景 / 边框 | `#2D2D2D` / 1px `#444444` |
| 标题 | 13px `#E0E0E0` |
| 副行 | 12px `#888888`，与标题间距 3px |
| 分隔线 | 1px `#3A3A3A`，上下留 8px / 4px |
| 选项行 | 13px `#BBBBBB`，左右内边距 8px，行高约 28px，行间距 1px，圆角 4，**无图标** |
| 悬停 | **整行**背景 `#3A3A3A`，文字 `#E0E0E0` |
| 未实现项 | `#666666`，不可点、无悬停 |
| 透明度 | 同 `DropActionOpacity` |

**为什么用整行悬停而不是图标**：整行铺满高亮后，右侧那片空白就变成了可点区域，不再是浪费；
同时把"鼠标停在哪一行"表达得比图标更清楚。

### 5.3 两个窗口的公共属性

与悬浮球同套（实测这套配置能正常接收拖放）：

```
WindowStyle=None / AllowsTransparency=True / Topmost=True
ShowInTaskbar=False / ResizeMode=NoResize / Background=Transparent
```

**必须是独立窗口**：实测透明区穿透（§3 第 3 条），任何浮层都不能靠在球窗口的透明区里画。

## 6. 判定与取值逻辑

### 6.1 内容判定（顺序不可颠倒）

```
Drop 时：
  1. GetDataPresent(DataFormats.FileDrop) 且有非空路径
        → 按【文件】处理
  2. 否则 GetDataPresent(DataFormats.UnicodeText)，去空白后非空
        → 按【文字】处理
  3. 都没有 → 不处理（可给一句"这个内容我读不到"）
```

**为什么必须 FileDrop 优先**：微信拖 xlsx 时 `Text` 格式里装的是**文件名**（`JD-260911.xlsx`）。
如果把"有文字就当文字"写在前面，会把文件名当成正文存成一条笔记。

### 6.2 文字取值铁律

> **一律从 `DataFormats.UnicodeText` 取，绝不从 `DataFormats.Text` 取。**

实测证据（浏览器拖「应用凭证」四个字）：

| 格式 | 取到的内容 |
|---|---|
| `Text`（CF_TEXT / ANSI） | `搴旂敤鍑瘉` ← **乱码** |
| `UnicodeText`（CF_UNICODETEXT） | `应用凭证` ← 正确 |

同一份数据，Chromium 给的 `CF_TEXT` 是坏的（微信给的 `CF_TEXT` 恰好是好的，但不能依赖）。
两者长度都不同（6 vs 4），说明是编码解码层面就错了。

### 6.3 文件名生成规则

| 来源 | 拿到的名字 | 处理 |
|---|---|---|
| 资源管理器 / WPS | 真实文件名 | 直接用 |
| 微信·文件（`msg\file\`） | 真实文件名（路径即真名，`Text` 里还有一份） | 直接用 |
| **微信·图片**（`temp\RWTemp\`） | **只有哈希名**（`697a54b2….jpg`） | **自动生成 `微信图片_yyyyMMdd_HHmmss.jpg`** |
| 浏览器·图片 | 无路径（虚拟文件流） | **本次不做** |

**必须知道的风险**：微信图片的源文件躺在 `temp\RWTemp\` 里，**微信随时会清**。
用户拖进来之后如果隔很久才点动作，文件可能已经不在 —— 实施时必须处理"文件已不在"的提示，不能静默失败。

### 6.4 源程序识别

`GetForegroundWindow()` + `GetWindowThreadProcessId` + `Process.GetProcessName()`，
拖放期间返回的就是源程序（实测稳定）。已知映射：

| 进程名 | 显示名 |
|---|---|
| `Weixin.exe` | 微信 |
| `Tabbit Browser.exe` / `chrome.exe` | 浏览器 |
| `360FileBrowser64.exe` / `explorer.exe` | 文件管理器 |
| `wps.exe` / `wpp.exe` / `et.exe` | WPS |
| 其他 | 进程名去掉 `.exe` |

## 7. 实测数据依据（全部来自探针真机记录）

| 结论 | 数据 |
|---|---|
| 无边框 + 透明分层 + 圆形容器**能**接收 OLE 拖放 | 40+ 次拖放，DragEnter/DragOver/DragLeave 序列完整，**零失败** |
| 吸附态 8×36 **能**接收 | 22:16:14~22:17:31 共 11 次成功记录 |
| 透明区**穿透** | 全部 DragEnter 的落点圆心距集中在 **19.68~20.35**（= 圆半径 20 + 描边 0.5）；若整个 48×48 窗口矩形可命中，应出现圆心距 20~28 的落点，实测**零次** |
| DragOver 心跳足够支撑悬停交互 | 8~278 次/秒（多数 26~79） |
| 用户自然拖放时长很短 | 25~675 ms（所以"悬停 N 秒"需要刻意停留，不是自然动作） |
| 浏览器文字带 `SourceURL` | `HTML Format` 里有 `SourceURL:https://…`，可作笔记来源标注（**本次未用，记入待办**） |

## 9. 新增设置项

全部放设置面板的**「外观」板块**（现有三个透明度滑块所在板块，`PanelAppearance`）。

| 属性 | 类型 | 默认 | 范围 | 说明 |
|---|---|---|---|---|
| `DragToSaveEnabled` | bool | **false** | — | 拖到悬浮球触发保存的总开关，**默认关闭** |
| `DropActionOpacity` | double | 0.90 | 0.3~1.0 | 小条与卡片的透明度，与 `FloatBallOpacity` 同套 |
| `DropActionStripSeconds` | int | 3 | 2~10 | 小条停留秒数 |

**注意事项**：
- 新增设置项属 `REGRESSION.md` 的维护触发条件，**必须同步登记**
- 设置面板透明度回填需同时改三处：XAML 滑块、`LoadSettings` 回填、`Changed` 事件（现有 `BallOpacitySlider` 就是这个模式）
- `DropActionOpacity` 变化要走 `_onChanged?.Invoke()` 让已打开的小条/卡片实时生效

## 11. 验收标准（现象级 —— 不满足就不算完成）

> 判级原则：**通过标准必须是用户能自己看见的终态**，不是内部状态显示什么。

1. 设置里总开关**默认是关的**；关闭状态下拖文件到球上**毫无反应**（光标都不变）
2. 打开开关后拖一个文件：球自动展开 → 松手 → 卡片弹出，标题是真实文件名
3. 点「存到网盘」→ 设置页「文件与网盘」里出现这个文件；稍后去百度网盘能真的看到它
4. 拖一段网页文字 → 球闪绿 → 灵感速览里出现这条笔记，**内容无乱码**
5. 点小条的「AI 问答」→ 对话窗口打开，且带着这段文字
6. 拖微信图片 → 卡片标题是 `微信图片_日期_时间.jpg`，**不是那串哈希**
7. 调透明度滑块 → 小条与卡片的透明度跟着变
8. **全程不点任何选项 → 零副作用**：网盘没多文件、笔记没多条目、源文件原地不动
9. 关掉开关再拖一次 → 行为与改造前完全一致
