## 调研：ima 知识库 / 夸克网盘 接入 Agent 工具框架可行性

用户诉求：得到大脑当前只能传纯文本笔记（PDF/Word/压缩包传不了），想把腾讯 ima 知识库和夸克网盘接进来。

### 结论（调研，未动代码）

**1. 腾讯 ima 知识库 —— 可行，官方 OpenAPI**
- Base URL `https://ima.qq.com`，路径前缀 `/openapi/wiki/v1`，HTTP POST + JSON
- 认证 header：`ima-openapi-clientid` + `ima-openapi-apikey`；凭证在 ima 客户端 Claw 配置 / `https://ima.qq.com/agent-interface` 生成（Key 只显示一次）
- 统一返回 `{retcode, errmsg, data}`，retcode=0 为成功
- **上传三步**：`create_media`（拿 media_id + 腾讯云 COS 临时凭证）→ COS 上传 → `add_knowledge`（带 media_type/file_info 入库）
- media_type 对照：1=PDF、3=Word 等；支持 PDF/Word/PPT/Excel/图片/音频/MD/TXT/XMind
- 大小限制：Excel/TXT/MD 10MB；图片 30MB；PDF/Word/PPT/音频 200MB
- 其他端点：`get_knowledge_base` / `get_knowledge_list` / `search_knowledge` / `search_knowledge_base` / `get_addable_knowledge_base_list` / `check_repeated_names` / `import_urls`
- **压缩包（zip/rar）不在支持列表**（搜到的第三方整理口径，官方未逐条核实）

**2. 夸克网盘 —— 不可行（官方层面无门）**
- 夸克无官方开放 API：`developer.quark.cn` / `open.quark.cn` 只有小程序与浏览器插件能力，网盘的上传/下载/目录管理完全未开放，无 OAuth2、无 AppKey 申请入口、无文档
- 社区流传的"夸克网盘 API"全是逆向抓包（复用 Cookie / 模拟登录 / 私有 RPC + 动态签名 + 设备指纹校验）
- 风险：违反《夸克用户协议》自动化访问条款；签名/风控一变即失效；会连累用户自己的网盘账号
- **结论：正式功能不依赖逆向接口**

**3. 网盘方向的正经替代**
- 坚果云 WebDAV（**最省**）：项目已有 `WebDAVProvider` + 凭证 + DPAPI 加密，`IFileStorageProvider` 就是现成通用文件级契约；需把 `UploadFileAsync(fileName, string content)` 扩展为字节流/Stream。免费版流量限制：每月上传 1GB / 下载 3GB
- 百度网盘开放平台：有官方 API，个人开发者可申请；工程量中等（WPF 内做 OAuth2 回调）
- 阿里云盘开放平台：有 OAuth2 上传，但政策曾变动，需现查

### 被低估的真工程量（关键判断）

**Agent 目前拿不到本地文件路径**——`LocalTools.cs` 全部工具都作用在 NoteService 的笔记库上，没有任何文件系统浏览/读取能力；也没有"选择文件"的 UI 入口。
→ 接任何文件上传目的地之前，必须先补：①对话窗加「选择文件」按钮（用户手动点选，最稳最安全）或 ②给 Agent 加受目录限制的 `list_directory`/`search_files` 只读工具。

- 是否落成 `docs/` 下的调研文档作为下一步 QUEST 开发依据

## 夸克网盘调研（第三轮）：skill 路线辨析 +「文件直存直取」需求 + 阿里云盘纠错

用户新提两问：①不走 API 改用「skill」能不能接？目标是"PDF 发给 AI 直接存夸克、说一声 AI 找到文件发给我"；②阿里云盘确认能像得到大脑一样直连吗？

### 纠错（重要）：阿里云盘个人开发者申请已暂停

- 开发者门户弹窗原文：「**2025年7月1日起，暂停个人开发者的申请；企业开发者如需对接，请邮件联系**」

- 官方 API **确实存在且完整**（4 大类 30+ 接口含上传/下载/列目录/回收站/分享，入口 `alipan.com/developer/f`）——比夸克强一档（夸克连 API 都没有）
- 但走 OpenList 公共 key 时，文档明确「刷新令牌**仅可用于 OpenList 挂载方式**，**也仅限用于 OpenList 使用**」→ **拿不回自己应用直连**
- **错因**：初版采信了 CSDN 一篇 2024-10 教程（当时确实可申请）。**教训：平台准入政策的时效性极强，二手教程不可作为依据，必须查门户实测。**（这条与上一条"假 API 文档"教训合流：教程类内容双重不可靠——既可能编造，也可能过期）

### 唯一"像得到大脑一样"的候选：百度网盘开放平台

- **个人实名即可申请**（可建 2 个应用），官方 API：获取网盘状态/文件信息、上传、下载、管理文件、视频服务、智能相册
- OAuth2.0 三模式（授权码/简化/**设备码**），回调支持 `oob` 与 `http://localhost:8080/callback` → **桌面应用可落地，不需要 server**
- 凭证：AppID / AppKey / SecretKey / SignKey；Access Token 30 天、**Refresh Token 10 年**（远优于夸克 Cookie）
- 旁证：已有人用 WorkBuddy 打通百度网盘做知识库采集（有公开操作手册）

### 「skill 接入」辨析（核心概念）

- **skill 替代不了 API**。skill = 给 AI 的说明书 + 可执行脚本，本身不产生网络能力；底下必须挂真实通道（官方 API / WebDAV / 逆向接口 / 浏览器自动化），只是把调用者从"应用"换成"本机脚本"
- 分两种场景：
  - **WorkBuddy 里跟我对话（有 skill 概念）** → 完全可行，随时能做
  - **FocusCapture 应用内的 AI（无 skill 概念）** → 应用唯一扩展点是 `AgentTool` 抽象类，加能力只能新写工具类 + 注册
- **重要架构判断**：用户要的"文件直存直取"**不该做 `IOutboundDestination` 适配器，而应做 `AgentTool`** —— 前者是"外发/发布"单语义带能力目录仪式，后者是"操作"天然双向、一个类 5 个成员

### 「文件直存直取」的三条链路现状（源码核实）

| 链路 | 现状 |
|------|------|
| 把文件交给对话框 | **不存在**。`AIDialogWindow.xaml` 检索 `AllowDrop`/`DragDrop`/`OpenFileDialog`/附件 → **零命中** |
| AI 拿路径 → 上传 | **不存在**。`LocalTools.cs` 7 个工具全在笔记库上 |
| AI 找到文件 → 交给用户 | **不存在**。且桌面应用无法像微信那样甩文件，"给用户"的形态需产品决策（下载到本地并定位？给路径？） |

装配点核实：`AIDialogWindow.xaml.cs` → `EnsureAgentRegistry()` **L769**，注册 7 个本地工具（L773–779）+ 得到大脑能力（L781–783）。

### 方案排序（本次结论）

1. **最省**：坚果云 WebDAV（项目已在用，零新增依赖）
2. **最正规**：百度网盘开放平台（唯一官方直连 + 个人可申请）
3. 自用野路子：夸克/阿里云盘 + OpenList（需常驻中间件 + Cookie 维护）
4. 零代码：本地文件夹 + 客户端自动备份（但 AI 无法确认结果、无法列云端）

## 输入框图片支持 + 灵感速览图片展示（方案讨论第一轮，未动代码）

用户诉求：悬浮球输入框支持粘贴图片、图文混排；灵感速览面板展示图片。用户提出的三个具体问题：①单图怎么展示 ②多图是一张一条还是塞一条 ③图文混排塞一条好不好。用户预设前提：**不改变条目高度，让图片适应条目高度**。

### 源码核实的关键事实（本轮）

| 事实 | 证据位置 |
|------|---------|
| 一条笔记 = md 文件一行；换行用 `\u23CE` 转义 | `Models/NoteEntry.cs` `ToMarkdownLine()` |
| 行身份 = `SHA256(完整行文本)`，**不含相对路径** | `Models/SyncNote.cs` `ComputeId()` |
| 灵感速览条目内容区**写死 40px 高**（等高设计，防列表跳动） | `QuickViewWindow.xaml` L486–491 `Height="40"` |
| 条目总高约 90px（40 内容 + 时间行 + 来源行 + padding 12 + margin 3） | 同上，Border `Padding="6,6,6,6"` |
| 预览是单行 NoWrap 截断，`DisplayPreview` 支持「首行 + AI 释义首行」 | `QuickViewWindow.xaml.cs` L45–51 |
| 项目内**零图片/附件代码**（grep `图片|附件|截图|Image|attachment` 仅命中文档） | 全仓 |
| 图片目录应放 `NotesPath`（用户可自定义）下，先例 = `.recycle_bin` | `Services/Sync/RecycleBinService.cs` L14 |
| `IFileStorageProvider.UploadFileAsync(fileName, **string** content)` —— **只支持文本，传二进制需扩接口** | `Services/Sync/IFileStorageProvider.cs` L27 |
| `ISyncProvider` 是笔记桶语义，不含二进制通道 | `Services/Sync/ISyncProvider.cs` |

### 本轮给出的判断

1. **「不改条目高度」这条前提会让功能报废**：可用空间仅 40px 高，竖屏截图（9:19.5）→ 只有 18×40 像素，等于一个色条。建议图片条目自身加高到约 170px（图片区 120px）。已用真实比例画图对比。
2. **多图建议「一张一条」**，理由是架构成本：塞一条的多图行后续增删单张图必须走「改行」流程（= 旧行消失 + 生成墓碑，即 `UpdateTodo` 那套高风险机制），且两端并发改同一行会冲突；一张一条永远是新增行，零风险。为保留「同批次」语义，建议加同批标记 + 面板显示 `1/3` 序号，而非额外做分组容器。
3. **图文混排方向可行但实现方式要换**：不能把输入框 `TextBox` 换成 RichTextBox（会推倒重做回车保存/Esc/自适应高度 `AdjustHeight`/草稿保留/Placeholder/IME 全套行为）。建议改成「文字框 + 下方缩略图条（chip 区）」的伪混排，图片可单独删除。
4. **必须提醒的隐性风险**：①坚果云免费版流量（官方定价页 + 帮助中心确认：上传 1GB/月、下载 3GB/月）→ 图片必须压缩，原图直传会撑爆配额 ②出现「半条笔记」状态（行在、图丢了），系统此前不存在这种部分失败状态 ③回收站/删除联动与孤儿图片清理 ④导出一致性（ExportDialog 支持 Markdown/Json/Txt/Word，图片会打破单文件导出）⑤图片无法被现有搜索命中（按 Content 文本匹配，除非做 OCR）。

### 待用户拍板

- 条目高度是否放开（图片条目单独加高 vs 严格 40px）
- 多图策略：一张一条（推荐）vs 塞一条
- 交付分档：M1 本地图片（不跨端）→ M2 跨端同步（需扩 `IFileStorageProvider` 支持字节流 + E2EE 加密二进制）

## AI 问答面板输入框多模态输入（方案讨论第一轮，已拍板 v1 范围，未动代码）

用户诉求：`AIDialogWindow` 输入框除文字外支持图片/PDF/Word/MD/MP3/MP4，可粘贴、可加号选文件，且**图文混排**（先打字→插图/文件→再打字）。

### 源码核实的关键事实

| 事实 | 证据位置 |
|------|---------|
| 消息模型只有 `Role` + `Content`（纯字符串），无附件概念 | `Services/AI/ChatModels.cs` L9 |
| **请求构造有两套序列化**，都只吐 `{role, content:"字符串"}` | `OpenAICompatibleProvider.BuildMessagesArray`（JsonObject，L320）/ `BuildRequest`（匿名对象，L344） |
| 会话整体存 `chat_history/{GUID}.json` | `Services/ChatSessionService.cs` L134–159 |
| 裁剪：只留最近 20 条 + user 消息截 2000 字符 | `ChatSessionService.cs` L9 / L123 |
| 云同步 = 整个 SessionFile 加密→Base64→PUT `chat-{Id}.json`，每轮全量扫 `chat_history/*.json` 对账 | `Services/Sync/ChatSyncEngine.cs` L196–226 / L332–335 |

| **可复用**：零依赖 docx/txt/md 文本抽取（`Parse()` L36）；本地 sherpa-onnx ASR（但 `WaveInEvent` **只吃麦克风**，L20） | `NoteImportService.cs` / `VoiceService.cs` |

### 核心结论（三条路，本质不同）

- **图片** → 压缩后转 base64 进消息体（`content` 数组），**要求模型有视觉能力**
- **文档（PDF/Word/MD/TXT）** → 本地抽文本再按位置拼进消息。**副产品：文字进了消息内容 → 随会话同步 → 跨端完整可见**
- **音视频** → 本地转写为文字（复用现有 ASR，但需改造为读文件）

### 关键技术决策（改这块代码前必读）

1. **两处序列化合并为一处**（`OpenAICompatibleProvider`）：原先非流式走匿名对象、流式走 `JsonObject`。加附件时若只改一处，症状是**连接测试正常、实际发送悄悄丢附件**。现统一由 `BuildMessagesArray` 生成。
2. **混排顺序 = `ChatAttachment.InsertOffset`**（附件插在正文第几个字符后）。输入区取值时记录、上行时据此把正文切开还原原序。正文 Trim 后必须同步修正偏移。
3. **附件只存引用，绝不嵌 base64**：落盘 `chat_history/attachments/{sha256前24位}.{ext}`（同内容去重），会话 JSON 只存 `ChatAttachment`。守护检查点 H8（实测会话 JSON 仅 2106 字符）。
4. **同步机制零改动**（已验证）：附件目录在 `chat_history/attachments/`，同步只扫外层 `*.json`；会话 JSON 新增字段走默认反序列化（忽略未知字段），新旧版互通。代价是跨端显示"仅存于原设备"占位。
5. **粘贴优先级**：剪贴板同时含文字与位图时**优先文字** —— Word/网页复制文本时会带位图，不判断会让用户想粘的文字变成一张图。
6. **图片必须白底合成再压 JPEG**（JPEG 不支持透明，直接编码透明区变黑）；WPF 图像对象有线程亲和性，剪贴板位图必须 Clone+Freeze 才能进后台线程。
7. **孤儿清理在启动时后台跑**，跳过 1 小时内的新文件（防与粘贴竞态）；不"删会话即删附件"（同内容去重后可能被多条会话共用）。
8. 输入区 `RichTextBox` 至少要有一个 Block；附件 chip 用 `InlineUIContainer` + `Tag` 挂数据。

### 结论（已回写方案文档）

1. **最大不确定性排除**：CLI 在非 WorkBuddy 环境（独立目录、清空宿主变量）**全部命令正常工作**
2. **隔离方案确认**：靠"装在自己目录"实现，**不要试图控制 agent 名**（环境变量覆盖无效）
3. **只需 `scripts/` 下两个 .cjs**（quark-drive.cjs + hash-worker.cjs），不需要 SKILL.md / references/
4. **错误码与官方文档不一致**：`auth.md` 写未授权是 `-1408`，实测是 **`-103`** → 实现须按 `code != 0` + msg 关键词判断，**禁止硬编码**
5. **CLI 会调 `reg.exe` 读注册表**，被安全策略拦截时只往 stderr 打"拒绝访问"，**功能不受影响** → Runner 不得因 stderr 有内容判失败，**以 stdout NDJSON 为准**
6. **未授权时 exit code = 1，但 stdout 仍有完整 NDJSON 结果行** → 判定失败不能只看退出码

### 排查过程（三组二分实验）

**实验 1 —— 确认是环境特征问题**
- 原样继承环境 → `QK_AGENT_ID=workbuddy` ✅
- **清空全部非系统变量 → `{"code":-104,"msg":"无法识别当前 Agent 环境，禁止继续使用"}`** ← 复现用户报错
- 去掉全部 `CODEBUDDY_*` → 仍返回 workbuddy（**说明读的不是 CODEBUDDY 系列**）

**实验 2 —— 逐组定位**
- 最小环境 + 全部 `CLIENT_INFO_*` → ✅ 通过
- 最小环境 + 全部 `WORKBUDDY_*` → ✅ 通过
- 最小环境 + 全部 `CLAUDE_*` → ❌ 失败
- 单变量细分：`CLIENT_INFO_PRODUCT_NAME` ✅ / `CLIENT_INFO_IDE_TYPE` ✅ / `WORKBUDDY_CONFIG_DIR` ✅ /
  `CLIENT_INFO_USER_AGENT_EXTENSION` ❌ / `WORKBUDDY_APP_NAME` ❌ / `WORKBUDDY_APPLICATION_NAME` ❌

**实验 3 —— 白名单广度 + 能否自定义**
- `CLIENT_INFO_PRODUCT_NAME = FocusCapture` → ❌
- 依次换成 **Claude / Cursor / CodeBuddy / VSCode / OpenClaw / Qoder / Trae → 全部 ❌**
- `QK_AGENT_ID = focuscapture` → ❌（该变量是只读输出，不能反向设置）
- `WORKBUDDY_CONFIG_DIR` 指向**不存在的目录** → ✅ 通过（**只校验变量是否存在，不校验内容**）
- 最小环境 + 白名单值跑 `get-user-info` → ✅ 成功返回账号 → **识别通过后功能完全正常，这是唯一的一道门**

### 结论

**该 CLI 是 WorkBuddy 专属：白名单当前只有 WorkBuddy 一个。**

- 与我的实现无关（安装/调用/解析链路全部实测正常）
- 与机器环境无关（两台电脑一致）
- 官方虽把 Skill 公开在 ClawHub 上（MIT-0），但**运行时把非 WorkBuddy 宿主全部挡在门外**

**已知绕过方式（记录事实，不推荐）**：设 `CLIENT_INFO_PRODUCT_NAME=WorkBuddy` 伪装成 WorkBuddy，
实测可让 CLI 完全正常工作。但这是欺骗性绕过平台准入校验 —— 官方只对该应用开放通道，
一旦加强校验（进程签名 / 服务端二次验证）即失效，且与"不逆向、走官方通道"的初衷相悖。
