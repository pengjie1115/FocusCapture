### 三条红线怎么落的

1. **路径参数绝不由 AI 生成** → 工具签名里根本没有 path；只能传 `handle`（用户点选产生）或 `file_id`（本地元数据编号）。

### 设计上值得记住的几个判断

- **取回永不触发上传**（origin=downloaded）与 **MD5 查重**两道防线都要，缺一不可。同理别指望百度「秒传」兜底——它省流量，不防重复条目。
- **元数据只记客观事实，会变的状态全放本机账本** → 多设备合并降级成「按 id 求并集」，规则简单到能写成检查点。
- **墓碑语义要留后门**：删除优先于普通修改（防被改标签复活），但 `CreatedAt` 晚于墓碑时刻的视为「删后重传」，必须放行（否则重传永远不生效）。
- **附件云端清理只作用于 attachment**：一刀切会让网盘从「全量权威仓库」退化成「滚动窗口」。
- **自定义数据根不可用时绝不静默回退默认根** —— 回退会造出两套数据，比启动报错难收拾一个量级。

## 第二轮：用户实机验收 → 上传 100% 失败的修复（同日，commit `6e9a104`）

**上面那条"未接真凭据实跑"当天就被验证了，而且翻车。** 用户填好 AppKey 授权后连传三个文件，
AI 都说"已保存到你的网盘"，用户去网盘一看 —— 空的。连带「测试连接」也报错。

### 证据链（`%AppData%\FocusCapture\logs\app_2026-09-16.log`）

```
[Files] 已登记文件：空白文档.txt（已上传，1.5 KB）
[Agent] 工具 store_file_to_cloud 返回：已保存到网盘：空白文档.txt...
[WARN ] [Files] 上传失败：拒绝访问沙箱以外的路径（/apps）。本应用只能读写自己的应用目录 /apps/{应用名}。
[WARN ] [Files] 上传失败：... （同上，连续 5 次，全部发生在 78 毫秒内）
```
三次上传、三份文件，**全部倒在同一个点**，一个字节都没上去。

### 根因：沙箱守卫粒度错位（一个 bug 瘫痪全链路，且不在上传逻辑里）

`EnsureSandboxed` 一律要求路径以 `/apps/` 开头（带斜杠）→ 而 `EnsureDirectoryAsync` 建目录时
**逐级探测父目录**，建 `/apps/FocusCapture/files` 必然要列一次 `/apps` → `"/apps"` 不满足
`StartsWith("/apps/")` → **被自己的守卫拒绝** → 抛错 → 上传整条挂掉。

「测试连接」同一个根因（它也要建目录）。网盘上连 `files` 目录都没建出来，所以是空目录。

### 修复（三项主修 + 三项顺带）

| 项 | 改法 |
|---|---|
| **① 守卫粒度错位**（根因） | `EnsureSandboxed(path, allowSandboxRoot)`：只读列目录放行 `/apps` 本身，写操作仍强制带下级。**建目录改为直接 create + 容忍 -8「已存在」**，不再依赖列父目录；加进程内已建目录缓存 |
| **② 失败重试零延迟** | 失败后不等待 → 78ms 烧光 5 次重试。改为 10s×N 退避（上限 60s，Kick 可提前唤醒） |
| **③ 工具文案把「登记成功」说成「已保存到网盘」** | 改为如实区分「已在云端 / 已存本机待传 / 未授权暂存」；工具描述里对模型加硬约束，禁止说"已上传成功" |
| 顺带 a | `RegisterLocalFile` 的 MD5 去重分支曾传 `markUploaded: CloudReady` —— 它只表示"配了凭据+有令牌"，会把从没传成功的文件记成已上传 → **永不重传**。改为保留原状态 + 清零重试 |
| 顺带 b | 新增 `FileRepository.ResetFailedUploads()`：测试连接通过 / 授权成功时自动把撞上限的文件放回队列（否则改对配置也永远等不到重传） |
| 顺带 c | `find_cloud_files` 补「云端位置在哪」的准确说法（用户问过"上传到哪个目录了"，此前模型只能编）；删掉死代码 `ListAppDirsAsync` |

### 测试

慢层 **+14 条检查点**（沙箱守卫 9 / 重试出口 3 / 目录配置 2），快层 21/21、慢层 **121/121** 全过，
编译 0 警告 0 错误。REGRESSION B-14 补了事故记录与对应验收项。

### 教训（跨项目可复用）

1. **守卫/校验的检查粒度必须与操作语义对齐** —— 拿一把尺子量所有请求，就会把自己的合法请求也杀掉。
   而且失败点会离根因很远（这里报的是"上传失败"，根因在"守卫太严"）。
2. **失败必须退避** —— 不退避时"重试 5 次"在一瞬间烧光，重试上限形同虚设，用户也来不及改配置。
3. **异步操作的返回值不许把 A 说成 B** —— 登记成功 ≠ 上传成功。说错了用户一去核对就穿帮，
   整块功能的信任当场归零。这条比 bug 本身更贵。
4. **验收必须落到"用户能自己看见的终态"** —— 内部状态显示"已上传"没用，要看网盘上有没有。

## 第三轮：第二轮修复后文件仍传不上去 → 第二个 bug（已定位，未修，待拍板）

用户重启后重传（10:45 起）：文件夹能建出来了、网盘里出现了 `/apps/FocusCapture/files`，
**但文件依然 100% 失败**。日志里的错误变了（说明第二轮的修复生效了，问题换了一层）：

```
[WARN] [Files] 上传失败（36bad2d9…）：The requested operation requires an element of type 'String',
                                          but the target element has type 'Number'.
```

（10:03/10:15 那批=旧版守卫错误；10:46 起=新错误。两次运行是两个编译版本，别把日志混读。）

### 根因：`BaiduNetdiskClient.UploadFileAsync` L450 把 precreate 返回的 `block_list` 当 md5 字符串数组

```csharp
foreach (var b in bl.EnumerateArray()) serverBlocks.Add(b.GetString() ?? "");
```

官方返回的是**「已上传分片的序号」数字数组**，不是 md5。`JsonElement.GetString()` 遇 Number 必抛该异常。

- 证据①：这是全项目**唯一**没有 ValueKind 检查的直接 `GetString()`（已 Grep 复核全部 `.GetString()` 调用点）。
- 证据②：实测响应示例 `{"errno":0,"return_type":1,"block_list":[0,1],"uploadid":"…"}`；
  alist 驱动源码定义为 `BlockList []int`（【一手·源码】）。
- 现象自洽：14.2MB PDF 与 1.1KB txt **失败耗时一样短**（<300ms）→ 失败发生在"还没开始传数据"之前；
  网盘恒空（precreate 只登记，create 从未跑）；文件夹走 `method=create&isdir=1`，与 block_list 无关
  → **「文件夹通了」不能证明「文件链路通了」，这是两条不同接口路径**（用户原判断有误，已纠正）。

### 顺带发现的两个遗留问题

1. `uploadid` 只在 `!rapid` 分支校验，`rapid` 分支仍会带空 uploadid 去 create；`return_type` 的语义
   （0/1/2 与"秒传"的对应）需按官方文档重新核对，现有 `rapid = returnType == 1` 判断存疑。
2. **旧版 `markUploaded: CloudReady` 留下的脏状态洗不掉**：`111.pdf`/蔡康永 PDF 那条账本状态是 `uploaded`，
   但网盘上根本没有 → `PendingUploadIds()` 永远跳过它；MD5 命中路径也只会保留 uploaded
   （`UpsertLedgerLocked` 里 `else if (e.UploadState != Uploaded)`）→ AI 会一直说"网盘上已有相同内容"，
   用户去核对是空的。**这类"状态无法自我纠正"要单独想清楚**，不是改一个赋值就完事。

### 修复后必须先做的数据动作（否则看起来像没修）

两条失败记录 `UploadRetry` 已到 5 上限 → 修完要让用户点一次「测试连接」（触发 `ResetFailedUploads`）
或重启应用；假 uploaded 那条需额外纠正（或让用户删记录重传）。

> 复用教训：**「两条路径看似同源、实则各自实现」时不能互证**。文件夹与文件都叫"上传"，
> 但一个是一次 create、一个是三阶段分片，前者通了跟后者毫无关系。

### 方案 A/B 权衡（决策讨论，未拍板）

用户问"长远看哪个更优更稳"。结论：**这不是二选一** —— A 是安全基座，B 是可选优化，正确形态是 A 打底 + B 包安全网。

- precreate 的 `block_list` 有**两套语义**：**请求**里是"本地算的分片 md5 列表"（我们自己的数据，可靠）；
  **响应**里是服务端口径的"已存在分片序号"（外部数据，第三方实现语义互相矛盾，我们从未实测过）。
- create 提交时带的 block_list 是**本地重算的 md5**，不依赖服务端那个字段
  → **A 方案下全链路只剩一个外部依赖：uploadid（字符串，官方文档明确）**。
- B 的收益仅限"重试时跳过已传分片"：单片 4MB，14MB 才 4 片；本功能定位是上传归档（KB~几十MB 为主），
  重传成本在秒级、用户基本无感。**GB 级文件才是 B 的舞台**。
- B 的错误代价是**上传失败**（不是文件损坏 —— 跳过错误时 create 会报缺片），而"上传失败"恰恰是今天连踩三次的坑。

→ 推荐形态：**行为按 A（顺序传全片），但解析函数升级为「类型安全 + 解析失败/字段缺失一律退化为不跳过」**。
   这样 B 的位置已预置（将来要省流量只改一处），且任何解析异常都不会再瘫痪上传链路。

## 第四轮：用户验收又失败 —— 第三层根因（含对上一轮理解的**反转**）

用户 11:24 重启后重传，现象升级：**网盘里多出一堆空文件夹**（`FocusCapture_20260916_104601`、
`FocusCapture_20260916_112442`、`files_20260916_112442`），文件仍然传不上去（`errno=31500`），
设置页报失败，而 **AI 却告诉用户"两个文件都已经上传成功，网盘上都能看到了"**（撒谎）。

### 实锤证据链

**日志（`app_2026-09-16.log` 11:24 起）**：每个文件都是
`服务端报告已存在 N 个分片（序号 …）` → `秒传命中（内容已存在）` → `上传提交失败 errno=31500`。
N 与文件大小精确对应：1.6KB→1 片；15.4MB→4 片（4MB×4）。

**源码铁证（`baidu-netdisk-sdk` Rust 源码，【一手·源码】）**：
```rust
/// List of missing block indices that need to be uploaded
#[serde(rename = "block_list")] pub block_list: Vec<u32>,
```
且该 SDK 的上传流程**完全不看 `return_type`**，只用 `block_list` 空不空来判秒传：
非空 → 上传这些分片；空 → 直接 create。

**官方 create 文档（抓到原文）**：`rtype`「默认 0：不重命名，返回冲突；1 冲突即重命名；
2 冲突且 block_list 不同才重命名；3 为覆盖，**需要与预上传 precreate 接口中的 rtype 保持一致**」。

### 根因（四条）

| # | 根因 | 证据等级 |
|---|---|---|

### 三轮需求对齐后收敛到的方案（待用户最终拍板）

| 议题 | 结论 |

## 23:47 用户首测反馈：点动作白弹「界面错误」框（commit `cc1db09`）

### 现象与定位

`[2026-09-16 23:33:06]` 起连报 7 次（23:33:06 / 23:35:01 / 23:35:15 / 23:35:25 / 23:35:39 / 23:38:14 / 23:38:44），

```
System.InvalidOperationException: 在窗口关闭期间，无法将可见性设置为可见…
   at System.Windows.Window.VerifyNotClosing()
   at System.Windows.Window.InternalClose(Boolean shutdown, Boolean ignoreCancel)
   at FocusCapture.Windows.DropActionCard.Dismiss()  ...DropActionCard.xaml.cs:line 89
   at FocusCapture.Windows.DropActionCard.Window_Deactivated(...)  ...:line 112
   at System.Windows.Window.WmActivate(IntPtr wParam)
```

### 根因（我的代码，不是 WPF 的锅）

`DropActionCard` 的关闭入口有五个：三个选项按钮 / 点卡片外面 / Esc / 兜底超时。
按钮路径的写法是「**先 `Dismiss()`（= `Close()`）再抛事件去开 AI 窗口**」，而 AI 窗口一激活，
本窗就收到 `WM_ACTIVATE` → `Deactivated` → 此时 `_armed` 早已是 true → **二次 `Dismiss()` → 二次 `Close()`**
→ WPF `VerifyNotClosing()` 抛异常。

**关键判断：功能其实是好的。** 异常发生在"关闭流程的再入"里，动作早已派发出去（所以点掉框之后问答/上传都正常），
纯粹白弹一个吓人的框。**用户的体感是"有问题"，但底下没有第二个 bug** —— 这点必须说清楚，别让用户以为功能是坏的。

### 修法（三件套 + 一刀副产品）

1. `Dismiss()` 幂等：一进关闭流程就 `_dismissed = true`，后到的入口直接返回
2. **`OnClosing` 也上锁 + 停表** —— 这条不只是防御：`MainWindow.CloseDropOverlays()` 在换浮层/退出时是**直接
   `Close()`** 的，不走 `Dismiss()`，所以只加幂等判空挡不住那条路。**别指望调用方守规矩，把它锁在被调方**
3. 关窗前 `Deactivated -= Window_Deactivated`（关窗自身会产生激活变化，先摘监听避免再入）
4. `DropActionStrip` 同类加固（风险低，但关闭入口也有四个且同样会被直接 `Close()`，加锁三行不值当赌）

### 自己踩的新坑（已修，记下来）

加 `-=` 之后**编译从 0 警告变成 1 条 CS8622**：`Deactivated` 是 `EventHandler(object?, EventArgs)`，
而我的处理函数签名是 `(object sender, EventArgs e)`，带 `?` 才匹配。
**有意思的是 XAML 那条订阅路径不查这个**，所以签名写错时毫无征兆，只在加 `-=` 的那一刻才炸出来。
→ 已把签名改成 `object?`，并把这条写进代码注释（否则下一个人删注释时又会踩）。**基线是 0 警告，1 条也是退。**
