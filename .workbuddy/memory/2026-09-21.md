## 灵感速览「分类」需求评估 + 竞品调研（**只调研，代码一行未动**）

**用户诉求**：给灵感速览里的笔记/待办加分类（分组 / 标签 / 或其他形式），以便批量操作（如「今天做过的事一步传得到大脑」）与长期管理。

### 核心结论（本轮最值钱的四条）

1. **用户的因果链反了 —— 「加分类」其实是两条独立需求被绑成一句话**：
   「批量上传今天的事」靠**筛选**就能满足，不需要分类；「长期管理」才需要分类体系。
   且**现有代码已经支持"不勾选 = 传当前筛选结果的全部"**（`QuickViewWindow.xaml.cs:911-915`）——
   用户抱怨的"一条条勾选"其实早就有捷径，**真正的唯一缺口是没有「今天」时间筛选档**。
   → 方案 A（筛选驱动）成本最小、零风险，推荐先做。

2. **`SyncNote.Tags` 是现成的分类承载通道（本轮新发现）**：`string[]`、行级、与 Content 一起**加密同步**、
   **不参与行 ID**（`SyncNote.cs:25-26`；`SyncEngine.cs:567 / 891-892`；`CryptoService.cs:11`）。
   → 改分类**不产生墓碑、不进回收站**。这条已写进项目 MEMORY.md §六。

3. **但 `Tags` 是"文件名的投影"而非独立来源**（上传 `Tags ← entry.Tag ← 文件名`，拉取 `文件名 ← Tags[0]`）
   → **单纯把 `Tags` 扩成多元素是假功能**：下次 push 会被文件名覆盖回单值。
   要支持多标签必须先给 `Tags` 独立持久化来源（sidecar / 独立字段文件 / 行内标记三选一）。

4. **标签写进正文行内 = 踩同步红线**：行 ID = `SHA256(完整行文本)`，改文本即"删旧行+加新行"
   → 进回收站 + 发墓碑 + 跨端可能双条（`NoteService.cs:366-372` 注释已明说）。

## 飞书跨端授权失败根因定位（**只查，未动代码**）

**用户现象**：换一台电脑后飞书授权永远卡在"正在生成二维码…"，界面上同时有红字报错。

**根因（已锁死）**：lark-cli 有二段前提，应用只做了一段。
- 第一段「应用凭据配置」= `lark-cli config init`，产物 `%USERPROFILE%\.lark-cli\config.json`（含 appId + **appSecret 明文**），
  **机器级/用户级、不随应用分发、不在 Skill 目录里** → 换机必然不存在。
- 第二段「用户身份授权」= `auth login`，应用代码里**只实现了这一段**（全仓 Grep 无 `config init` / `config bind`）。
- 配置缺失时 `auth login --no-wait --json` **直接返回** `{"type":"config","subtype":"not_configured"}`（退出码 3），
  **连 device_code 都拿不到** → 二维码永远出不来。这不是"卡住"，是第一步就死了。

**硬证据链**：
1. `app_2026-09-21.log:28` 09:22:42 本机（Debug）也是 not_configured —— **本机当天先复现了同一个 bug**。
2. `%USERPROFILE%\.lark-cli\config.json` 的 **CreationTime = 09:24:20**（今天新建）；`auth status` 显示 appId `cli_aa93ebc4a9ba1cb3`。
3. `auth-2026-09-21.log`：09:24:20 `auth logout` 200 → 09:24:25 `device_authorization` **200（出码成功）**。
   即**配置出现的那一刻，二维码就能出了** —— 因果闭合。
4. 清掉 `HERMES_HOME` 后实测 `config show` → `workspace: local` / `Config file path: .lark-cli\config.json`，
   **确认应用读的就是根配置**（`SkillProcess.HostMarkerVars` 刻意清 HERMES_HOME/OPENCLAW_HOME/LARK_CHANNEL/PYTHONPATH）。
   顺带证明：`workspace=hermes` 那份（appId `cli_aae612d5b878dd16`，8-21 建）**不是应用用的那份**，两个 appId 不同。

**连带发现（两个副作用，都要单独修）**：
- **UI 文案自相矛盾**：`SkillAuthWindow.ShowFailure()` 只改 StatusText、**不改 QrPlaceholder.Text**
  （`SkillAuthWindow.xaml.cs:126-134`，占位文案仍是 StartFlowAsync 里写的"正在生成二维码…"）
  → 用户看到的"卡在生成二维码"很大程度是这个 bug 造出来的。
- **错误分类缺失**：`not_configured` 被 `ProbeAsync` 归成 `DependencyAuth.Unknown`（"状态查询失败"），
  用户看到的是 CLI 原始 JSON；且失败面板给的「重新生成二维码 / 在浏览器打开」**永远不会成功**（根因不在二维码）。
- **本机 user identity 仍是 `missing`**（`auth status`：bot ready / user missing）→ 即使另一台配好，
  本机现在也跑不通 kb.py（它走用户身份）。用户那轮"重新授权"实际未完成。

**待用户确认（不影响根因结论）**：09:23~09:24 之间是谁/什么让根配置出现的（app log 缺这一段）——
决定"产品级修复"该走 `config init --new`（应用内出码、浏览器创建新应用）还是 `--app-id + --app-secret-stdin`。

## 飞书授权第二轮：拷 config.json 不够（**我给的 A 方案是错的**，2026-09-21 上午）

**现象**：用户按 A 方案把本机 `~\.lark-cli\config.json` 拷到另一台同路径 → `not_configured` 消失，但报新错：
`device authorization failed: The request is missing a required parameter`（`/oauth/v1/device_authorization` **400**）。

**我的判断失误**：上一轮我看到 `config show` 有 appSecret 字段就以为"secret 在文件里，拷文件=搬凭据"。
**实际（事实，已开文件核对）**：config.json 里 appSecret **只是一个引用**，不含密钥本身：
```json
{"apps":[{"appId":"cli_aa93ebc4a9ba1cb3",
          "appSecret":{"source":"keychain","id":"appsecret:cli_aa93ebc4a9ba1cb3"},
          "brand":"feishu","lang":"zh_cn","users":[]}]}
```
→ 真实密钥存在**机器本地密钥库（keychain）**，config.json 只是索引。
**所以「拷 config.json」在原理上就不可能成功** —— 搬了钥匙串的标签，没搬钥匙。

**预防**：以后凡涉及"凭据跨机迁移"的建议，**必须先开文件确认凭据是「值」还是「引用」**，再给方案。

### 本轮拿到的硬事实

1. `config.json` 结构如上（`apps[]` → `appSecret{source,id}`）；hermes 那份同构（appId `cli_aae612d5b878dd16`）。
2. Windows 上 **cmdkey /list 里没有 lark/feishu/cli_ 条目**（9 条全是别的）→ keychain 不在 Windows 凭据管理器可见层，具体落点**未定位**（不是重点）。
3. **换 USERPROFILE 不能复现**：在 `%TEMP%` 下另造 USERPROFILE + 同结构 config.json + 清宿主变量，`auth login --no-wait --json` **依然成功**（退出码 0、拿到 device_code）
   → 说明 keychain 不随 USERPROFILE 走，**无法在本机复现"另一台"的现象**（隔离不了"机器"）。这条实验没能证实假设，记下来免得下次重复试。
4. 顺手验证：`$env:USERPROFILE` 隔离时若**不清 HERMES_HOME**，lark-cli 直接报
   `hermes context detected but lark-cli is not bound to it` → **反证 `SkillProcess.HostMarkerVars` 清宿主变量是必须的**。
5. **决定性**（从 lark-cli.exe 二进制里挖到它自己的文案 @24977362）：
   > `requires a terminal for interactive mode. Run with --new to create a new app: lark-cli config init --new. This command blocks until setup is complete and outputs a verification URL.`
   - `config init` **不带 `--new` = 需要终端** → 应用拉起的无终端子进程跑不了
   - `config init --new` **非交互、阻塞、输出 verification URL** → **可被应用后台驱动**（与 `auth login --no-wait` 同构）
   - 另有文案 `appId and appSecret keychain key are out of sync / please run lark-cli config init to reconfigure` —— CLI 自己就有"appId 与 keychain 密钥不同步"的语义，与本场景同族
6. `config init` 的其他非交互入口（来自 `--help`）：`--app-id X --app-secret-stdin --brand feishu`（要 secret，可复用同一应用）。

### 结论

- **每台机器都必须各自完成一次「应用凭据录入」**，无法靠拷文件绕过。
- 立刻解法（不动代码）：在另一台跑
  `lark-cli config init --app-id cli_aa93ebc4a9ba1cb3 --brand feishu --app-secret-stdin`（secret 从飞书开放平台复制）
  或 `config init --new`（浏览器新建应用，不用 secret，但会多一个应用、权限要重配）。
- 治本：授权窗口在 `auth login` 前加"配置预检" → 识别 `not_configured` 时应用内后台跑 `config init --new` 抓 URL 出码。
  ⚠ 待验证：`--new` 输出的 JSON 字段名（假设与 `auth login --no-wait` 类似）；`--new` 会创建新应用，是否可接受需用户拍板。

### 附带发现（仍挂着）

- `SkillAuthWindow.ShowFailure()` 不同步 `QrPlaceholder.Text`（`SkillAuthWindow.xaml.cs:126-134`）→ 假"卡在生成二维码"。
- `StartAuthAsync` 失败**不写日志**（只有 `MakeQrPngAsync` 失败才 `AppLog.Warn`）→ 完整报错进不了日志，还被 `Short()` 截到 200 字符。

## L1 方案选型取证：`config init --new` 是不是官方路径？（2026-09-21）

**用户拍板**：乙方案（应用内走 `config init --new`，用户在浏览器里创建应用，不用手填 appId+secret）+ L2 + L3 现在做。

**取证结论（一手来源 = larksuite/cli 官方 README，main 分支）**：

1. **`config init --new` 就是官方给 AI Agent 的标准路径**，原文：
   > Step 2 — Configure app credentials. Run this command in the background. It will output an
   > authorization URL — extract it and send it to the user. **The command exits automatically
   > after the user completes the setup in the browser.** `lark-cli config init --new`
   - 特性页原话：`Up and Running in 3 Minutes — One-click app creation, interactive login`。
   - **与我们的用法完全同构**（后台跑 → 抓 URL → 交给用户 → 浏览器完成），L1 可行。
2. **README 未提"新建应用需要企业管理员权限"**，个人开发者直接走 Quick Start。
   ⚠ 但这是"README 没说"，**不等于**一定不需要 —— 属于【判断】。
3. **scope 在 `auth login` 阶段申请，不是 config init 时固定**；官方把 `--recommend` 说成
   "Recommended **auto-approval** scopes" → 存在"免审批 scope"这一类。
4. ⚠ **风险（二进制文案佐证，事实）**：lark-cli 里有
   `access denied: app %s has not applied for the required scope(s): %s` /
   `ask the tenant admin to re-enable the app in the Lark admin console`
   → 说明**新建应用确实可能缺 scope 或需要管理员**。
   我们用的是 `--domain base,docs,drive,sheets,wiki`（非 `--recommend`），
   这些是否属于免审批集合 —— **未知**。

## 方案丙被否决（2026-09-21，用户约束 + 查证发现）

   这是依赖闸检查点能稳定跑的前提；签名改成非 virtual 会直接把那条路堵死。
2. **`ParseStatus` 收 `stdout` + `stderr` 两路** —— 实测成功走 stdout、错误走 stderr，
   只喂一路会漏掉最关键的 `not_configured`。检查点里两个方向都断言了。
3. **纯文本解析抽成 `public static DepAuthText`** —— 原因与项目既有做法一致：
   解析最容易出错、最需要喂样本，抽公开是为了让检查点不必真起外部进程
   （`LarkDeviceCodeFlow` 是 `internal`，测试工程看不见它）。
4. **flow 构造时持有 owner（dependency）** —— 换来"命令与字段名只搬不改"，改动面最小；
   代价是循环引用（同一程序集内，可接受）。
5. **界面按钮禁用条件加 `dep.Flow != null`** —— 没有协议的依赖点了没流程可走，
   等于制造"点了没反应"（本项目踩过的坑）。
