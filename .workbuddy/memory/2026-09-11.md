## CI/CD 适用性分析（用户提问，纯分析未改代码）

用户问「CI 和 CD 是什么，咱们这个项目有必要部署吗」。做了一轮实测盘查 + 概念讲解 + 适用性判断。

### 结论

**不部署 CI/CD。** 四条理由：①零测试，CI 最核心的「跑测试」无内容可跑；②每次改动本来就要本地 `dotnet build` 才能开软件验证，云端再查一遍属重复劳动；③GitHub 国内连接实测失败（`HTTP2 framing layer`），触发环节本身不稳定；④发版形态是「给一整个文件夹」，与 GitHub Actions 产出的单文件 exe 方向不匹配（单文件启动慢、体积反而更大）。

### 测试分层适配评估（本次结论）

| 层级 | 项目例子 | 评估 |
|---|---|---|
| 逻辑零件测试 | TimeParser 时间解析（「明天10点」→ 次日 10:00）、CryptoService 加密往返 | **最容易写、最值得做** |

## 真实需求确认：用户要的是「AI 交付前自动验证」（2026-09-11）

用户主动澄清真实需求，关键原话：

- 项目代码全部由 AI 编写，用户只负责设计 + 提需求，「每次 AI 写完代码我都要自己手动去测」
- **最痛的场景是修 bug**：用户只能描述「看到的现象」，讲不到点上；AI 靠现象猜原因，一轮轮浪费；「本来很简单的 bug，如果最开始就说对了那个现象，前面就不用浪费那么多时间」
- 核心诉求原话：「**至少别把一个仅仅通过编译的半成品交到我手上**」
- 用户预期：AI 懂代码、理解需求，应该自己清楚问题在哪、怎么制定修复方案

**需求判定（重要）**：用户要的不是「测试代码」本身，而是 **验收自动化 / 交付门禁**——把 AI 的交付标准从「编译通过」抬到「行为已验证」。测试只是实现该目标的手段。

**机制洞察（本次给出的核心解释）**：AI 之所以把用户的描述当唯一线索，根因是它**没有手段自己验证猜测**。有可跑的测试后，反馈闭环从
`用户描述 → AI 猜 → 编译过就交付 → 用户人肉测 → 用户再描述`（长循环、用户被卷入多轮）
变为
`AI 改 → AI 跑测试 → FAIL 自己再改 → 全绿才交付`（短循环、用户只参与最后一环）。

**已给方案方向（待用户拍板）**：

| 方案 | 内容 | 作用 |
|---|---|---|
| A | 给高危纯逻辑模块（TimeParser / CryptoService / 同步冲突判定）写测试 + 一键运行入口 | 解决「有没有东西可跑」 |
| B（推荐，与 A 配套） | 项目级规则文件写明「改完必须跑测试，FAIL 不算交付」 | 解决「AI 会不会真跑」 |
| C | 把 REGRESSION.md 可自动化条目全部自动化 | 覆盖最高，成本也最高；界面类仍无法自动化 |

**A + B 必须配套**：只有 A 则 AI 可能不跑；只有 B 则无东西可跑。二者缺一，需求不成立。

**诚实边界（已告知用户）**：①测试只能拦住「写出来的用例」覆盖到的问题；②界面层 bug（窗口不弹 / 热键失效）仍需人工；③测试本身需随功能同步维护（由 AI 维护，需在规则里写明"改功能必须同步改测试"，否则三个月后变死文档）。

## 测试维护机制设计（用户提出「别做成有害的摆设」，2026-09-11）

用户提出关键质疑：测试怎么判定过时？谁判定？什么时候判定？判定后怎么处理？——「我不希望做一个今天用着很好、用一段时间就是摆设、甚至是有害摆设的东西」。

### 给出的机制设计

**1. 「过时」分两种，危险程度差一个量级（核心区分）**

| 病 | 成因 | 症状 | 危险性 |
|---|---|---|---|
| 误报 | 功能设计有意改了，测试仍按旧标准卡 | 测试红但软件是对的 | 中——导致用户无视测试 |
| **放水** | 测试红了不修代码，而是**把测试标准改成符合当前代码行为** | 测试全绿但软件是错的 | **高——绿灯保护 bug，且有「已验证」的假安心** |

放水的最常见成因：改代码的角色（AI）自己有权改测试标准 → 会选择"最容易通过的路径"。

**2. 判定时机：靠自动报警，不靠定期体检**
功能一改，测试立刻变红，**红色即判定时刻**。不设「每月检查测试是否过时」的定期任务（注定被遗忘且无人知晓）。

**3. 处置流程（四步，责任分明）**
1. 测试亮红灯
2. AI 先按「代码错了」处理，自己查自己修（不打扰用户）
3. 修不好 → AI 必须停下来，**用中文**说清：分歧在哪、两种可能是啥
4. 用户回答后才继续；改测试标准必须记录原因。**只有用户能拍板改标准**

**4. 红线（防放水）**
禁止 AI「为了让测试通过而修改测试标准」。改标准必须：用户确认 + 在测试代码里写明改的原因与日期。

**5. 监督机制（用户可执行）**
AI 每次交付必须**附上测试输出**（贴出 PASS/FAIL 结果），把证据摆出来；而不是只口头说"测过了"。此举可呼应既有四段式交付报告（改了什么/影响哪些/验证了什么/没验证什么）。

**6. 起步策略（防「信任崩塌」）**
不要一开始追求覆盖率。首批只放 3–5 条**最稳、最不易变**的检查（如「加密后必须能原样解密」这类核心不变量），先让它建立可信度，再逐步加。若一开始就一堆测试频繁误报，用户会很快学会无视它——那才是真正的死因。

**用户实际时间投入量级**：每次改动跑一遍由 AI 承担（30 秒–1 分钟机器时间）；用户仅在「设计变更」时回答一个问题（几秒）。合计约每周几分钟。

**待办**：等用户确认此机制，再动手建测试工程（起步范围未拍板）。

## 闭环补全：接口与防作弊设计（用户追问「还差点什么」，2026-09-11）

用户提出两点疑问：①加新功能时 AI 能否主动加检查点？②改动涉及 3 个检查点时，只测 3 个还是全量测？并明确要求：**主动显化他因知识储备不足而意识不到的盲点**。

### 两项决策（本次定案）

**1. 新功能是否进测试 → 写成硬规则，不靠 AI 自觉**

- 原因：写测试不产出功能，是纯成本；无明确要求时 AI 的自然选择是不写
- 判定标准：**「新增功能未补检查点 = 交付未完成」**（不满足就不算做完）
- 落点：项目根目录 `REGRESSION.md`（用户已有，每次开工必读）；写在对话里的承诺会被遗忘，写进文件的约束不会
- 顺序约束：**先出中文规格 → 用户确认 → 再写检查点**。防止 AI 自定标准又自写测试

**2. 跑测试范围 → 全量跑，不做增量**（关键定案）

- 用户「只测 ABC 三个」的问法本身有陷阱：**「影响哪三个检查点」这个判断是 AI 给出的**。AI 的推理可能漏，漏掉的那条就永久未被验证，而用户以为验过了
- 链路影响是传递的（CryptoService → NoteService → 同步），凭「被谁引用」数关系不精确
- 成本账：全量跑 = 秒级到几十秒、**不烧 token**；维护「代码↔检查点」映射表 = 持续成本。全量跑是更划算的那边
- 定死：**默认全量跑；报告时可标注「本次改动相关的是哪几条」，但跑要全跑**
- 唯一例外：将来检查点多到跑一次需数分钟以上才值得拆。现在几十条，谈增量属过早优化

### 主动显化的盲点（用户未问但结构性存在）

| # | 盲点 | 危害 | 破解 |
|---|---|---|---|
| 1 | **检查点最值钱的来源 = 用户踩过的每个坑** | 靠凭空想检查点，覆盖率随机 | 每修完一个 bug 必须补一条永久检查点（回归测试的本质；直接命中用户「简单 bug 绕多轮」的痛点） |
| 2 | **出题人 = 答题人 = 判卷人**（AI 写标准、写测试、自己判自己） | 结构性漏洞 | 三层破解：①标准来自用户确认的中文（REGRESSION.md）②测试文件改动必须显式报告 ③定期把检查点清单用中文念给用户听，让其做最终仲裁 |
| 3 | **测试文件本身会被放水**（不只「放松断言」，还包括**直接删掉困难的检查点**） | 比改标准更隐蔽 | 交付报告必须含测试文件的 diff 说明；删检查点等同改标准，需用户确认 |
| 4 | **失败信息必须是中文人话** | 用户看不懂堆栈，只能听 AI 转述，防作弊机制失效 | 检查点失败时输出中文说明（期望什么/实际什么） |
| 5 | **「假红」需与「真失败」区分**（环境问题：文件被占用、临时目录权限） | 误报导致用户无视测试 | 失败时先分类：代码问题 vs 环境问题 |
| 6 | **测试全绿 ≠ 没有 bug** | 用户形成错误信任 | 诚实告知：只证明「检查过的这些没坏」 |

### 交付形态

一张内联闭环图（六步蛇形布局，标注「原来缺的三道关」）。未改代码，无 present_files。

## 方案自审：真矛盾 / 真遗漏 / 更轻方案（用户要求以审查者身份复核，2026-09-11）

用户四项要求：①公平客观审查整套设计（矛盾/遗漏/可完善）②第一性原理找更轻方案，若有为何不用 ③担心全量跑长期膨胀成技术债 ④抽象出可复用的跨项目测试规范。并强调**不许无中生有挑刺**。

### 自审发现（区分真问题 / 表述问题）

**真矛盾 1：禁止改测试标准 vs 测试须随功能变更**

- 「功能有意改了 → 测试红是正确红」与「AI 不许改测试标准」直接冲突，按原绝对表述 AI 会卡死、红灯长期挂着 → 用户无视测试
- 修正：区分两种红——**修 bug 引起的红**（代码错，测试不动）/ **需求变更引起的红**（标准过时，该改但须用户确认）
- 补充降级规则：**用户不在线时不许静默，红就是红，交付报告必须标红**，禁止 AI 自行认定「这算需求变更」

**真矛盾 2：规则写进文件 ≠ 硬约束（原表述过强）**

- 与 SOUL.md 三-11「文档只是软约束，真正的锁是交付标准」自相矛盾
- 真正的锁有两把，都不在文档里：①**用户验收动作**（交付后第一句问「测试结果呢」）②**交付报告固定栏目**（「验证了什么」从一句话变成「跑几条/过几条」）

**真遗漏 1（严重）：测试数据隔离从未提及**

- 测试要验「保存笔记 / 同步」，若跑在真实数据目录上，写错的测试会搞乱甚至删除用户笔记——项目核心资产
- 必须写死：**测试一律跑在隔离临时目录，绝不可指向真实数据目录**；建议列为规则第 0 条

**真遗漏 2：新检查点自身可能写错，且会反向带偏代码**

- 原设计只防「AI 放松标准」，未防「标准本身错误」：AI 理解错期望行为 → 写进测试 → 为让测试绿而修改**本来正确的代码** → 代码被带偏且测试一路绿灯保护错误
- 修正：**新检查点写完先在当前代码上跑，必须全绿**；红了不许动代码，先问用户「我理解期望是 X，代码实际是 Y，哪个对」

**真遗漏 3：技术可行性未验证，且可能失败**

- 项目为单项目 / WPF / 无 .sln；要让测试程序跑到主项目类，需确认目标类**不依赖 System.Windows**
- 归档的 `fc-sync-test` 用「独立 Console + 直链源文件」，对纯逻辑类可行，引用 WPF 类型则编译失败
- **未实测 TimeParser / CryptoService 是否依赖 WPF**，必须先做可行性验证，结果可能为否

### 膨胀问题：用户担心正确，但成因判断需修正

- **条数不是问题，耗时才是**。纯逻辑检查点微秒级，1000 条也可能不到 1 秒；真正拖慢的是文件 IO / 假云盘服务 / 进程启动 / 等待

- 技术债真正来源不是检查点多，而是**过时/误报的检查点无人清理**

## 游标保护缺陷：实测暴露并修复（commit `83c2d91`）

**结论：推断成立，缺陷真实存在，已修复 + 加常驻检查点。**

### 实验设计（`TestCursorProtectionAsync`）

1. 基线同步 → 记录游标
2. 向云端注入一条「用别的钥匙加密的行」（模拟他端以不同密钥推送的数据）
3. 本机新增一行 —— 制造「本轮既有解密失败、又有本地新增待推送」的组合
4. 同步 → 观察游标是否推进

### 最值钱的部分：方法论教训（本日最大收获）

**前两次实验都显示「游标不推进 = 保护有效」，是假象。**

原因：注入行与本地新增行的上传时刻落在**同一秒**内 → 游标值相等 → 看起来"没推进"。
加 `await Task.Delay(1100)` 隔开后才暴露真相：`09:36:45Z → 09:36:47Z`（**推进了 2 秒**）。

→ **涉及时间戳比较的实验，必须排除同一时间精度内的「相等假象」。**

### 修复与验证

| | 修复前 | 修复后 |
|---|---|---|
| 游标变化 | `45Z → 47Z`（推进 2 秒） | `06Z → 06Z`（不推进） |
| 检查点结果 | FAIL | PASS |

修复位置：`SyncNotesCoreAsync` 记录 Pull 前游标，若 `decryptFailed > 0` 则 Push 后回退。

**修复前的危害**：设备在「拉不到数据」的同时若本地也有新增 → 那批未拉到的行因
`UpdatedAt/UploadedAt ≤ 新游标`，在下轮增量拉取中被**永久过滤**，密钥对齐后也捞不回。

另：移除 D 组「换码重传后游标已重置」断言（不稳定 —— 是否前移取决于时间戳比较）。

### bug2 定根：未到期待办在本机删不掉

`QuickViewWindow:727 → NoteService.DeleteNote → FindEntryFile`：`FindEntryFile` 只找 **`灵感_{entry.Timestamp:yyyy-MM-dd}.md` + 标签文件**，而**带提醒的待办在写入时被归类到 `DueTime` 日文件**（`SaveNote`: `TodoDisplayTime(entry).Date`）→ 文件名对不上 → 返回 null → 弹「删除失败：未在笔记文件中找到该条目」。

**「只有创建设备删不掉」的解释**：另一台从云端拉到同一条时，落地路径 = CreatedAt 日文件 → 与其 `Timestamp` 日一致 → 找得到、删得掉；而创建端本体在 DueTime 文件里 → 找不到。

**「B 删了 A 还在」的解释**：墓碑 ID = hash(B 的行所在路径｜行)；A 的行在另一文件 → ID 不同 → 墓碑匹配不上 A 的行 → A 保留。

### 真正的根（两个 bug 同一个根）

**行的身份 = SHA256(相对路径｜行文本)，而"路径"在系统里有三套口径：**

| 环节 | 现在的口径 |
|---|---|
| 本地写入 `SaveNote` | **DueTime 日**文件 |
| 删除/查找 `FindEntryFile` | **Timestamp 日**文件（且不扫全部） |
| 跨端落地 `ResolveRelativePath` | **CreatedAt 日**文件 |

→ 同一条逻辑行在不同设备/不同操作下落到不同文件 = 不同 ID ⇒ ①跨端删除/状态变更失效 ②旧版本行永久驻留云端被反复投递（复活）③本机删除找不到文件。
