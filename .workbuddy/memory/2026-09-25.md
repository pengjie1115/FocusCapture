## 2026-09-25 [WorkBuddy] 流程讨论第二轮：快层耗时归因（**结论：文档写错了**）

**实测（全部可复现，均已排除编译与外壳）**

| 项 | 实测 |
|---|---|
| `dev.ps1 test`（快层，干净跑） | **58.3 s** |
| 同上，连续热态两次 | 49.4 s / 47.9 s |
| **直接跑已编译的 `FocusCapture.Tests.exe`（纯断言）** | **44.6 s** |
| `dotnet build tests/`（增量） | 2.9 s |
| `dotnet run --no-build` | 45.1 s（≈纯断言） |
| 起一个已编译 .NET 进程并退出 | 0.25 s |
| 慢层断言（605 条） | 45.7 s（墙钟 63.2 s，差 17.5 s 为启动/沙箱） |

- **核心结论（事实）**：快层 175 条 → **254 ms/条**；慢层 605 条 → **76 ms/条**。**快层每条比慢层贵 3.3 倍。**
  `REGRESSION.md` §二 写的「快层｜纯逻辑，秒级」**是错误描述**，从写下来那天就错。
- 逐行间隔测量（管道有缓冲，**近似**）：~28 秒（63%）压在 **[9] 内置技能落地与恢复 / [10] 运行时下载器** 附近。这两组不是纯逻辑：真实文件复制/备份/原子替换、自建本地 TcpListener HTTP 源、解压、目录清理。
- 相关环境税（实测）：**连一个没人监听的 loopback 端口 = 2.07 s**（PITFALLS 已记同类现象）；建 300 个小文件 0.56 s、递归删 1.04 s。`[10]` 用 `localhost` 去连只绑 `127.0.0.1` 的服务会先撞 ::1，按次付这笔税（**推断**）。
- 指令入口实证：最近 6 天日志里 `test -Slow` 出现 0~3 次，而 `ready` 频繁出现 → **实践中走的是全量入口**，「慢层按需跑」没被使用。
- 文档提交占比：30 天 220 提交中**纯 docs 提交 71 次（32.3%）**；`.workbuddy` 被跟踪 30 个文件，其中 **25 个是 daily 日志（83%）**。

**自我更正两处（上一轮的方案有错）**

1. 「`ready` 从每次交付改成合并前一次」表述偷懒 → 准确版：**按触发条件分层 + 把快层真正压到秒级**。快层 45 秒，「每次改动后跑」物理上执行不了，被跳过是必然，不是纪律问题。
2. 「检查点命中账本 + 让用户判断删哪些」**方案错误** → ① 「从没触发过」是成功指标（防线没被攻破），不是删除指标 ② 不该把技术判断推给不懂代码的用户。替代机制：**自动变异测试**（在被守护代码里注入故障，看检查点是否变红 = 证明它**现在**还有杀伤力）+ 孤儿检查点静态检测 + 重复项参数化合并。**变异测试成本未验证，属建议**。
3. 补：清理目标是「**消灭慢的条数**」，不是「减少条数」。会话分组 74 条仅 0.5 s、拖放保存 46 条 68 ms —— 清这类收益为负。

## 2026-09-25 [WorkBuddy] 流程讨论第三轮：对照业界正规做法（已查证，带来源）

用户问「这一摊是不是都在干回归测试？正规军怎么做？」。查证结论（来源：Google Testing Blog 测试分桶、Software Engineering at Google 第 23 章 CI、TAP 论文 ICSE-SEIP2019、Meta ACH 工程博客 2025-09-30、Nx affected 文档）：

**拆解：我们这一摊其实是 4 件不同性质的事捆成一个动作**
① 780 条断言 = 回归测试本身 ② `dev.ps1 ready` = 发布门禁（执行政策，不是测试） ③ `REGRESSION.md` = 验收清单 **+ 知识库**（混装，34% 是设计知识） ④ `.workbuddy/memory/` = 知识管理 / 决策记录（**与回归测试无关**）。→ 「效率被摁住」的根因不是测试重，是**该分开的没分开**。

**业界四层防线（关键：他们也不是每次跑全量）**
| 层 | 正规军 | 我们 |
|---|---|---|
| ① 保存时 | Google Small 测试：单进程、**无 I/O、无 sleep、无网络**、≤60s，**由框架强制**（开了 socket 就 fail） | 快层，但实测 44.6s，且 [9]/[10] 真做 I/O 与本地 HTTP |
| ② 提交前 presubmit | **只跑依赖图选出的受影响最小集**（150M 测试里 typically <0.1%）；平均等 11 分钟；过 presubmit 有 95%+ 概率过其余 | **每次跑全量 177 秒** |
| ③ 提交后 postsubmit | 异步跑**全部受影响**测试（含 Large） | 我们把 ③ 的活压进了 ② |
| ④ 上线后 | 灰度 / 监控 / 自动回滚；**回滚优先于修好再往前** | **无服务端、无遥测（红线 12），结构上没有** |

- **最重要的差异**：Google 敢把全量放提交后，是因为有 ④ 兜底（回滚优先、「Build Cop」守门）。我们的 ④ 等价物 = **「每完成一步立即提交」这条纪律**（有了它才能丢掉坏分支）→ 这条纪律**不能砍**，它是最便宜的安全网。
- 规模变大后的重点转移（原文）："at scale, test selection and flakiness management are more important than test writing." —— **我们一直在加检查点，从没做「选择」与「可信度管理」**，方向正好相反。
- flaky 是独立资产：Google 实测 1.5% 跑次 flaky、**84% 的 pass→fail 是 flaky 引起**；>2% flaky 的测试**自动隔离出关键路径 + 自动建单**。我们的规矩只有「红不许瞒」，**没有「这条红了但与本次改动无关」的处置出口** → 缺隔离机制会让人开始不信门禁。
- 变异测试业界的真实用法（Meta ACH）：**不是用来删测试**，是用来**生成缺失的测试**（定向、真实、LLM 判等价体；试点接受率 73%）。→ **修正上一轮建议**：方向应是「找没被守住的代码」，不是「找没用的检查点」。

**可借鉴（按性价比）**：① 给测试桶加**强制力**（快层禁 I/O/网络/sleep 要机器拦，不能只写文档）② 测试选择**从代码反推**取代手写触发表 ③ 给 flaky 一个隔离出口 ④ presubmit/postsubmit 分层 ⑤ 保留「每步提交」（我们的回滚能力）。
**不该借**：CI 农场 / 分布式构建、金丝雀与生产监控（无服务端）、变异测试当常规门禁（Meta 自己都说贵 + 等价变异体数学上不可判定 —— 我们这种单人单机规模，现实形态只能是季度抽查 10 条，非全量）。
**反直觉结论**：真正的效率黑洞不在测试（108s/177s），而在文档与知识管理（30 天 71 次纯 docs 提交，32%）—— 顺着「都在干回归测试」去优化，方向会错。

## 2026-09-25 [WorkBuddy] 流程讨论第四轮：以微信为参照（来源已分级）

用户问「微信这么大的成熟 App，像我们这样干不得累死？」。查证结果（**来源强度已标注，弱来源不得当事实用**）：

- **一手有力（第一财经对陈磊·时任腾讯高级执行副总裁兼腾讯云 CEO 的报道）**：原话「客户端产品发布新版本其实是一件很困难的事，必须让用户下载才能完成更新。微信团队做了很多的后台开关，'很多的功能能不能被用户用到'，或者'表现形式是什么'都有后台控制的」；「前几个版本，功能上线都是一部分用户先使用，另外一部分用户是看不见的……用的多，就往前挪，用的少，删掉」。同一篇称微信团队「每天可以发 20 个版本」（指服务端/后台，非客户端）。
  → **微信把"改动的代价"从「发版 + 全量回归」降成「改一个开关」（开关是数据不是代码）**。这套机制我们一个字用不上（无服务端，红线 12）。
- **腾讯官方产品站 TAPD 的微信案例**：迭代**第三周后冻结需求范围**；迭代最后一周对**小部分用户开 α 版做灰度**；灰度期 crash 信息自动同步成缺陷单。→ 微信的「全量回归」是**月级发版前**的动作，不是每次提交的动作。
- **弱来源（百科 / 头条类，未找到官方口径，只能当参考）**：正式版大版本 30-60 天一次、小补丁 7-20 天；灰度分批随机按账号、发现问题「临时收回部分账号的新功能，回滚调整」。
- **行业通用做法（AWS Device Farm 官方页 + 移动端 CI/CD 资料）**：真机云（2500+ 台真机并行）、Monkey/fuzz 随机遍历（Android 自带 UI/Application Exerciser Monkey）。**关键原文**：monkey 这类非确定性测试「最有效的 CI 集成方式是 nightly 或合并到主干时跑，**不是每次提交**，因为结果非确定且耗时」。Canary + 崩溃门禁：灰度 60 分钟后自动查 crash-free session rate，低于阈值自动停量并回滚。行业总结与 Google 同构：「layered defense：每次提交跑快且确定的，合并到主干跑更宽的概率性检查」。
  → **他们的检查点是自动生成的（随机/遍历），我们是人手写的**。人手写的清单必然腐化（本项目已实测：条数三处三个数、承诺的清理 0 次执行）。

**公平话（不要动）**：REGRESSION 现在的优先级排序 = 不可逆损失类（加密/同步/删除）重投入、界面类只留快照 + 人眼，**这恰好是"唯一用户就是开发者本人"这一条件下的最优策略**，别改。
