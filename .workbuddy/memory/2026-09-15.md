## 第三轮：本地元数据缓存方案（用户新构想，架构讨论中）

**用户构想**：本地维护一个文件区 + 本地元数据 JSON；百度网盘当**纯仓库**（只做数据中转站）；检索/筛选/分析全在本地完成；元数据随笔记待办一起同步到坚果云，登录时先拉它。写入路径＝先存本地 → 建元数据 → 后台异步上传网盘；读取路径＝查本地元数据定位 → 取回。本地区可设保留时长/容量上限。

**已拍板的决策**：
1. **按需下载**（关键转向）。登录只同步元数据（几 MB，秒级），文件本体**用户真的要用时才下载**。用户最初说的"登录静默全量拉回"已放弃。
   理由：全量拉回与本地容量上限**互斥**（本地 50G / 云端 200G → 拉满即死循环）；改按需后"淘汰复活""首登雪崩""要不要黑名单"三个问题**同时消失**。
   依据：用户自己的原始描述就是按需的——"先在本地元数据里找到存到网盘哪里，**然后直接过去拿**"。
2. **本地角色 = 缓存**；网盘 = 全量权威仓库。本地删除/淘汰不影响网盘。
3. **不做全量自动拉 → 不需要"云端不要名单"**。只保留「彻底删除」一个云端标记（走现有回收站 + 墓碑机制防复活）。
4. **淘汰 = 设备级事件，只在本机记账，绝不写云端**。用户原建议是"把不要名单放云端"，其中「用户主动不要」放云端是对的（账号级意图），但「自动淘汰」混进去会造成**自动过期变永久删除**——已指出并被接受。
5. **淘汰机制**：时间 + 容量**双条件**，设置面板可调。
6. **网盘里已有的老文件不纳入**（受 `/apps` 沙箱限制，需手动搬运）；只管从本地上传的新文件。
7. **文件实体区复用现有 AI 问答附件的文件夹**，不另起炉灶（顺带解决"B 设备看不到附件"这个现存缺陷）。
8. **附件上网盘的开关默认关**（保持现有"只存本机"行为），手动开启。

**讨论中/待定**：
- 附件上传触发方式：用户倾向"开启后自动上传 + 云端按 N 天（可设，如 30 天）保留"。⚠️ 已指出问题：**"云端也自动清理"会让网盘从"全量仓库"退化成"滚动窗口"**，与方案根基冲突 → 建议按类型分级：**产出文件/用户主动上传的文件云端永久保留；仅"对话附件"类可设保留期**。
- 副作用待用户知悉：云端附件到期删除后，历史对话里的附件引用会变死链。
- ⚠️ **隐私边界变化必须用户明确拍板**：现有"AI 问答附件只存本机、不进同步"是有意设计；纳入网盘通道＝附件离开本机到第三方，与项目"数据全本地"定位有让步。

**方法论沉淀（可复用）**：用户提出"把某名单放云端"时，先拆**意图级 vs 设备级**两类事件——意图可跨设备共享，设备状态不可。混在一起的典型后果是「自动过期变永久删除」。

### 第五轮：用户把「AI 对话框存取文件」定为本次基座

用户补充关键定性：本地文件夹 + 自动同步只是**后台存储**；**用 Agent / AI 对话框「存文件到网盘」和「从网盘取文件」这两条必须支持，是本次更新的基座**。没有这一层，网盘接入退化为需要手动操作的同步盘。

**五个判断（已写入文档）**：
1. **五条链路**：A 把 AI 生成内容存网盘（**最轻**，内容在内存、不需要文件路径）/ B 对话已附附件存网盘 / C 本机任意文件存网盘（**依赖「选择文件」入口**）/ D 从网盘找到文件交给用户 / E 取回读内容自用（受"本项目未做 PDF 解析"限制）。**C 与 D 是基座核心体验**
2. **安全红线（最重要）**：**工具的路径参数绝不能由 AI 生成** —— 否则模型可编造任意路径，等于把整台电脑文件系统向 AI 敞开，与 `LocalTools.cs`「只作用于笔记库」的沙箱设计直接冲突。解法：**「用户选择 → 产生句柄 → AI 只能引用，无法凭空构造」**，AI 可达范围＝用户亲手点过的文件
3. **交付动作四选**：打开 / 资源管理器定位 / 下载到指定位置 / **插入当前对话当附件（推荐至少做这个，能与现有附件机制打通）**
4. **实施顺序改为三阶段**：阶段一最小闭环（授权+上传+取回+链路 A/D 两个工具）→ **目的是尽早实测限速**；阶段二基础设施（本地文件区、元数据、按需下载、缓存账本）；阶段三体验治理（选择文件入口、淘汰、附件开关、设置面板、到期清理）
5. **基座定位改变了优先级**：AI 存取链路 > 本地缓存基础设施。原计划"先搭本地缓存再开放"是反的

**记录要点**：用户明确"这个是这次更新的基座"——后续任何方案裁剪都不得砍掉第七章的 A/C/D 链路。

### 第十二～十三轮：下载实测 0.08 MB/s + 上传通畅 → 方案重新定位

**单连接下载实测（脚本跑通，关键数据）**：
| 已用 | 已下载 | 平均 |
|---|---|---|
| 5s | 0.4 MB | 0.08 MB/s |
| 13s | 1.0 MB | 0.08 MB/s |
| 18s | 1.4 MB | 0.08 MB/s |

→ **0.08 MB/s ≈ 80 KB/s，第 5 秒后稳定不再上升**（开头 0.20 是冷启动噪声）。是**限速曲线，非网络抖动**。
→ 换算：100MB ≈ 21 分钟 / 1GB ≈ 3.5 小时 / 10GB ≈ 35 小时
→ **印证调研**：第三方「非 SVIP 的 API 限速 50–300KB/s」→ 实测落在区间内 ✅
→ 按原方案判定：**取回通道不可用**

**用户补充实测（改变定性）**：
- **上传：很快，几乎没有限速** ✅
- **客户端下载同一 50MB PDF**：前 30 秒 1.x MB/s，之后波动，多数 200–300KB/s，偶有 500–900KB/s

**三条关键推论**：
1. **方案没死** —— 上传通畅 ⇒「存」这条路完全成立，可重新定位为**归档为主、取回为辅**
2. **API 被额外压制** —— 客户端 200KB–1MB/s vs API 稳定 80KB/s，差 3–10 倍
3. **80KB/s 的「稳定」像是每连接限速**（而非总带宽限制）⇒ **多连接并发可能叠加**。这是唯一可能救回"自动取回"的路 → 已给脚本追加「8 连接并发对比」（`curl.exe` + Range 分段，各进程下到临时文件后统计字节）。已验证 BOM/SYNTAX/curl 可用。

**若多连接无效，方案需重定的点（已预判，待与用户讨论）**：
- 主用途改为 = **上传归档（全自动）+ 取回走客户端手动**（比 API 快 3–10 倍）
- ⚠️ **本地 5GB 上限 + 慢取回是矛盾的**：超限被淘汰的文件要取回极痛 ⇒ 淘汰策略必须重定（要么上调上限，要么极保守淘汰）

**方法论沉淀**：判断"是否限速"要看**速度曲线是否稳定**（稳定 = 被限速的信号）；判断"能否多线程救"要看**客户端与 API 的速度差**（差得多 = API 有额外单连接压制）。

### 第十四轮：用户质疑脚本准确性 → 交付三方式对照诊断

**用户质疑（站得住）**："为什么脚本测出来每次都是稳定 80K？是不是脚本有问题？跟 APP 上下载差距太大。"

**我承认的疏漏**：上一轮直接归因"服务端限速"，**跳过了「脚本自身有问题」这一步**。80KB/s 稳定得毫无波动，本身就可疑。主要嫌疑：**PowerShell 的 `HttpWebRequest` 逐块读流**——若底层每次只返回少量数据，循环开销会拖垮吞吐（这是 PowerShell 层的固有开销，不是百度的问题）。

**已交付**：`tools/baidu-diag.ps1` + `baidu-diag.bat`（**新文件，不动已跑通的旧脚本**）
同一文件、同一条 dlink，三方式对照：
- **A. HttpWebRequest 单连接**（原脚本方式）
- **B. curl 单连接**（换客户端实现，其余条件不变）
- **C. curl 8 连接分段并发**（Range 请求，各进程下到临时文件后统计）

判读：A 慢 B 快 → 脚本读取方式问题 / A B 都慢 C 快 → 单连接限速可叠加 / 三者都慢 → 服务端确实限速
已验证：BOM（EF BB BF）✅ / 语法 ✅ / bat 纯 ASCII ✅ / curl.exe 可用 ✅

**待用户**：跑诊断脚本，把 A/B/C 六个数字发回。

**方法论沉淀（重要，跨项目可复用）**：**测量工具本身必须先被验证**。用自研脚本测外部服务性能时，**必须设一个独立实现的对照组**（本机 `curl` 零成本），否则无法区分"被测量对象慢"与"测量工具慢"。这与夸克那次「假绿」是**同一类错误的反向版本**——那次是环境不对导致**假通过**，这次是工具不对可能导致**假不通过**。

### 第十五轮：诊断脚本自身有 bug（已定位并修复）

**首轮诊断结果**（被测 8.54 MB 的 .doc）：
```
A. HttpWebRequest 单连接 : 0.08 MB/s (80 KB/s)
B. curl 单连接          : 0 MB/s    (1 KB/s)     ← 异常
C. curl 8 连接并发       : 0.01 MB/s (8 KB/s)     ← 异常
```

**我的 bug（根因）**：给 curl 传 `-H "User-Agent: pan.baidu.com"`，**参数值里含空格，而 PowerShell 的 `Start-Process -ArgumentList` 拼命令行时不加引用** → 该头被拆成 `User-Agent:`（空值）+ 裸网址 `pan.baidu.com`，curl 实际收到两个 URL 和一个空头。**B/C 两组数据全废**，脚本还据此报出"并发有救"，结论也是错的。
→ **教训：`Start-Process -ArgumentList` 传含空格参数必须自己加引号，或改用无空格的等价写法**（本次改为 curl 的 `-A pan.baidu.com`）。
→ **辅助教训**：`-s` 纯静默会吞掉 curl 的错误输出，导致"下载失败"被当成"下载很慢"。诊断类脚本应用 `-sS`（静默但显示错误）。

**已修复**：① 两处 `-H "User-Agent: ..."` → `-A pan.baidu.com`；② `-s` → `-sS`；③ HttpWebRequest 显式 `$req.Proxy = $null` 并打印代理状态；④ **新增：把「纯直链」（不含 access_token）自动复制到剪贴板**，用户可直接贴给我在本机复测，**省去反复授权**。已验证 BOM/SYNTAX，`-H` 残留 0 处、`-A` 2 处。

**待用户**：重跑诊断，发回 A/B/C 三个数字 + 剪贴板中的直链。

**方法论沉淀（补）**：**脚本报出"反直觉的极端值"时，第一反应是查自己的参数传递，而不是下业务结论** —— 1KB/s 与 80KB/s 差 80 倍，这种量级差不合理，本身就是 bug 信号。
